# Collection Iteration

After choosing a data structure, most algorithms still need to visit its elements. If every caller had to understand how arrays, nodes, trees, or hash buckets were stored internally, code would become tightly coupled to implementations. Java separates the **traversal protocol** from the **storage structure** through `Iterable`, `Iterator`, `ListIterator`, and `Spliterator`.

## <a id="iterator-contract">Iterator Contract</a>

`Iterator<E>` represents a logical cursor moving through a sequence of elements:

```java
Iterator<Order> iterator = orders.iterator();

while (iterator.hasNext()) {
    Order order = iterator.next();
    System.out.println(order.id());
}
```

Its core operations are:

- `hasNext()` asks whether another element exists;
- `next()` returns the next element and advances the cursor;
- `remove()` is an **optional operation**, available only when the specific iterator supports it.

Calling `next()` after the iterator is exhausted throws `NoSuchElementException`. Callers should not use that exception as the normal loop condition; the standard pattern checks `hasNext()` first.

An iterator does not promise one universal ordering. Its encounter order comes from the source collection:

- `ArrayList` iterates in list order;
- `LinkedHashSet` iterates in its defined encounter order;
- `TreeSet` iterates in sorted order;
- `HashSet` promises no particular encounter order;
- a `PriorityQueue` iterator does not promise priority-sorted order.

That separation lets algorithms depend on an interface while preserving source semantics:

```java
void printOrders(Iterable<Order> source) {
    Iterator<Order> it = source.iterator();
    while (it.hasNext()) {
        System.out.println(it.next());
    }
}
```

Iterators are normally stateful and represent one forward traversal. To traverse again, obtain a new iterator from the collection.

Directly changing a collection's structure while an iterator is active may invalidate iterator assumptions and can trigger fail-fast behavior in many ordinary collections. The Fail-Fast chapter owns the details of `ConcurrentModificationException`; the key point here is that mutation during traversal must follow the iterator/collection contract.

## <a id="enhanced-for">Enhanced For</a>

The enhanced `for` loop is syntax for using a traversal protocol without manually managing an iterator.

```java
for (Order order : orders) {
    System.out.println(order.id());
}
```

For an object implementing `Iterable<Order>`, a useful mental desugaring is:

```java
for (Iterator<Order> it = orders.iterator(); it.hasNext(); ) {
    Order order = it.next();
    System.out.println(order.id());
}
```

This is a mental model, not a requirement that generated bytecode have exactly this shape. The important point is that enhanced for depends on the iteration contract rather than `ArrayList`, `HashSet`, or another concrete class.

Arrays also work with enhanced for:

```java
Order[] array = {orderA, orderB};
for (Order order : array) {
    System.out.println(order.id());
}
```

Arrays are a language-level special case; an array does not implement `Iterable` and does not create a collection `Iterator`.

Enhanced for is ideal when the algorithm only needs each element. It does not directly expose:

- the current index;
- `Iterator.remove()`;
- coordination between multiple iterators;
- split/traversal control from `Spliterator`.

When an algorithm needs those capabilities, using the traversal API directly is clearer.

## <a id="iterator-remove">Safe Iterator Removal</a>

A common mistake is removing directly from a collection inside enhanced for:

```java
for (Order order : orders) {
    if (order.totalCents() == 0) {
        orders.remove(order); // may invalidate the iterator used by the loop
    }
}
```

When the iterator supports removal, remove through that iterator:

```java
Iterator<Order> it = orders.iterator();

while (it.hasNext()) {
    Order order = it.next();
    if (order.totalCents() == 0) {
        it.remove();
    }
}
```

`Iterator.remove()` removes the last element returned by `next()`. Two contract details matter:

1. `remove()` is optional; an iterator from an unmodifiable collection or an implementation without removal support may throw `UnsupportedOperationException`;
2. calling `remove()` before `next()`, or twice for the same `next()` result, throws `IllegalStateException`.

For example:

```java
Iterator<Order> it = orders.iterator();

Order first = it.next();
it.remove(); // valid if removal is supported

// it.remove(); // IllegalStateException: no new next() call
```

When the intent is simply to filter a mutable collection by a predicate, `removeIf` is often more direct:

```java
orders.removeIf(order -> order.totalCents() == 0);
```

Understanding `Iterator.remove()` is still valuable because it shows how mutation can be coordinated with traversal. Fail-fast behavior and structural-modification rules are covered in the later dedicated chapter.

## <a id="listiterator-contract">ListIterator: Bidirectional Traversal and Positional Mutation</a>

`ListIterator<E>` extends the iterator idea specifically for `List`. In addition to moving forward, it can move backward, expose neighboring indexes, and coordinate mutation with the traversal position.

```java
List<Order> orders = new ArrayList<>(List.of(orderA, orderB, orderC));
ListIterator<Order> it = orders.listIterator();

while (it.hasNext()) {
    int index = it.nextIndex();
    Order order = it.next();
    System.out.println(index + " -> " + order.id());
}

while (it.hasPrevious()) {
    Order order = it.previous();
    System.out.println(order.id());
}
```

Characteristic operations include:

| Operation | Meaning |
| --- | --- |
| `hasPrevious()` / `previous()` | move backward |
| `nextIndex()` / `previousIndex()` | inspect cursor position |
| `set(e)` | replace the element returned by the latest `next/previous` |
| `add(e)` | insert at the cursor position |
| `remove()` | remove the element most recently returned by traversal |

For example, normalize an order while traversing:

```java
ListIterator<Order> it = orders.listIterator();
while (it.hasNext()) {
    Order current = it.next();
    if (current.totalCents() < 0) {
        it.set(new Order(current.id(), current.userId(), 0));
    }
}
```

Use `ListIterator` when the algorithm genuinely needs **position + bidirectional traversal + traversal-aware mutation**. Enhanced `for` is simpler for read-only element processing, while `removeIf` is often clearer for predicate-based removal. `add/set/remove` remain optional operations when the underlying list does not support mutation.

## <a id="spliterator-boundary">Spliterator Boundary</a>

`Spliterator<E>` can be viewed as a traversal abstraction that extends the iterator idea with two capabilities:

1. visit elements;
2. attempt to partition the source into pieces that can be processed independently.

```java
Spliterator<Order> spliterator = orders.spliterator();

spliterator.tryAdvance(order ->
        System.out.println(order.id())
);
```

`tryAdvance` processes one element when available and returns whether it succeeded. `forEachRemaining` consumes the remainder.

The distinctive operation is `trySplit()`:

```java
Spliterator<Order> left = orders.spliterator();
Spliterator<Order> right = left.trySplit();
```

An implementation may return another spliterator representing part of the data, or `null` when it cannot or chooses not to split further. Do not assume every source partitions evenly or efficiently.

A spliterator also reports **characteristics** that help consumers understand the source, for example:

- `ORDERED` — a defined encounter order exists;
- `DISTINCT` — elements are distinct under the source contract;
- `SORTED` — the source has sorted order;
- `SIZED` — the exact size is known;
- `SUBSIZED` — split parts also satisfy the relevant sizing contract.

```java
boolean ordered = spliterator.hasCharacteristics(Spliterator.ORDERED);
long estimate = spliterator.estimateSize();
```

The important boundary in this chapter is its relationship to Stream:

```text
Collection
    ↓ spliterator()
Spliterator
    ↓ traversal + splitting + source characteristics
Stream pipeline
```

`Collection.stream()` and `parallelStream()` use a spliterator as a traversal source. A `Spliterator` provides a foundation for partitioning data, but it does **not** by itself make traversal parallel or make a collection thread-safe. Stream execution, parallelism, and concurrency belong to their own topics.

For the Collection module, keep this distinction: `Iterator` is optimized for sequential element-by-element traversal; `Spliterator` enriches traversal with source information and partitioning support for higher-level consumers such as Stream.
