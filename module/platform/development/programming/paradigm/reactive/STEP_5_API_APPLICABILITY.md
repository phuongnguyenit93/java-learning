## Approved Knowledge, real experiments and HTTP suitability

The locked Curriculum and seven bilingual Roadmap milestones make this module the owner of the **reactive paradigm**: event values arriving over time, propagation and composition, subscriptions, source/consumer rate differences, demand/backpressure, Reactive Streams signal contract, termination and cancellation. Six current Knowledge chapters have 38 anchored H2 per language. The implementation of HTTP reactive handlers, Reactor operators, Java Flow APIs and schedulers belongs to specialist framework/language modules.

| Current Knowledge identity | Actual observable proof worth teaching | Why HTTP would not improve that proof |
| --- | --- | --- |
| `3.Backpressure/Backpressure.md`: `reactive-rate-mismatch`, `reactive-queue-overflow` | Producer 100 items/s, consumer 40/s: uncontrolled queue grows about 60/s; bounded buffer of 120 fills after roughly 2s under idealized conditions | A deterministic rate/queue harness can sample queue occupancy and consumption directly. HTTP client/server buffering, connection scheduling and flush intervals add confounders and do not themselves demonstrate Publisher/Subscriber demand |
| `3.Backpressure/Backpressure.md`: `reactive-demand-flow-control`; `4.ReactiveStreams/ReactiveStreams.md`: `reactive-request-n` | A **real** Publisher/Subscriber exchange: `onSubscribe`, `request(2)`, two `onNext`; `request(3)` adds available demand; check no `onNext` exceeds accumulated requests | A direct compliant Reactive Streams test harness can record request and signal order exactly. An HTTP query parameter `?request=2` is **not** equivalent to invoking `Subscription.request(2)`; returning a hand-built sequence or string would only repackage the Knowledge trace in JSON |
| `4.ReactiveStreams/ReactiveStreams.md`: `reactive-protocol-failures`; `5.ErrorCancellation/ErrorCancellation.md`: `reactive-terminal-success`, `reactive-terminal-failure` | `request(0)` causes a protocol error; `onComplete` and `onError` can terminate without demand; no signal may follow a terminal event | These are obligations of the Reactive Streams contract, most precisely checked with a compliant Java publisher/subscriber and a test probe. HTTP status and SSE end-of-response are *different* contracts; REST results could misleadingly label a web error as a Publisher `onError` |
| `5.ErrorCancellation/ErrorCancellation.md`: `reactive-cancellation`, `reactive-inflight-signals` | Consumer `cancel()` requests eventual cessation, not immediate elimination of in-flight signals, and does not itself require `onComplete` | Browser closing an SSE stream/HTTP connection does not prove the Reactive Streams Subscription cancellation timing or upstream propagation. A controlled subscription + asynchronous barrier gives more accurate signal-level evidence |
| `2.DataFlow/DataFlow.md`: `reactive-flow-trace`; `6.Tradeoffs/Tradeoffs.md`: `reactive-end-to-end-example` | Sensor `27, -300, 33`: validation filters `-300`, classification emits normal/alarm, signal/lifecycle transitions visible | A Java/console/test trace directly exposes the same causal steps. Exposing a snapshot over HTTP would only serialize the result, while streaming the values through WebFlux adds another independent runtime and network protocol requiring separate conceptual teaching |

**Why not a bounded HTTP controller?** The meaningful experimental controls are actual `Subscription.request(n)`, `onNext`, cancellation, terminal signals, queue capacity and source/consumer rates. A standalone Java Reactive Streams experiment or contract test offers precise, controllable evidence without conflating subscription demand with TCP, browser/SSE demand, HTTP cancellation or WebFlux scheduler behavior. A web adapter can be built around such a harness, but its observable body/trace would **not be stronger evidence** and would introduce framework and serialization prerequisites the learner has not needed to master this **paradigm**. A fake `request(n)` replay in a REST response is expressly insufficient. Real Reactor/WebFlux/Java Flow mechanics should be demonstrated and tested in their canonical technical owners, not duplicated as an HTTP wrapper in this conceptual module.

This does **not** say dynamic verification lacks value: focused Java runtime experiments are a good optional study/evidence path, and the specification's normative requirements must be verified against real Publisher/Subscriber implementations. It says a **module-owned executable HTTP/Swagger learning API is not necessary** to fulfill the currently approved outcomes.
