## <a id="aop-compile-time">Compile-Time Aspect Weaving</a>

<details>
<summary>Click for details</summary>

**Compile-time weaving** puts additional behavior into generated bytecode before the application starts. AspectJ's compiler/weaver can act on supported join points without requiring calls to pass through a proxy, including certain field operations.

The build pipeline must deliberately include the weaving step. The absence of a logger call in a target's source does not mean the executed bytecode lacks that behavior. This distinction describes **how behavior is installed**, not why every application should use aspects.

</details>

## <a id="aop-load-time">Load-Time Aspect Weaving</a>

<details>
<summary>Click for details</summary>

With **load-time weaving**, class bytecode is transformed as the class loads, later than compilation but before normal execution of that class. This transforms class behavior rather than routing calls through a wrapper around an already created object.

When behavior is missing, inspect whether the relevant class was transformed and whether it was loaded before weaving could take place. The use of agents or particular class loaders is an AspectJ implementation matter, not part of the general paradigm.

</details>

## <a id="aop-runtime">Runtime Interception through an Intermediate Boundary</a>

<details>
<summary>Click for details</summary>

Some implementations apply cross-cutting behavior at runtime through an intermediate layer or interception mechanism.

Mental model:

```text
caller
  ↓
interception boundary
  ↓
cross-cutting behavior
  ↓
target
```

A **proxy** sits between a caller and a target, applies matching advice and then delegates: `external → timingProxy → transferService.transfer()`. A call that bypasses that proxy does not encounter the advice installed on the proxy.

This can avoid bytecode weaving and can be integrated at runtime, but only intercepted calls within the supported boundary participate. Compare real call paths instead of assuming two similarly annotated designs provide the same coverage.

</details>

## <a id="aop-model-boundary">Observation Scope and Limitations of Composition Models</a>

<details>
<summary>Click for details</summary>

The implementation determines **which kinds of join point an aspect can observe**. Runtime interception may cover only method executions reached through a proxy, whereas bytecode weaving can support a wider range of join points, including certain field reads and writes in AspectJ. Even the most precise pointcut cannot turn an ordinary field assignment into a Spring AOP method-execution join point.

For a design review, record the weaving approach, target eligibility, supported join point kinds, intercepted and bypassed calls, and error observations. A policy's actual scope can be judged only against that evidence.

</details>

## <a id="aop-aspectj-spring-boundary">AspectJ Weaving versus Spring AOP Proxies: Different Join Point Models</a>

<details>
<summary>Click for details</summary>

**AspectJ weaving** can modify bytecode and supports a broader join point model, including method calls/executions, constructors, and some field access according to AspectJ semantics. **Spring AOP** generally applies proxy-based **method-execution advice to Spring beans**, not arbitrary field reads or writes. Using AspectJ-style `@Aspect` declarations with Spring **does not mean AspectJ is weaving the bytecode**.

For example, an internal assignment `balance = balance - 100` is not a Spring AOP field-set join point. A suitable weaving technology or a different behavioral boundary would be required. This is a **capability limit**, not a pointcut typo. Compare [Spring AOP Capabilities](https://docs.spring.io/spring-framework/reference/core/aop/introduction-spring-defn.html) and the [AspectJ Programming Guide](https://eclipse.dev/aspectj/doc/latest/progguide/progguide.html).

</details>

## <a id="aop-interception-limits">Interception Boundaries and Internal Calls in Proxy Models</a>

<details>
<summary>Click for details</summary>

Suppose an external caller invokes `proxy.execute()`, then the target's `execute()` calls `this.verify()`. The second call goes directly from the target to itself, **not back through the proxy**. Consequently Spring AOP advice on `verify()` does not apply to that self-invocation. An eligible call to `proxy.verify()` from outside may be intercepted.

The proxy kind and eligible methods also affect the interception boundary; interface-based and class-based proxies differ. AspectJ bytecode weaving does not suffer from **bypassing the proxy** in this particular way. The implementation details belong with Spring's proxy mechanisms: [official documentation](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html).

</details>
