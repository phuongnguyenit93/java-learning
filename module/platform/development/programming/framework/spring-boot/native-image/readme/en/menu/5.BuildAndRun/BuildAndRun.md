## <a id="native-build-workflow">What Is the Supported Boot Native Build Workflow?</a>

<details>
<summary>Click for details</summary>

Spring Boot supports two practical native production paths: GraalVM Native Build Tools through Maven/Gradle, and Cloud Native Buildpacks configured to build a native application image. Both paths perform Spring AOT before native-image compilation.

```text
application + build-time environment
→ Spring AOT
→ generated code/hints
→ GraalVM Native Image
→ native executable
→ optionally package executable in OCI image
```

The native build should be reproducible from build configuration. Avoid relying on manual local changes to generated hint files or one developer's machine state as the only way the application builds.

## <a id="graalvm-native-build-tools">How Do Maven and Gradle Integrate GraalVM Native Build Tools?</a>

<details>
<summary>Click for details</summary>

For Maven projects that inherit from `spring-boot-starter-parent`, Boot provides a `native` profile that works with GraalVM Native Build Tools. That profile arranges `process-aot` and native plugin defaults so the prepared application becomes input to native compilation. A typical parent-based build uses the profile around the package/native lifecycle.

For Gradle, applying the GraalVM Native Build Tools plugin alongside Spring Boot adds native tasks and connects them to Boot/Spring AOT processing. The important mental model is integration, not task-name memorization: the build tool prepares AOT output first, then the native plugin compiles it.

With `spring-boot-starter-parent`, the supported direct-executable entry point makes that ordering concrete; Gradle exposes the corresponding native task when the GraalVM Native Build Tools plugin is applied:

```text
mvn -Pnative native:compile
gradle nativeCompile
```

With Maven, the `native` profile wires Boot's AOT processing into the build **when that profile is inherited from `spring-boot-starter-parent`**. A Maven project that does not use the parent must configure the equivalent Boot `process-aot` and GraalVM Native Build Tools executions explicitly rather than assuming `-Pnative` exists. With Gradle, the Spring Boot plugin configures the AOT task dependencies when `org.graalvm.buildtools.native` is applied.

The exact Maven/Gradle mechanics remain build-tool concerns; this module owns what those steps mean for a Boot native application.

</details>

## <a id="aot-to-native-compile">How Does AOT Output Flow into Native Compilation?</a>

<details>
<summary>Click for details</summary>

Generated AOT Java source is compiled, generated bytecode is added to the application inputs, and native-image configuration/hints are made available under the expected `META-INF/native-image` locations. GraalVM analyzes this enriched application classpath.

That ordering matters. Running native-image against an ordinary Boot artifact that lacks required AOT-generated assets does not reproduce the supported Spring native pipeline. Spring Boot 3.3 can convert an executable JAR when that JAR already contains the necessary AOT assets, but the AOT preparation cannot simply be skipped.

## <a id="native-executable-output">What Does the Platform-specific Native Executable Contain?</a>

<details>
<summary>Click for details</summary>

The result contains machine code and the runtime support selected by native-image analysis, plus the application resources/metadata included by reachability configuration. It is built for a target platform rather than remaining portable JVM bytecode.

This has two practical consequences. First, build and release pipelines need a strategy for every target OS/architecture. Second, native-image does not generally solve this by cross-compiling one binary for all targets; builds commonly run on the target platform or matching build environment.

The executable still behaves as the Spring Boot application from the learner's perspective: it starts configuration, beans, web/server integrations, and business code prepared by AOT—just without ordinary JVM startup as the deployment boundary.

</details>

## <a id="native-buildpack-image">How Does Spring Boot's Buildpacks Integration Produce an OCI Image with a Native Executable?</a>

<details>
<summary>Click for details</summary>

Spring Boot's `bootBuildImage` / Maven `build-image` integration can select the native build path when configured accordingly. Paketo buildpacks detect the application, run AOT/native compilation in the builder environment, and place the resulting native executable into the application image instead of shipping a normal JVM-based launch form.

For a Maven build inheriting `spring-boot-starter-parent`, and for a Gradle build with GraalVM Native Build Tools applied, the corresponding entry points are:

```text
mvn -Pnative spring-boot:build-image
gradle bootBuildImage
```

The Maven `-Pnative` form relies on the parent-provided profile; a non-parent Maven build must configure equivalent native/AOT plugin execution explicitly. The Gradle form produces a native image when the GraalVM Native Build Tools plugin is applied; otherwise `bootBuildImage` follows the normal JVM image path.

This is useful when the delivery platform already expects OCI images and you want the builder to provide the GraalVM/native toolchain. The generic concepts of builder images, run images, cache, publishing, and registry credentials still belong to `build-tooling-packaging`.

</details>

## <a id="native-run-comparison">How Does Running the Native Executable Differ from `java -jar`?</a>

<details>
<summary>Click for details</summary>

`java -jar` starts a JVM and gives Boot a bytecode/classpath runtime. A native binary starts directly as an OS process. You do not pass it to `java`; you execute the produced binary (or start the OCI image that contains it).

Operational configuration such as environment variables and external application properties still matters, but remember the AOT boundary: runtime inputs cannot invalidate structural decisions already fixed during processing.

When comparing startup/memory, compare equivalent configuration and workload. A native process and JVM process can have different warm-up, diagnostic, and memory-management behavior, so one metric from an idle local process is not a complete production decision.

</details>

## <a id="native-build-tooling-boundary">Where Does Native-image Ownership Hand Off to Build Tooling and Packaging?</a>

<details>
<summary>Click for details</summary>

Native-image owns the AOT/closed-world semantics that make the executable viable. Build-tooling-packaging owns the general Boot plugin model, dependency alignment, Buildpacks concepts, OCI naming/publishing, archive/image delivery choices, and generic build-tool commands.

This module may show the command that activates a native path because the command is necessary evidence. It should not repeat the complete Gradle/Maven/Buildpacks curriculum. Conversely, build-tooling-packaging may mention native as a handoff but should not re-teach Runtime Hints or closed-world behavior.

</details>
