## <a id="spring-aot-purpose">What Does Spring AOT Prepare for a Boot Application?</a>

<details>
<summary>Click for details</summary>

Spring AOT inspects the application at build time and turns decisions that are normally discovered during context startup into generated assets. Its purpose is to make a Spring `ApplicationContext` sufficiently explicit for restricted/native execution.

The process prepares bean registration/initialization code, generated proxy bytecode where needed, and Runtime Hints that describe dynamic access. The resulting application still uses Spring at runtime, but it relies less on open-ended discovery after the executable has been built.

## <a id="aot-entry-model">Which Application Model Does AOT Processing Analyze?</a>

<details>
<summary>Click for details</summary>

AOT starts from the Boot application's normal configuration model and prepares its `BeanFactory` using the build-time classpath and environment. That means the build is not analyzing arbitrary source code in isolation; it is asking Spring to establish the application model that will later be encoded as generated initialization assets.

The practical consequence is that build-time inputs matter. Profiles, properties, classpath contents, and auto-configuration conditions that affect bean presence can influence the generated result. Treat the AOT environment as part of the native build contract.

</details>

## <a id="aot-generated-assets">Which Source, Bytecode, and Hint Assets Are Generated?</a>

<details>
<summary>Click for details</summary>

Spring AOT can generate three useful categories of evidence:

```text
generated Java source
→ context/bean initialization that would otherwise be discovered dynamically

generated bytecode
→ for example proxy classes needed by the prepared application

Runtime Hints / native-image metadata
→ reflection, resources, serialization, JDK proxies and similar dynamic needs
```

Build tools place these outputs in generated-AOT directories and feed them into later compilation/native-image steps. They are generated build artifacts; do not edit them manually as the source of truth.

</details>

## <a id="aot-condition-timing">When Are Conditions and Bean-definition Decisions Evaluated?</a>

<details>
<summary>Click for details</summary>

During AOT processing, Spring prepares the bean factory and evaluates decisions that influence which bean definitions exist. This changes the timing compared with a normal dynamic Boot startup: relevant classpath and environment choices are effectively captured in the build-time model.

If a property or profile changes whether a bean exists, you cannot assume a native executable built under one model can freely recalculate a completely different bean graph at runtime. Runtime configuration is still available for values that do not alter the prepared application structure, but structural choices must respect the AOT model.

</details>

## <a id="aot-runtime-handoff">How Do Generated AOT Assets Become Inputs to Native Compilation?</a>

<details>
<summary>Click for details</summary>

The generated source and bytecode are compiled along with application code, while generated native-image metadata is placed where GraalVM Native Image can consume it. Native compilation then analyzes this prepared application rather than the original dynamic runtime model alone.

```text
Spring AOT
→ generated application initialization
→ generated proxy/code assets
→ native configuration/hints
        ↓
GraalVM native-image
→ reachability analysis + native compilation
```

This is a handoff between Spring's understanding of the application and GraalVM's compiler. Spring does not replace the native compiler; GraalVM does not infer every Spring semantic by itself.

</details>

## <a id="aot-diagnostic-evidence">How Can Generated AOT Output Help Diagnose Native-only Behavior?</a>

<details>
<summary>Click for details</summary>

When JVM behavior and native behavior diverge, inspect the AOT boundary before guessing. Generated sources can show whether a bean/configuration path was included. Generated hint metadata can show whether a resource/type/proxy requirement was recorded. Build logs can show which environment and plugins participated.

A useful diagnostic sequence is:

```text
Does normal JVM startup work?
→ Does AOT processing succeed?
→ Is the expected bean/generated code present?
→ Is required hint/resource metadata present?
→ Does native compilation succeed?
→ Does the native process fail only on a dynamic path?
```

Each answer narrows the responsible layer.

</details>

## <a id="aot-auto-configuration-boundary">Where Does AOT Processing Hand Off to Auto-configuration Ownership?</a>

<details>
<summary>Click for details</summary>

AOT **evaluates and materializes** decisions made by Spring configuration and Boot auto-configuration; it does not redefine how auto-configuration conditions, ordering, back-off, or custom auto-configuration should be designed.

If the question is “why did this `@AutoConfiguration` match or back off?”, the auto-configuration module owns the semantic explanation. Native-image owns the additional consequence: that the resulting bean/configuration model is prepared at build time and must remain compatible with closed-world execution.

</details>
