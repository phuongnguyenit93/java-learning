## How Should Faster Startup and Lower Memory Be Evaluated?

<!-- VIDEO_SECTION -->

### Scene 1 — Benchmark the operational problem, not the technology label

**Time:** `00:00–00:42`

**Visual:**

Show a dashboard with cold startup, resident memory, throughput, p99 latency, CPU, and warm-up. Highlight startup/memory first, then reveal the other metrics with `measure under equivalent load`.

**Script:**

Native images are strongest when the problem is cold startup or memory pressure: scale-to-zero services, bursty workers, command applications, or environments where service density matters. But “starts faster” is not the same as “serves every workload faster.” Measure throughput, tail latency, CPU, memory under load, and steady-state behavior with equivalent configuration. A long-running JVM can recover part of its startup cost through JIT optimization, so the right comparison is your application under its real workload, not a headline benchmark from somewhere else.

**Purpose:**

Keep the runtime-benefit discussion evidence-based and preserve the JVM/JIT caveat from Knowledge.

## What Build-time and Resource Costs Increase?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `00:42–00:53`

**Visual:**

Slide the runtime dashboard left and open a delivery-pipeline timeline on the right with increasingly long build stages.

**Script:**

If startup becomes cheaper because work moved earlier, the build has to pay that bill. The pipeline cost is part of the architecture decision.

**Purpose:**

Link runtime gains directly to the extra native build and CI cost that enables them.

### Scene 1 — Budget native compilation as delivery work

**Time:** `00:53–01:31`

**Visual:**

Compare `JVM compile/test/package` with `JVM feedback → AOT/hint checks → native analysis/compile → native test`. Add CPU and memory meters beside the native stages and separate target-platform build jobs.

**Script:**

Producing a native executable is normally much slower and more CPU- and memory-intensive than producing a JVM JAR. CI needs a suitable GraalVM toolchain or a builder that provides one, and platform-specific binaries can require separate target jobs. That changes engineering practice: keep ordinary feedback on the JVM, use focused AOT checks for native-sensitive changes, and pay the full native build cost where it gives meaningful confidence—especially before release.

**Purpose:**

Show how native build cost changes feedback-loop design instead of treating compilation time as a one-off inconvenience.

## How Does Third-party Dependency Native Readiness Affect the Application?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `01:31–01:42`

**Visual:**

Insert a third-party library box into an otherwise green application pipeline and turn only that box red.

**Script:**

Your own application can be AOT-friendly and still fail because one dependency owns dynamic behavior the native build cannot describe.

**Purpose:**

Move from pipeline cost to ecosystem compatibility as a separate adoption risk.

### Scene 1 — Native readiness is version- and dependency-specific

**Time:** `01:42–02:24`

**Visual:**

Show a dependency card with checks for reflection, runtime scanning, bytecode generation, native libraries, and unusual resource discovery. Beside it compare `v1: no metadata` with `v2: library/reachability metadata available`.

**Script:**

Libraries that use deep reflection, runtime classpath scanning, generated bytecode, native libraries, or unusual resource lookup may need dedicated native support. Check the exact library version: does it document GraalVM support, ship native-image metadata, or have coverage in the reachability-metadata ecosystem? Readiness can change between versions. If your application must carry a large private hint workaround for a dependency, record that maintenance cost and prefer an upstream fix when one is available.

**Purpose:**

Teach dependency-native readiness as a concrete versioned compatibility input rather than an application-only concern.

## Why Does Reachability Metadata Quality Matter?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `02:24–02:35`

**Visual:**

Zoom from the dependency box into two metadata files: one missing a required entry, one registering an entire package broadly.

**Script:**

Having metadata is not enough; its quality changes both correctness and what the native build retains.

**Purpose:**

Connect dependency support to the precision and maintainability of reachability metadata.

### Scene 1 — Prefer narrow, owned, test-backed metadata

**Time:** `02:35–03:16`

**Visual:**

Compare three panels: `missing` → runtime failure, `too broad` → excess retention and unclear contract, `specific` → exact type/resource plus focused test. Add labels `owner`, `version`, `test` to the specific case.

**Script:**

Missing metadata can remove behavior the runtime actually needs. Metadata that is too broad can retain unnecessary types or resources and hide the real dynamic contract. Good metadata sits close to the code that owns the behavior, is specific enough to explain the need, tracks version changes, and is covered by a test that exercises the dynamic path. Treat metadata like code: review it, version it when application-owned, and delete stale workarounds when upstream support makes them unnecessary.

**Purpose:**

Define metadata quality in terms of correctness, ownership, precision, and maintainability.

## How Do You Separate Hint, Metadata, Build-integration, and Dependency Failures?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `03:16–03:27`

**Visual:**

Transform the metadata comparison into a vertical troubleshooting decision tree ordered by the last successful boundary.

**Script:**

When a build or runtime path fails, changing several hints and plugin settings together destroys evidence. Classify the failure by the last boundary that still worked.

**Purpose:**

Introduce a diagnostic method that prevents broad, simultaneous native workarounds.

### Scene 1 — Follow the last successful boundary

**Time:** `03:27–04:18`

**Visual:**

Walk a decision tree: `JVM fails` → application/config; `JVM works, AOT fails` → prepared model/unsupported registration; `AOT succeeds, native compile fails` → toolchain/build/unsupported construct/metadata; `native starts, dynamic path fails` → hints/resources/proxy/reflection/dependency metadata; `one third-party feature fails` → dependency support. Keep logs/generated assets attached to each node.

**Script:**

If the JVM application fails too, solve the ordinary application or configuration problem first. If the JVM works but AOT processing fails, inspect the prepared Spring model and unsupported registration patterns. If AOT succeeds but native compilation fails, look at native build configuration, toolchain, unsupported constructs, and reachability inputs. If the native executable starts and only one dynamic path fails, hints, resources, proxies, reflection, or dependency metadata become stronger suspects. If only one library feature fails, inspect that library's native support before adding broad application workarounds. Preserve logs and generated assets at each step.

**Purpose:**

Replace the previously corrupted script with a complete evidence-based failure classification.

## When Is a Regular JVM Deployment the Better Choice?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `04:18–04:29`

**Visual:**

Put the diagnostic tree beside a decision scoreboard with columns `native value` and `native cost`.

**Script:**

A correct native build can still be the wrong deployment choice. The final question is whether its measured value pays for the extra constraints and pipeline cost.

**Purpose:**

Separate technical feasibility from architectural desirability.

### Scene 1 — Keep the JVM as a first-class option

**Time:** `04:29–05:10`

**Visual:**

Score example factors: infrequent scaling, long-running service, JIT-sensitive workload, weak dependency support, JVM-only agents/diagnostics, long native build latency. Move the final marker toward `JVM` as those costs accumulate.

**Script:**

Prefer the JVM when native-specific benefits are small compared with build and compatibility cost. A long-running service that rarely scales may not value cold-start gains. Some workloads benefit strongly from JIT optimization. A dependency stack may have weak native support, or the team may rely on diagnostics and agents available only in the JVM world. Native build latency may also dominate delivery time. Choosing the JVM in those conditions is not failed modernization; it is choosing Spring Boot's most flexible deployment model based on measured constraints.

**Purpose:**

End the trade-off video with a defensible decision rule instead of treating native adoption as the default goal.
