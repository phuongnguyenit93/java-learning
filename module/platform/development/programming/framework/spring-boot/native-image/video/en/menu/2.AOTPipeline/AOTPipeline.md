## What Does Spring AOT Prepare for a Boot Application?

<!-- VIDEO_SECTION -->

### Scene 1 — Turn startup discovery into generated initialization

**Time:** `00:00–00:41`

**Visual:**

Draw a timeline from ordinary context startup to build time. Move bean registration, proxy generation, and dynamic-access metadata from the runtime side into a box labeled `Spring AOT`.

**Script:**

Spring AOT prepares the application model before deployment. It asks Spring to build the application context far enough to understand the bean definitions and infrastructure that would normally be discovered during startup, then generates assets that can recreate that model with less open-ended discovery later. The application still runs on Spring; AOT does not replace the container. It makes the container initialization explicit enough for restricted and native execution.

**Purpose:**

Define AOT as preparation of Spring's application model, not as source-to-native compilation itself.

## Which Application Model Does AOT Processing Analyze?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `00:41–00:52`

**Visual:**

Zoom into the input side of the AOT box and reveal `main application`, `classpath`, `environment`, `profiles/properties`, and `auto-configuration`.

**Script:**

If AOT prepares a real Spring context, its input is not just source code. The build-time classpath and environment participate in the model Spring sees.

**Purpose:**

Connect AOT purpose to the concrete inputs that can change the generated application structure.

### Scene 1 — AOT prepares a BeanFactory from the build environment

**Time:** `00:52–01:35`

**Visual:**

Show `Application main class` feeding a `BeanFactory preparation` box. Add classpath and environment arrows, then display an example conditional configuration card appearing or disappearing as an input changes.

**Script:**

AOT starts from the Boot application's normal configuration model and prepares its `BeanFactory` using the classpath and environment available to the build. Spring is not scanning arbitrary Java source in isolation; it is establishing the same kind of application model that startup would normally create, but at build time. That means dependency versions, classpath contents, profiles, and properties that influence conditions are part of the AOT input contract. If those structural inputs change, the generated model can change even when application source does not.

**Purpose:**

Show why native reproducibility depends on the build-time application environment as well as source code.

## Which Source, Bytecode, and Hint Assets Are Generated?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `01:35–01:46`

**Visual:**

Keep the BeanFactory box and fan its output into three lanes: `generated Java`, `generated bytecode`, and `native-image metadata`.

**Script:**

Once Spring knows the model, the useful question becomes: what concrete evidence does AOT leave behind for later build stages?

**Purpose:**

Move from the abstract prepared model to the inspectable artifacts that represent it.

### Scene 1 — Three categories of AOT evidence

**Time:** `01:46–02:31`

**Visual:**

Open a generated-output tree and highlight three destinations in sequence: sources for context/bean initialization, generated classes such as proxies, and `META-INF/native-image` resources containing reachability metadata.

**Script:**

The generated output has three useful categories. First, Java source captures context and bean initialization that would otherwise rely on more runtime discovery. Second, generated bytecode can provide classes such as proxies needed by the prepared application. Third, Runtime Hints are translated into native-image metadata for reflection, resources, proxies, serialization, JNI, and related dynamic needs. Build tools feed these generated assets into compilation; they are diagnostic build output, not files that should become the application's manually edited source of truth.

**Purpose:**

Give the learner concrete artifacts to inspect later when diagnosing AOT or native failures.

## When Are Conditions and Bean-definition Decisions Evaluated?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `02:31–02:42`

**Visual:**

Replace the generated-output tree with a conditional bean decision card and move its decision point from runtime startup to the AOT build stage.

**Script:**

Those generated initializers encode choices. The critical timing change is that conditions affecting the bean structure are evaluated while AOT prepares the application.

**Purpose:**

Connect generated assets to the build-time condition semantics that constrain the resulting bean graph.

### Scene 1 — Structural conditions are resolved during AOT

**Time:** `02:42–03:27`

**Visual:**

Show a condition reading build-time environment input and selecting `Bean A present` or `Bean A absent`; freeze that result into the generated model. Add a callout: `runtime value ≠ runtime bean-graph switch`.

**Script:**

By the time AOT finishes, Spring has fully prepared the `BeanFactory`, so conditions that decide which bean definitions exist have already been evaluated against the build-time environment. This is why profiles or properties used for structural conditions must be supplied to the AOT build when they are relevant. The generated application cannot later treat a different runtime profile or an `@ConditionalOnProperty` style flag as permission to reconstruct another bean graph. Runtime properties can still change ordinary values when they do not control bean creation; the structural model is the part fixed by AOT.

**Purpose:**

Explain the exact build-time/runtime boundary without falsely freezing all application configuration.

## How Do Generated AOT Assets Become Inputs to Native Compilation?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `03:27–03:37`

**Visual:**

Unfreeze the three generated lanes and connect them to the Java compilation/classpath and finally to a GraalVM Native Image box.

**Script:**

AOT has prepared the model; now those outputs must travel through the build rather than sit beside it as documentation.

**Purpose:**

Bridge Spring's preparation stage to the native compiler handoff.

### Scene 1 — Compile the generated code, carry the metadata

**Time:** `03:37–04:17`

**Visual:**

Animate generated Java through `javac`, generated classes onto the application classpath, and generated native-image resources into the same compile input. End with the complete prepared classpath entering GraalVM analysis.

**Script:**

Generated Java is compiled with the application, generated bytecode is added to the build outputs, and the native-image metadata is packaged where GraalVM can consume it. Native compilation therefore analyzes an enriched application: original code plus Spring's generated initialization and reachability evidence. Skipping that preparation and invoking native-image on an ordinary, unprepared Boot application is not the supported pipeline. The handoff works because the build plugins wire the AOT outputs into the later native task.

**Purpose:**

Make the AOT-to-native handoff concrete and prevent the misconception that native-image independently discovers Spring's model.

## How Can Generated AOT Output Help Diagnose Native-only Behavior?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `04:17–04:28`

**Visual:**

Turn the pipeline into a diagnostic ladder: `JVM` → `AOT processing` → `generated sources/hints` → `native compile` → `native runtime`.

**Script:**

The same assets that feed the compiler also tell us where a native-only failure entered the pipeline.

**Purpose:**

Reframe generated output from build plumbing into diagnostic evidence.

### Scene 1 — Diagnose from the earliest failing boundary

**Time:** `04:28–05:16`

**Visual:**

Walk through the ladder. At `generated sources`, open a bean initializer; at `generated hints`, show one resource/reflection entry; at `build logs`, highlight profiles and plugins used. Mark each boundary green until the failing step turns red.

**Script:**

Start with comparison evidence. Does the normal JVM application work? Does AOT processing succeed? In generated sources, is the expected bean or configuration path present? In generated hint metadata, is the required type, resource, or proxy recorded? Do the build logs show the environment and plugins you intended? Then ask whether native compilation succeeds and whether failure appears only when a dynamic path runs. Reading generated sources, hints, and logs in that order narrows the owner far faster than adding broad reflection configuration at random.

**Purpose:**

Restore the complete Knowledge diagnostic sequence and show exactly which generated evidence answers each question.

## Where Does AOT Processing Hand Off to Auto-configuration Ownership?

<!-- VIDEO_SECTION -->

### Transition

**Time:** `05:16–05:27`

**Visual:**

Place `AOT materializes decision` beside `auto-configuration defines condition/back-off/order`; draw a boundary line between them.

**Script:**

AOT can reveal which configuration was selected, but it does not become the owner of the rules that made an auto-configuration match or back off.

**Purpose:**

Prevent AOT diagnosis from duplicating the neighboring auto-configuration curriculum.

### Scene 1 — Materialize here, explain condition semantics there

**Time:** `05:27–06:05`

**Visual:**

Show one `@AutoConfiguration` condition being evaluated by Spring during AOT. Route a question bubble `Why did this condition match?` to `auto-configuration`, and a second bubble `What does fixing that decision at build time mean for native?` to `native-image`.

**Script:**

Spring AOT evaluates and materializes decisions made by Spring configuration and Boot auto-configuration; it does not redefine condition semantics, ordering, back-off, or how custom auto-configuration should be authored. If the question is why an `@AutoConfiguration` matched, the auto-configuration module owns that explanation. This module owns the native consequence: the selected bean and configuration structure is prepared during AOT and must remain compatible with closed-world execution.

**Purpose:**

Close the AOT pipeline with an explicit ownership boundary while keeping the native consequence in scope.
