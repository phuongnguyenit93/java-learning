## Spring AOT chuẩn bị điều gì cho ứng dụng Boot?

<!-- VIDEO_SECTION -->

### Scene 1 — Spring AOT chuẩn bị điều gì cho ứng dụng Boot?

**Time:** `00:00–00:30`

**Visual:**

Hiện ApplicationContext trước và sau AOT: các bước discovery lúc startup được thay bằng bean-registration code, proxy bytecode và runtime-hint metadata đã sinh sẵn.

**Script:**

Có thể xem Spring AOT như việc chuẩn bị ApplicationContext trước khi ứng dụng chạy ở production. Spring thực thi đủ configuration model tại build time để sinh code đăng ký và khởi tạo bean, proxy bytecode khi cần, cùng Runtime Hints cho truy cập động. Ứng dụng vẫn dùng Spring khi chạy, nhưng không còn phụ thuộc nhiều vào discovery mở rộng như startup JVM thông thường.

**Purpose:**

Định nghĩa output cụ thể và mục tiêu runtime của Spring AOT.

**Time:** `00:40–01:10`

**Visual:**

**Script:**

Vì vậy active profiles, properties, dependency presence và auto-configuration conditions có thể đổi những bean và infrastructure xuất hiện trong model được encode. Hãy coi AOT environment là một phần của native build contract, không phải trạng thái ngẫu nhiên trên máy developer.

### Scene 1 — Những mã nguồn, bytecode và metadata hint nào được tạo?

**Time:** `01:20–01:56`

**Visual:**

Ba panel evidence: generated Java cho context/bean initialization; generated bytecode cho proxy/helper; Runtime Hints/native metadata cho reflection, resources, serialization và proxies.

**Script:**

AOT output không phải một blob bí ẩn. Generated Java mô tả context và bean initialization vốn thường được khám phá động. Generated bytecode có thể cung cấp proxy hoặc helper class mà application model cần. Runtime Hints được chuyển thành native-image metadata để giữ reflection, resource, Java serialization, JDK proxy và các dynamic capability liên quan. Build tool sẽ compile và đóng gói các artifact này; đây là bằng chứng để inspect chứ không phải source of truth để sửa tay.

**Purpose:**

Phân biệt source, bytecode và hint output để chẩn đoán đúng artifact ở các bước sau.

### Scene 1 — Đầu ra AOT đã tạo có thể hỗ trợ chẩn đoán hành vi chỉ xuất hiện ở native như thế nào?

**Time:** `03:32–04:10`

**Visual:**

Failure ladder sáu bước: JVM startup → AOT processing → expected generated bean code → expected hint/resource metadata → native compile → failing native dynamic path; build logs gắn vào checkpoint AOT.

**Script:**

Khi native khác JVM, đừng đoán reflection config ngay. Đầu tiên xác nhận JVM startup bình thường. Sau đó kiểm tra AOT processing. Mở generated sources để xem bean hoặc configuration path mong đợi có được đưa vào không, kiểm tra generated hint và resource metadata cho dynamic capability, rồi dùng build logs để xác nhận environment và plugin thực sự tham gia. Chỉ khi các bước đó đúng mới chuyển sang native compilation và runtime path bị lỗi. Mỗi checkpoint loại bớt một nhóm nguyên nhân.

**Purpose:**

Khôi phục đầy đủ sequence chẩn đoán dựa trên generated code, metadata và build logs.

### Scene 1 — Quá trình AOT bàn giao sang trách nhiệm của auto-configuration ở đâu?

**Time:** `04:20–04:50`

**Visual:**

Một cây @AutoConfiguration condition thuộc auto-configuration; mũi tên sang generated bean initialization thuộc native-image integration.

**Script:**

AOT đánh giá và materialize quyết định từ Spring configuration và Boot auto-configuration. Nó không định nghĩa lại condition semantics, ordering, back-off hay cách thiết kế custom auto-configuration. Nếu câu hỏi là vì sao một @AutoConfiguration match, module auto-configuration sở hữu lời giải thích đó. Native-image chỉ sở hữu hậu quả bổ sung: model đã resolve được chuẩn bị ở build time và phải tương thích với closed-world execution.

**Purpose:**

Giữ semantics của auto-configuration tách khỏi hậu quả native của model đã resolve.
