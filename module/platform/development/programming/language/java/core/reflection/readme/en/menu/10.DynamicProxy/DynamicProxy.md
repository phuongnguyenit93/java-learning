# Dynamic Proxies

Earlier chapters used reflection to discover members and operate directly on their descriptors. Dynamic proxies raise that idea to a higher abstraction: instead of application code calling `Method.invoke()` everywhere, the JDK can generate an object at runtime that **implements one or more interfaces** and routes interface calls through an `InvocationHandler`.

This is a foundation for interception patterns such as logging, authorization, transaction boundaries, metrics, and remote clients. The caller still sees a normal typed interface; the dynamic behavior lives behind the proxy.

To connect with the recurring example, we add an interface because JDK dynamic proxies are interface-based:

```java
interface PaymentGateway {
    String pay(PaymentRequest request);
}

final class PaymentGatewayImpl implements PaymentGateway {
    private final PaymentService service;

    PaymentGatewayImpl(PaymentService service) {
        this.service = service;
    }

    @Override
    public String pay(PaymentRequest request) {
        return service.pay(request);
    }
}
```

## <a id="jdk-proxy-model">The JDK Dynamic Proxy Model</a>

Before the API, start with the problem a proxy solves. Without proxy generation, logging can be added with a handwritten wrapper:

```java
final class LoggingPaymentGateway implements PaymentGateway {
    private final PaymentGateway target;

    LoggingPaymentGateway(PaymentGateway target) {
        this.target = target;
    }

    @Override
    public String pay(PaymentRequest request) {
        System.out.println("before pay");
        try {
            return target.pay(request);
        } finally {
            System.out.println("after pay");
        }
    }
}
```

That is perfectly reasonable for a few methods. When logging, authorization, or metrics must be repeated across dozens of interfaces and methods, however, many nearly identical wrappers appear. JDK Dynamic Proxy replaces that boilerplate with one model:

```text
typed interface call
        ↓
runtime-generated implementation
        ↓
one InvocationHandler receives Method + args
        ↓
shared interception/delegation policy
```

That is the **WHY** of JDK Proxy: callers retain a typed interface contract while dynamic cross-cutting behavior is centralized in one handler.

`Proxy.newProxyInstance(...)` needs three main pieces:

1. a `ClassLoader` used to define/resolve the proxy class;
2. the interfaces the proxy must implement;
3. an `InvocationHandler` that receives calls.

The example uses `PaymentGateway.class.getClassLoader()` because the loader that creates the proxy must be able to see the interfaces the proxy implements. That visibility constraint is enough for this chapter; class identity, delegation, and multiple-loader behavior belong to the following ClassLoader module.

```java
PaymentGateway target = new PaymentGatewayImpl(
        new PaymentService("stripe")
);

InvocationHandler handler = new LoggingHandler(target);

PaymentGateway proxy = (PaymentGateway) Proxy.newProxyInstance(
        PaymentGateway.class.getClassLoader(),
        new Class<?>[] { PaymentGateway.class },
        handler
);

String result = proxy.pay(new PaymentRequest("ORD-42", 150_000L));
```

The `proxy` object is not an instance of `PaymentGatewayImpl`. It is an instance of a class generated by the JDK at runtime, and that generated class implements `PaymentGateway`. The caller can therefore keep using a type-safe interface:

```java
PaymentGateway gateway = proxy;
gateway.pay(request);
```

while the actual call flow is:

```text
caller
  ↓ PaymentGateway.pay(...)
generated proxy object
  ↓ encode call as Method + args
InvocationHandler.invoke(...)
  ↓ optional logic
target / delegate
```

A dynamic proxy therefore keeps the interface contract while inserting an interception boundary between caller and implementation.

## <a id="invocation-handler">InvocationHandler and Delegation Flow</a>

`InvocationHandler` has one central method:

```java
Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
```

`method` describes the operation the caller invoked, `args` contains its arguments, and `proxy` is the proxy instance itself. The handler can log, check permissions, measure time, route to a remote endpoint, or delegate to a real object.

A small handler for the payment example is:

```java
final class LoggingHandler implements InvocationHandler {
    private final PaymentGateway target;

    LoggingHandler(PaymentGateway target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        if (method.getDeclaringClass() == Object.class) {
            return handleObjectMethod(proxy, method, args);
        }

        System.out.println("before " + method.getName());

        try {
            Object result = method.invoke(target, args);
            System.out.println("after " + method.getName());
            return result;
        } catch (InvocationTargetException ex) {
            throw ex.getCause();
        }
    }

    private Object handleObjectMethod(Object proxy, Method method, Object[] args) {
        return switch (method.getName()) {
            case "toString" -> "PaymentGatewayProxy[" + target + "]";
            case "hashCode" -> System.identityHashCode(proxy);
            case "equals" -> proxy == args[0];
            default -> throw new UnsupportedOperationException(method.toString());
        };
    }
}
```

Unwrapping `InvocationTargetException` is significant when delegating with `Method.invoke()`. If `pay()` throws a business exception, a handler usually wants to propagate the underlying cause according to the interface contract instead of exposing the reflective wrapper as the primary failure.

Exceptions leaving the handler must also fit the method contract implemented by the proxy. Runtime exceptions and errors can pass through directly; a checked exception should be assignable to a type declared by the corresponding interface method. If the handler throws an undeclared checked exception, the proxy caller can receive an `UndeclaredThrowableException` wrapping it.

A handler does not have to delegate to a local object. An HTTP/RPC client proxy can inspect the `Method` and its annotations, encode a network request, and decode the response. The central idea is that a proxy converts a **typed interface call** into a **runtime interception event**.

## <a id="proxy-interfaces">Interfaces as the JDK Proxy Contract</a>

JDK Dynamic Proxy generates interface implementations; it does not create a subclass of the concrete target class. Therefore:

```java
proxy instanceof PaymentGateway     // true
proxy instanceof PaymentGatewayImpl // false
```

Callers should normally hold the proxy through interface types. If an external API requires the concrete implementation class, a JDK proxy cannot pretend to be that class.

One proxy can implement multiple interfaces:

```java
Object proxy = Proxy.newProxyInstance(
        loader,
        new Class<?>[] { PaymentGateway.class, Auditable.class },
        handler
);
```

Those interfaces must be visible through the class loader used for proxy creation and must satisfy the `Proxy` API constraints. On Java 21, proxy interfaces **must not be hidden interfaces or sealed interfaces**. Non-public interfaces also have stricter package/module rules, which is one reason frameworks commonly proxy public business interfaces.

If multiple proxy interfaces contain methods with the same signature, the handler still receives a `Method` according to JDK proxy selection rules. Handler design should not assume that the declaring interface always corresponds to the particular interface type through which the caller happened to reference the proxy.

Interface default methods are also dispatched through the handler. When a handler intentionally wants to invoke the interface's default implementation, `InvocationHandler.invokeDefault(...)` provides that operation.

## <a id="object-methods-proxy">equals, hashCode, and toString on a Proxy</a>

The three public, non-final `Object` methods—`equals`, `hashCode`, and `toString`—have an important proxy rule: invoking them on a proxy also dispatches to `InvocationHandler.invoke(...)`. The `Method` supplied to the handler has `Object.class` as its declaring class.

This makes the following handler logic dangerous:

```java
return method.invoke(proxy, args);
```

It invokes the method on the proxy again, which calls the handler again, causing recursive dispatch.

Blindly delegating those methods to the target can also produce surprising semantics. For example, `proxy.equals(proxy)` followed by `target.equals(proxy)` may return `false`, even when the proxy design intended identity semantics.

The handler should define these methods deliberately. The sample handler above uses identity semantics for `equals/hashCode` and a custom `toString`. Another framework can choose target-based semantics, but `equals` and `hashCode` must still remain contract-consistent.

Other final methods inherited from `Object`, such as `getClass()`, `wait()`, and `notify()`, do not become interception points in the same way as those three methods.

## <a id="proxy-limitations">Proxy Limitations and the Spring AOP Boundary</a>

The core limitations of JDK Dynamic Proxy follow from its interface-based model:

- without an interface, a JDK proxy cannot expose a concrete class API;
- only instance calls that pass through the proxy reach the `InvocationHandler`;
- static methods and constructors are not interface instance invocations and are not intercepted by a JDK proxy;
- calling the target object directly bypasses the proxy;
- private methods/state outside the interface do not automatically become interception points.
- sealed interfaces and hidden interfaces are not valid proxy interfaces for `Proxy.newProxyInstance(...)` on Java 21.

A concrete `final` class can still be **wrapped** behind a JDK proxy if its object implements an interface, because the JDK proxy does not subclass the target. `final` becomes a constraint for **class-based proxies** that generate subclasses: a final class cannot be extended, and a final method cannot be overridden/intercepted through subclass dispatch.

Spring AOP provides a higher-level proxy abstraction. It can use JDK dynamic proxies for interface-based proxying or class-based proxies (CGLIB in Spring) when proxying concrete classes is required/configured. Because class-based proxying relies on subclassing, final classes, final methods, and private methods cannot be overridden for advice through that mechanism.

Dynamic Proxy also does not solve every interception problem. Constructor interception, static-call interception, bytecode weaving, and self-invocation behavior belong to other mechanisms or design choices. For this Reflection module, the key model is that JDK Proxy provides a runtime-generated **interface implementation** with one handler boundary for calls.

The complete Reflection roadmap now forms one chain:

```text
Class metadata
→ Field / Method / Constructor descriptors
→ access boundary
→ generic signature metadata
→ dynamic invocation
→ safety/performance/maintainability trade-offs
→ interface interception with Dynamic Proxy
```

Reflection is most valuable when dynamic structure is a real requirement and the dynamic behavior is kept inside a clear boundary. When the compile-time type is already known, a direct Java contract usually remains simpler and easier to maintain.
