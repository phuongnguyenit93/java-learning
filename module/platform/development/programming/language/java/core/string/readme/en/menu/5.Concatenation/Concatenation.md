# String Concatenation

The `+` operator is convenient for String construction, but separate **language semantics** from the compiler/runtime implementation strategy.

## <a id="concat-semantics">Concatenation Semantics</a>

When String concatenation applies, Java produces a String value containing the combined content.

```java
String message = "Hello " + name;
```

Existing String objects are not mutated.

### String conversion happens inside the expression

Concatenation can accept primitive and reference values:

```java
String message = "count=" + 42;       // "count=42"
String flag = "active=" + true;       // "active=true"
Object value = null;
String text = "value=" + value;       // "value=null"
```

Java performs the required string conversion; application code does not need to call `toString()` for every operand.

That convenience can also hide a bug. If `null` is an invalid domain state, validate it rather than allowing concatenation to quietly turn it into the text `"null"`.

Evaluation order matters in mixed numeric/String expressions:

Operands are evaluated left to right. Numeric addition can therefore happen before the expression enters String-concatenation mode.

Avoid packing complex side effects into one concatenation expression; separate steps are easier to reason about and debug.

```java
System.out.println(1 + 2 + "x"); // "3x"
System.out.println("x" + 1 + 2); // "x12"
```

## <a id="compile-time-concat">Compile-time Concatenation</a>

When the whole concatenation is a Java **constant expression**, it is evaluated at compile time:

```java
String value = "ja" + "va";
```

The result is a constant String and is interned, so this example has the same canonical reference as the literal `"java"`. Do not generalize that identity guarantee to concatenation whose values are determined at runtime.

Constant variables can participate too:

```java
final String left = "ja";
String a = left + "va";
String b = "java";

System.out.println(a == b); // true
```

### final does not automatically mean compile-time constant

A `final` variable participates in a constant expression only when it is actually a Java **constant variable**:

```java
final String prefix = "ja";
String a = prefix + "va";
String b = "java";

System.out.println(a == b); // true
```

But a value determined at runtime is different:

```java
final String prefix = args.length > 0 ? args[0] : "ja";
String a = prefix + "va";
String b = "java";

System.out.println(a.equals(b));
```

`final` prevents reassignment; it does not convert every runtime expression into a compile-time constant. The important concept is **compile-time constant expression**, not merely the presence of `final`.

## <a id="runtime-concat">Runtime Concatenation</a>

For runtime values, the compiler/JVM may use different implementation strategies across Java versions, including builder-like lowering or `invokedynamic` machinery.

Application code should depend on the **language result**, not on a particular helper class appearing in generated bytecode.

Do not memorize a rule such as:

```text
every String +
→ compiler always creates StringBuilder
```

That is not the language contract. Modern Java may use other concatenation strategies, and implementations can evolve.

## <a id="loop-concat-cost">Repeated Concatenation Cost</a>

Repeated `result += part` in a large loop may create repeated intermediate work and copies:

```java
String[] parts = {"java", "-", "core"};
String result = "";
for (String part : parts) {
    result += part;
}
```

Mental model:

```text
""
 + part1 → result 1
 + part2 → larger result 2
 + part3 → larger result 3
 ...
```

As the result grows, the same prefix may be copied repeatedly. For sufficiently large workloads, this creates substantially more copying than reusing one mutable buffer.

When building text incrementally through many steps, `StringBuilder` usually expresses the intent more clearly and efficiently.

This does **not** mean every `+` is bad:

```java
String fullName = firstName + " " + lastName;
```

A small, readable expression is usually best left simple. Builder matters most for **incremental** construction, especially in loops or many branches.
