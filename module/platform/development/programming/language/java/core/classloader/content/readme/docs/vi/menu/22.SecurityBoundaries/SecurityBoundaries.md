# Bytecode verification bảo vệ điều gì và không bảo vệ điều gì trong Java?

## 1. Vấn đề cốt lõi: bytecode hợp lệ không đồng nghĩa chương trình đáng tin

Java Virtual Machine (JVM) có một **bytecode verifier** để kiểm tra những ràng buộc cấu trúc và an toàn kiểu đối với mã trong class file. Đây là một phần quan trọng giúp JVM thực thi bytecode được nạp động mà không phải tin rằng mọi compiler, công cụ biến đổi bytecode hay plugin đều tạo mã đúng.

Tuy nhiên, cần phân biệt hai câu hỏi hoàn toàn khác nhau:

- **“Bytecode này có tuân thủ các quy tắc kiểu và luồng thực thi của JVM để được chạy không?”** — Đây là trách nhiệm chính của **verification**, phối hợp với kiểm tra class-file format và các cơ chế liên kết/chạy khác.
- **“Nếu được chạy, chương trình này có an toàn, có đúng nghiệp vụ và chỉ làm những việc được phép hay không?”** — Verifier **không đưa ra lời bảo đảm** như vậy.

Ví dụ class Java sau hoàn toàn có thể được compiler tạo thành **bytecode hợp lệ**:

~~~java
public final class BusinessRule {
    public static int discount(int price) {
        return price * 100; // Công thức sai nghiệp vụ, vẫn hợp lệ về bytecode.
    }
}
~~~

Verifier không biết rằng discount không nên lớn hơn số tiền gốc; nó chỉ có thể kiểm tra các ràng buộc JVM như lời gọi/kiểu giá trị phù hợp. Một class khác có thể dùng `Files.readString` để đọc file mà process có quyền đọc. Mã đó vẫn có thể qua verification: **quyền filesystem không phải mục tiêu kiểm tra của bytecode verifier**.

Có thể xem ranh giới tổng quan như sau:

~~~text
      class bytes / generated bytecode / plugin
                         |
                         v
           Class file format checks
                         |
                         v
                    LOADING
                         |
                         v
                    LINKING
           +-------------+--------------+
           |             |              |
       Verification   Preparation    Resolution
           |             |              |
   kiểm tra an toàn  cấp phát và    giải quyết symbol
   kiểu bytecode     giá trị tĩnh   / thành viên / quyền
           +-------------+--------------+
                         |
                         v
                 INITIALIZATION
                  chạy <clinit>
                         |
                         v
                     EXECUTION
               logic, I/O, threads, JNI...
                         |
             verifier không phải sandbox
~~~

Sơ đồ mang tính khái niệm: **resolution có thể được thực hiện lười hoặc sớm** theo các điều kiện của JVMS, và các bước bên trong linking không nhất thiết xuất hiện như một chuỗi log dễ thấy. Không được suy rằng mỗi dependency đã được resolve hết trước khi class bắt đầu được sử dụng.

## 2. Verification nằm ở đâu trong vòng đời class?

JVM phân biệt:

1. **Loading** — tìm biểu diễn nhị phân (class file/bytes), tạo ra runtime Class/interface.
2. **Linking** — bao gồm **verification**, **preparation** và **resolution** theo các quy tắc JVM.
3. **Initialization** — chạy logic static initialization khi điều kiện khởi tạo được đáp ứng.
4. **Execution** — thực thi các phương thức và hoạt động của chương trình.

Trong custom `ClassLoader`:

~~~java
Class<?> defined = defineClass(
        binaryName, bytes, 0, bytes.length);
~~~

Đây là **đoạn minh họa bên trong subclass của ClassLoader**, không phải file Java độc lập. `defineClass` định nghĩa một lớp từ mảng bytes, nhưng việc nó trả về một `Class<?>` không phải bằng chứng rằng:

- Mọi tham chiếu dependency đã được resolve.
- Static initializers đã chạy.
- Mọi mã nghiệp vụ an toàn.
- Plugin không thể thao tác với API hệ thống.
- Mọi hành vi khi kích hoạt method đã được kiểm thử.

Verification là một **hàng rào tính hợp lệ của bytecode**, không phải một quyết định cho phép toàn bộ hành vi về sau.

### 2.1. Thời điểm VerifyError có thể xuất hiện

Theo JVMS §5.4.1, verification thuộc linking, và một số công việc có thể được thực hiện sớm hoặc trì hoãn theo cơ chế JVM. Vì thế `VerifyError` có thể lộ ra trong lúc nạp/liên kết class, trong lúc lấy method metadata hoặc lần đầu một thao tác buộc class phải được verified.

Đừng viết code test bắt buộc `defineClass` **phải** ném lỗi ngay tại dòng gọi. Ví dụ runnable ở phần 10 bao trọn cả bước define và method lookup/invoke trong một `try` để không phụ thuộc chi tiết thời điểm verifier chạy của implementation.

### 2.2. Verification khác initialization

Giả sử:

~~~java
final class Profile {
    static {
        System.out.println("Profile initialized");
    }
}
~~~

Đây là **mã minh họa**. JVM có thể verification/link `Profile` mà không chạy khối static. Việc khởi tạo class thường do active use như `new Profile()` hoặc truy cập static member không phải constant variable gây ra. **`<clinit>` có thể ném lỗi runtime ngay cả khi bytecode đã verify thành công**.

## 3. Verifier thực sự kiểm tra những gì?

Ở mức ý tưởng, verifier bảo đảm method bytecode phù hợp với **kiểu của từng operand, local variable, luồng điều khiển và những ràng buộc cấu trúc** được quy định trong JVMS `4.9–`4.10. Nó không phân tích ý định nghiệp vụ.

| Nhóm ràng buộc | Ví dụ bytecode không hợp lệ | Verifier hoặc kiểm tra JVM liên quan |
| --- | --- | --- |
| **Operand stack** | `pop` khi stack đang rỗng; `iadd` khi không có hai giá trị int | Từ chối dòng bytecode với trạng thái stack không phù hợp |
| **Local variables** | `iload_1` từ local chưa có giá trị int hợp lệ | Kiểm tra type state của các local slots |
| **Method invocation** | Dùng các operand sai kiểu hoặc sai số lượng cho opcode invoke | Kiểm tra kiểu và cấu trúc lời gọi |
| **Field access** | `putfield` với receiver/value không đúng kiểu yêu cầu | Kiểm tra kiểu operand cho thao tác trường |
| **Return** | `ireturn` khi method khai báo trả `void`, hoặc stack không có int | Kiểm tra opcode return phù hợp descriptor |
| **Control flow** | Nhảy tới vùng không phải instruction boundary; stack states không hợp lệ tại điểm merge | Static/structural constraints, type states |
| **Constructor discipline** | Dùng reference đang uninitialized như object đã được khởi tạo trong tình huống bị cấm | Theo dõi trạng thái uninitialized/`uninitializedThis` |
| **Exception handler** | Target, phạm vi hoặc type state tại handler không hợp lệ | Kiểm tra Code attribute và exception flow |
| **Class inheritance rules** | Mở rộng một final class | Ràng buộc type/class compatibility |
| **Stack maps** | Frames mâu thuẫn với luồng opcode | Kiểm tra `StackMapTable` và type transitions |

Bảng này gom các kiểm tra **class-file format, static constraints và type verification** để giải thích thực tế. **Không phải tất cả đều được Java đặc tả là do cùng một hàm verifier Java-level thực hiện hoặc cùng ném một loại Error.** Ví dụ classfile format hỏng có thể thành `ClassFormatError`; vi phạm instruction type-safety thường là `VerifyError`.

### 3.1. An toàn ngăn xếp operand

JVM là máy trừu tượng dựa trên operand stack. Bytecode như:

~~~text
iconst_1      // push int 1
iconst_2      // push int 2
iadd          // pop hai int, push kết quả int
ireturn       // trả về int cho method ()I
~~~

là một luồng opcode hợp lệ cho method static có descriptor `()I` khi các điều kiện khác thỏa.

Ngược lại:

~~~text
pop           // stack rỗng: không có operand để pop
ireturn       // không có int trên stack để return
~~~

vi phạm quy tắc stack. Nếu cấu trúc classfile còn lại hợp lệ, verifier từ chối trước khi method đó được chạy như một method Java hợp lệ. Đây là kiểu lỗi mà phần 10 cố ý tạo ra bằng cách sinh class bytes.

### 3.2. Local variable và kiểu slot

Các bytecode opcodes sử dụng typed operations như `iload`, `aload`, `istore`, `astore`. Verifier theo dõi trạng thái kiểu trừu tượng của local slots; không cho phép sử dụng một slot như `int` khi tại điểm đó nó chưa chắc chứa giá trị phù hợp.

`long` và `double` chiếm **hai đơn vị slot** trong một số cấu trúc JVM, nên việc theo dõi stack/locals cần tuân thủ quy tắc loại category 1/category 2. Không được suy diễn rằng bất kỳ bit pattern nào cũng được reinterpret thành arbitrary object reference.

### 3.3. Control flow và nhánh

Ở điểm nhiều nhánh hợp lại:

~~~text
       if condition
       /         \
  branch A     branch B
       \         /
        join point
~~~

Verifier kiểm tra type state khi flow đến `join point`. Các stack map frames chỉ ra trạng thái hợp lệ tại các vị trí xác định. Code không thể tùy ý nhảy vào giữa một instruction hoặc tạo ra một state không phù hợp rồi tiếp tục như đã hợp lệ.

Điều này giúp JVM không phải chạy một đường control flow sai cấu trúc chỉ vì class bytes do một nguồn bất kỳ cung cấp.

### 3.4. Object chưa khởi tạo

Sau opcode `new`, reference tới object mới mang trạng thái **uninitialized** trong verification type system. Việc gọi constructor qua `invokespecial <init>` và những hạn chế sử dụng reference trước khi được khởi tạo được kiểm soát. Bytecode không được đối xử với uninitialized object như một instance đã khởi tạo trong những điểm bị cấm.

**Nhưng** việc constructor sau đó tính nhầm giá, đọc nhầm cấu hình hoặc ghi sai dữ liệu vẫn là lỗi logic có thể nằm trong method hoàn toàn hợp lệ về bytecode.

## 4. StackMapTable trong Java 17

Với classfile version hiện đại, verifier thường sử dụng **verification by type checking**. Thông tin quan trọng nằm trong thuộc tính `StackMapTable` của `Code` attribute:

- Frame mô tả **verification types** của local variables và operand stack ở những bytecode offsets được chỉ định.
- Các frames hỗ trợ JVM xác minh consistency của các nhánh và entry points.
- Method descriptor cung cấp trạng thái khởi đầu có thể suy ra.
- Classfile version **50.0 trở lên** không khai báo `StackMapTable` có **implicit StackMapTable rỗng** theo JVMS; điều này **không tự làm mọi method không có nhánh trở thành không hợp lệ**.
- Với các classfile cũ đủ điều kiện, JVM specification còn mô tả cách verification bằng **type inference**; đừng áp dụng mọi ràng buộc format/version hiện đại một cách mù quáng cho classfile rất cũ.

Ví dụ lệnh quan sát class do `javac` tạo:

~~~bash
javac --release 17 -d out src/demo/Sample.java
javap -classpath out -v -p demo.Sample
~~~

Đây là **mẫu lệnh** giả định file `src/demo/Sample.java` tồn tại. Dùng `javap -v` để xem constant pool, `Code`, `StackMapTable` khi compiler tạo. Một method thẳng, không nhánh có thể **không có StackMapTable attribute được in**, không có nghĩa nó chưa verify.

**Lưu ý khi dùng ASM, Byte Buddy, Javassist hoặc javaagents:** nếu tự thay bytecode điều khiển luồng mà không tính lại max stack/frames phù hợp, class có thể bị `VerifyError` dù source-level intent hợp lý. Đó là lỗi của **biểu diễn bytecode cuối cùng**, không tự động là bằng chứng Java compiler “không an toàn”.

## 5. Verifier không bảo vệ những gì?

Có nhiều lớp rủi ro mà verifier **không được thiết kế để ngăn**:

### 5.1. Không quyết định quyền đọc/ghi file, mạng hay process

Mã sau hoàn toàn hợp lệ về Java typing:

~~~java
import java.nio.file.Files;
import java.nio.file.Path;

public class ReadableCode {
    public static String readAllowedFile(Path path) throws Exception {
        return Files.readString(path);
    }
}
~~~

Đây là **class có thể biên dịch** nhưng không có main nên không phải một demo độc lập. Verifier xác nhận lời gọi `Files.readString(Path)` được dùng với kiểu đúng; nó **không quyết định file nào được người dùng hoặc policy doanh nghiệp cho phép đọc**. Nếu tiến trình có quyền OS tương ứng, lời gọi có thể đọc dữ liệu.

Tương tự, dùng `Socket`, `ProcessBuilder`, reflection hoặc APIs khác không mặc nhiên bị verifier cấm chỉ vì các hành động ấy nhạy cảm.

### 5.2. Không phát hiện logic sai hay gian lận nghiệp vụ

Một method trả sai số tiền, áp dụng discount quá mức, bỏ qua authentication check hoặc cấu hình logging sai vẫn có thể thỏa mọi ràng buộc bytecode.

~~~java
public static boolean isAuthorized(String role) {
    return true; // logic sai, nhưng bytecode hoàn toàn hợp lệ
}
~~~

Verifier không có định nghĩa domain của “authorized”. Điều đó cần **thiết kế API, code review, kiểm thử, policy checks và giám sát nghiệp vụ**.

### 5.3. Không ngăn DoS, deadlock hoặc resource exhaustion

Mã sau cũng có thể verify thành công:

~~~java
public static void spin() {
    while (true) {
        // Vòng lặp vô hạn; JVM typing vẫn hợp lệ.
    }
}
~~~

Code này là **mã minh họa, không gọi trong chương trình đang làm việc**. Verifier không chứng minh termination, bounded CPU, bounded heap allocation, số threads hay lock-free progress. Một plugin có thể tạo quá nhiều objects hoặc gây deadlock dù bytecode chuẩn.

### 5.4. Không chứng minh chương trình không có bug concurrency

Race condition, mất atomicity, visibility bugs, deadlock và các lỗi do chia sẻ mutable state đều có thể xuất hiện từ **bytecode hợp lệ**. Java Memory Model, `volatile`, locks và concurrent APIs kiểm soát semantics; verifier không tự chứng minh chương trình đúng trong mọi thread interleaving.

### 5.5. Không tự bảo vệ trước JNI, native libraries hoặc implementation bug

JNI, Foreign Function & Memory APIs, native libraries, OS syscalls và những thành phần native khác có các ranh giới riêng. Verifier của classfile không phải static analyzer cho mã C/C++ được load và không chứng minh memory safety của native code. Nó cũng không loại trừ hoàn toàn lỗi trong JVM/JIT runtime implementation hay side channels.

### 5.6. Không quyết định một JAR/bytecode “đến từ ai”

`defineClass` có thể nhận byte array từ disk, mạng hoặc bộ sinh bytecode. Verification xử lý **tính hợp lệ của biểu diễn**, không tự xác thực tác giả, nguồn tải, hash, chữ ký hoặc supply-chain provenance. JAR signing, code source, deployment policy và artifact allowlist là **những cơ chế khác**; mỗi cơ chế có giới hạn riêng.

### 5.7. Không biến ClassLoader thành security sandbox

Một custom `ClassLoader` có thể giới hạn **nơi lấy class bytes**, cô lập namespace và chia sẻ APIs qua delegation. Nhưng sau khi code được nạp và thực thi, `ClassLoader` không phải cơ chế phổ quát chặn code ấy gọi filesystem, network hoặc các API hệ thống với quyền của process.

Dùng một loader riêng cho untrusted plugin có lợi về **type identity, dependency isolation và lifecycle**, nhưng **không mặc nhiên cấp ít quyền OS hơn**. Khi code không đáng tin cần hạn chế quyền thực tế, cân nhắc chạy nó ở **process/container/VM riêng** với filesystem, network, users, CPU/memory quotas và IPC contracts theo threat model.

### 5.8. Không thay thế kiểm soát đầu vào và cấu hình

Bytecode của một phương thức xử lý request có thể verify thành công nhưng vẫn dễ bị SQL injection, path traversal, command injection hoặc bỏ quên validation. Verifier không hiểu nguồn dữ liệu nào là user-controlled và quy tắc escape/authorization ở tầng ứng dụng.

## 6. Phân biệt kiểm tra classfile format, verification và runtime checks

Một số lỗi đều xuất hiện khi nạp/chạy class nên dễ bị gom chung:

| Lớp kiểm tra | Mục tiêu | Lỗi có thể thấy |
| --- | --- | --- |
| **Class-file format** | Magic, constant pool, cấu trúc attribute, kích thước/format | `ClassFormatError` |
| **Verification** | Bytecode type-safety, stack/locals, control flow, uninitialized state | `VerifyError` |
| **Resolution** | Liên kết symbolic references tới class/method/field thích hợp | `NoClassDefFoundError`, `NoSuchMethodError`, `NoSuchFieldError`, các `LinkageError` |
| **Access control** | Quyền truy cập class/member/module theo JVM rules | `IllegalAccessError`, lỗi access tương ứng |
| **Runtime type checks** | Ví dụ cast, array store, null dereference | `ClassCastException`, `ArrayStoreException`, `NullPointerException` |
| **Initialization** | Thực thi `<clinit>` | `ExceptionInInitializerError` hoặc initialization failure |
| **OS/process policy** | Quyền file, process, network, sandbox boundary | `AccessDeniedException`, permission/OS errors phù hợp |

Một class có thể **qua verifier** nhưng lần đầu gọi method mới phát sinh `NoSuchMethodError` vì library version mismatch. Một class có thể **qua verifier** nhưng mã khi chạy `checkcast` vẫn ném `ClassCastException` nếu object runtime không phù hợp.

**Vì sao verifier không loại bỏ mọi runtime check?** Type state được kiểm tra tĩnh theo những quy tắc JVM, nhưng một số thao tác có điều kiện phụ thuộc object/value runtime. Ví dụ `checkcast` có cấu trúc hợp lệ và operand là reference; thực tế object có thuộc target class hay không được kiểm tra lúc thực thi.

## 7. Verifier bảo vệ “type safety” theo nghĩa nào?

**Type safety ở đây là quy tắc của JVM bytecode**, không phải lời hứa “mọi code đều lành tính”. Khi các assumptions của JVM và implementation đúng, verifier cùng phần còn lại của JVM ngăn bytecode Java thông thường vi phạm các quy tắc như:

- Dùng một `int` trực tiếp như một object reference tùy ý.
- Pop hay consume operand từ stack không tồn tại.
- Truy cập local variable theo kiểu không hợp lệ tại điểm điều khiển.
- Trả về kiểu không tương thích với method descriptor.
- Tạo trạng thái uninitialized object không hợp lệ.
- Nhảy giữa các opcode làm phá cấu trúc method.
- Dùng các opcodes với số lượng/kiểu operand sai.

Ví dụ trong Java source không thể viết thao tác “reinterpret int bit pattern thành arbitrary live Object pointer” bằng cast thông thường. Nhưng sự an toàn đó đến từ **nhiều tầng**: ngôn ngữ, bytecode verification, runtime typing, access checks, garbage collector và JVM implementation; không thể quy mọi cơ chế vào verifier riêng lẻ.

**Verifier không thực hiện code review đạo đức hoặc security audit.** Mã được tạo bởi compiler Java chuẩn thường đã có type checking ở compile-time, nhưng đó không phải lý do để bỏ qua verifier đối với classfile đến từ bytecode transformers, class loaders, dynamic proxies, generated classes hoặc môi trường bị sửa class bytes.

## 8. Custom ClassLoader phải làm gì thêm?

Một loader đọc từ thư mục hoặc plugin JAR có thể dùng:

~~~java
protected Class<?> findClass(String name)
        throws ClassNotFoundException {
    byte[] bytes = readApprovedClassBytes(name);
    return defineClass(name, bytes, 0, bytes.length);
}
~~~

Đây là **mã minh họa không độc lập**, vì `readApprovedClassBytes` phải do người viết cài đặt và xử lý I/O tương ứng.

`defineClass` không phải security approval workflow. Loader/library nên có thêm chính sách theo yêu cầu thực tế:

1. **Allowlist binary class names** hoặc package scopes có giới hạn.
2. **Trusted source roots** cho bytes; chống path traversal, symlink escape và rủi ro TOCTOU khi storage có writer không đáng tin.
3. **Kích thước class bytes giới hạn** trước khi cấp phát; timeout/cancellation nếu nguồn mạng.
4. **Artifact provenance/integrity** nếu cần: pinned hashes, signatures, content-addressed IDs và trusted metadata.
5. **ClassLoader delegation rõ ràng**: JDK classes và shared API types thường do parent định nghĩa; plugin implementations/dependencies có scope riêng.
6. **Giới hạn resource cấp tiến trình** nếu plugin có thể thực thi mã nguy hiểm hoặc rất tốn CPU/heap.
7. **Quyền filesystem/network ở OS/container/process** không dựa vào class loader.
8. **Quản lý errors và logs**: phân biệt class bytes invalid, `VerifyError`, linking, initialization và application failures.
9. **Không tự tắt verification** để “sửa” class file hỏng. Các options tắt/giảm verification thay đổi theo phiên bản JDK và có thể làm mất một hàng rào safety.

### 8.1. Có nên tự bắt VerifyError và tiếp tục?

`VerifyError` là subclass của `LinkageError` (và `Error`). Một plugin loader/framework có thể bắt **đúng lỗi** tại ranh giới khởi động plugin để disable plugin và ghi chẩn đoán. Không nên catch mọi `Throwable` rồi coi như class không tồn tại: điều đó che mất lỗi format, OOM, VM errors, class hierarchy conflicts và những vấn đề nghiêm trọng khác.

Nếu **một class không qua verifier**, hướng xử lý là kiểm tra artifact/classfile generator/dependency compatibility, **không** làm “data patch” bừa bãi sau khi JVM đã phát hiện lỗi.

## 9. Vì sao cần phân biệt VerifyError và ClassFormatError?

**`ClassFormatError`** có thể xảy ra khi byte stream **không có cấu trúc classfile hợp lệ**: sai magic, constant pool entry hỏng, attribute length không hợp lệ hoặc cấu trúc file vi phạm grammar.

**`VerifyError`** thường liên quan bytecode đã qua bước format cần thiết nhưng **không tuân theo constraints an toàn kiểu/luồng opcode**. Ví dụ có `Code` attribute được cấu trúc hợp lệ nhưng method `()I` thực thi `pop` khi stack rỗng.

Ví dụ:

~~~text
File A:
    magic = 0xDEADBEEF (không phải classfile magic)
    -> class-file format failure

File B:
    magic = 0xCAFEBABE (đúng)
    constant pool và method structure hợp lệ
    Code method ()I = pop; ireturn
    -> verification failure
~~~

Đây là **sơ đồ**; chương trình phần 10 xây trường hợp B thực sự, với binary names rõ ràng và classfile version hỗ trợ Java 17.

Nếu gặp `NoClassDefFoundError`, `ClassNotFoundException` hoặc `UnsupportedClassVersionError`, đừng gọi tất cả là VerifyError. Đây có thể là vấn đề tìm class, JVM version hoặc liên kết khác.

## 10. Ví dụ Java 17+ runnable: bytecode đúng và sai khác một opcode

Để quan sát verifier rõ ràng, ta tạo **classfile rất nhỏ bằng API chuẩn `DataOutputStream` của JDK**; không cần ASM, Byte Buddy hay Java agent.

Hai class bytes được tạo với cấu trúc giống nhau:

- `demo.ValidCalc` có method `public static int value()`: bytecode `iconst_1; ireturn` — hợp lệ.
- `demo.InvalidCalc` có method `public static int value()`: bytecode `pop; ireturn` — cố gắng pop từ stack rỗng, nên vi phạm verification.

Classfile tạo ra dùng **version 61 = Java 17**, có constant pool tối thiểu. Không có branch instructions nên implicit empty `StackMapTable` đủ cho ví dụ. Method được dùng là static, vì vậy **không cần constructor trong classfile tối giản**.

### 10.1. File VerifierBoundaryDemo.java

~~~java
import java.io.ByteArrayOutputStream;
import java.io.DataOutputStream;
import java.io.IOException;

public class VerifierBoundaryDemo {
    static final class BytesLoader extends ClassLoader {
        BytesLoader() {
            super(VerifierBoundaryDemo.class.getClassLoader());
        }

        Class<?> define(String binaryName, byte[] bytes) {
            return defineClass(binaryName, bytes, 0, bytes.length);
        }
    }

    static byte[] classBytes(String internalName, boolean invalid)
            throws IOException {
        ByteArrayOutputStream buffer = new ByteArrayOutputStream();

        try (DataOutputStream out = new DataOutputStream(buffer)) {
            out.writeInt(0xCAFEBABE);
            out.writeShort(0);          // minor version
            out.writeShort(61);         // major version: Java 17

            out.writeShort(8);          // constant_pool_count = 8
            out.writeByte(1);           // #1 CONSTANT_Utf8
            out.writeUTF(internalName);
            out.writeByte(7);           // #2 CONSTANT_Class
            out.writeShort(1);
            out.writeByte(1);           // #3 CONSTANT_Utf8
            out.writeUTF("java/lang/Object");
            out.writeByte(7);           // #4 CONSTANT_Class
            out.writeShort(3);
            out.writeByte(1);           // #5 CONSTANT_Utf8
            out.writeUTF("value");
            out.writeByte(1);           // #6 CONSTANT_Utf8
            out.writeUTF("()I");
            out.writeByte(1);           // #7 CONSTANT_Utf8
            out.writeUTF("Code");

            out.writeShort(0x0021);     // ACC_PUBLIC | ACC_SUPER
            out.writeShort(2);          // this_class
            out.writeShort(4);          // super_class
            out.writeShort(0);          // interfaces_count
            out.writeShort(0);          // fields_count
            out.writeShort(1);          // methods_count

            out.writeShort(0x0009);     // public static method
            out.writeShort(5);          // name_index: value
            out.writeShort(6);          // descriptor_index: ()I
            out.writeShort(1);          // method attributes_count
            out.writeShort(7);          // Code attribute name_index
            out.writeInt(14);           // Code attribute length

            out.writeShort(1);          // max_stack
            out.writeShort(0);          // max_locals
            out.writeInt(2);            // code_length

            out.writeByte(invalid ? 0x57 : 0x04);
            // 0x57 = pop (sai vì stack rỗng).
            // 0x04 = iconst_1 (đúng, tạo một int).
            out.writeByte(0xAC);        // ireturn

            out.writeShort(0);          // exception_table_length
            out.writeShort(0);          // Code attributes_count
            out.writeShort(0);          // class attributes_count
        }

        return buffer.toByteArray();
    }

    static int wrongBusinessRule(int amount) {
        return amount * 100;            // logic sai, vẫn type safe
    }

    public static void main(String[] args) throws Exception {
        BytesLoader loader = new BytesLoader();

        Class<?> valid = loader.define(
                "demo.ValidCalc",
                classBytes("demo/ValidCalc", false)
        );
        System.out.println("valid value: "
                + valid.getMethod("value").invoke(null));

        try {
            Class<?> invalid = loader.define(
                    "demo.InvalidCalc",
                    classBytes("demo/InvalidCalc", true)
            );
            invalid.getMethod("value").invoke(null);
            System.out.println("invalid accepted: true");
        } catch (VerifyError rejected) {
            System.out.println("invalid rejected: VerifyError");
        }

        System.out.println("bad business result: "
                + wrongBusinessRule(50));
    }
}
~~~

### 10.2. Biên dịch và chạy

Tạo đúng file `VerifierBoundaryDemo.java` và dùng JDK 17+:

~~~bash
javac --release 17 VerifierBoundaryDemo.java
java VerifierBoundaryDemo
~~~

**Stdout kỳ vọng trên JVM tuân thủ Java 17**, không phụ thuộc thông điệp chi tiết của verifier:

~~~text
valid value: 1
invalid rejected: VerifyError
bad business result: 5000
~~~

### 10.3. Giải thích vì sao kết quả như vậy

**Bước 1:** `BytesLoader` là subclass of ClassLoader nên được quyền gọi `defineClass` protected. Tên truyền vào dạng binary name `demo.ValidCalc`; trong constant pool `this_class` là internal name `demo/ValidCalc`.

**Bước 2:** `classBytes` tạo một classfile version 61. Constant pool cung cấp class name, superclass, method name, descriptor và `Code` attribute name. Classfile không có public constructor, nhưng có static method `value()I` để gọi bằng reflection.

**Bước 3:** Method hợp lệ chứa `iconst_1; ireturn`. Ban đầu operand stack rỗng; `iconst_1` đẩy int 1; `ireturn` lấy int và trả đúng method descriptor `()I`. JVM chấp nhận và reflection trả boxed Integer in được thành `1`.

**Bước 4:** Method không hợp lệ chứa `pop; ireturn`. `pop` cần một category-1 operand nhưng stack ở entry đang rỗng. Đây là lỗi verifier, không phải một method trả về “giá trị lạ” ở runtime.

**Bước 5:** `try/catch VerifyError` bao cả `define`, `getMethod` và `invoke`. Một JVM có thể thực hiện một số checks sớm/muộn nhưng phải bác bỏ bytecode vi phạm verifier constraints trước khi nó được thực thi như method hợp lệ. Ví dụ không phụ thuộc vào wording của message hay bytecode offset được report.

**Bước 6:** `wrongBusinessRule(50)` trả 5000 theo một công thức sai. Verifier **không biết** giá trị này nên là bao nhiêu; opcode nhân int hợp lệ. Đây là phản ví dụ trực tiếp cho suy nghĩ “class đã verify thì code đúng/đáng tin”.

### 10.4. Điều gì làm ví dụ này khác ClassFormatError?

Hai classfile đều có magic, version, constant pool, `Code` header, byte length và cấu trúc tương thích. Sự khác nhau duy nhất trong code của method là **một opcode**. Nó làm luồng stack-state không hợp lệ, thay vì phá header/constant-pool layout. Vì vậy kết quả dự kiến thuộc nhóm **`VerifyError`**, không phải “không nhận dạng được classfile”.

**Không cần và không nên dùng `-Xverify:none`, `-noverify` hoặc các tùy chọn vô hiệu hóa verifier** để chạy thí nghiệm. Mục đích là nhìn thấy bảo vệ của JVM, không bỏ qua nó.

## 11. Mã đã verify có thể vẫn ném lỗi runtime

Ví dụ Java 17:

~~~java
public class RuntimeChecksDemo {
    public static void main(String[] args) {
        Object x = "not a number";

        try {
            Integer n = (Integer) x;
            System.out.println(n);
        } catch (ClassCastException expected) {
            System.out.println("cast rejected at runtime");
        }

        try {
            int n = 10 / 0;
            System.out.println(n);
        } catch (ArithmeticException expected) {
            System.out.println("division rejected at runtime");
        }
    }
}
~~~

Chạy:

~~~bash
javac --release 17 RuntimeChecksDemo.java
java RuntimeChecksDemo
~~~

Stdout chính xác:

~~~text
cast rejected at runtime
division rejected at runtime
~~~

Vì sao verifier không ngăn hai exception này trước? Bytecode của `checkcast` và `idiv` **có cấu trúc/kiểu hợp lệ**, còn kết quả phụ thuộc vào value của object hoặc số chia ở runtime. Một lời gọi Java hợp lệ có thể ném exception bình thường khi điều kiện động không thỏa. Verifier bảo vệ kiểu/structure của bytecode, không loại bỏ mọi lỗi runtime.

## 12. Bytecode verifier và Java SecurityManager khác nhau

Hai cơ chế từng bị nhầm vì đều liên quan “an toàn Java”:

| Cơ chế | Câu hỏi nó giải quyết |
| --- | --- |
| Bytecode verification | Classfile/method instructions có thỏa JVM type/flow constraints không? |
| JVM access/linkage checks | Code có tham chiếu class/method/field hợp lệ và được phép truy cập theo rules JVM không? |
| SecurityManager (legacy) | Trong những cấu hình cũ, operation cụ thể có được policy cho phép không? |
| OS/container permissions | Process thực sự có thể làm gì đối với file, network, CPU/memory, users? |
| App authorization | User/request hiện tại có quyền thực hiện action nghiệp vụ không? |

Ở **Java 17**, `SecurityManager` đã được đánh dấu `@Deprecated(since="17", forRemoval=true)` theo JEP 411. Không nên xây một security architecture mới dựa vào một cơ chế đang được loại bỏ. Các JDK sau đó đã siết thêm; ở Java 24, Security Manager bị vô hiệu hóa vĩnh viễn. Mặt khác, **bytecode verifier vẫn là một thành phần quan trọng của JVM** và không phải thứ có thể bỏ đi chỉ vì SecurityManager bị deprecated.

Ngay cả trong môi trường từng có SecurityManager, verification không “kiểm tra file permission”: đó là **trách nhiệm riêng** của access-control mechanisms. Không suy rằng một class có `ProtectionDomain` hoặc `CodeSource` nhất định thì mọi hành vi của nó đã được verifier phê duyệt.

## 13. Trong plugin/agent/bytecode instrumentation, cần chính sách gì?

Khi ứng dụng hỗ trợ bytecode được sinh động hoặc bytecode từ plugin:

### Ranh giới A: lựa chọn nguồn bytes

- Tên lớp nào được phép? Có allowlist package/binary names?
- Bytes đến từ artifact nào? JAR ký, checksum được pin, build pipeline tin cậy?
- Class file có đúng binary name được yêu cầu khi gọi `defineClass` không?
- Có giới hạn bytes, timeouts, size của JAR và số class definitions?
- Có chống path traversal, symlink escape, ZIP extraction hazards và arbitrary URL fetch?

**Verifier không làm các kiểm tra nguồn dữ liệu này thay ứng dụng.**

### Ranh giới B: tương thích linkage/type identity

- Parent delegation có bảo đảm shared service APIs cùng Class runtime?
- Plugin đóng bản copy API, annotation, exception hoặc DTO không?
- Classfile version có chạy được trên JDK mục tiêu không?
- Bytecode transformers có cập nhật StackMapTable/frames/max_stack không?
- Custom loader có ném `ClassNotFoundException`, `ClassFormatError`, `VerifyError` đúng ý nghĩa?

**Verification không bảo đảm mọi dependency/version/loader configuration tương thích.** Có thể class qua verify, sau đó method resolution gặp `NoSuchMethodError` hoặc module access failure.

### Ranh giới C: hành vi code sau khi chạy

- Plugin được phép đọc file nào, mở outbound network nào?
- Có CPU/heap quotas, timeout và watchdog không?
- Business logic có được test, validate và audit?
- Dữ liệu user input có được xử lý an toàn?
- Có một process/container boundary khi code không tin cậy không?
- Có logging/monitoring và cách disable plugin nếu lỗi?

**Verifier không quyết định các policy hành vi này.**

## 15. Quy trình chẩn đoán lỗi VerifyError

Khi thấy stack trace dạng:

~~~text
java.lang.VerifyError: Bad type on operand stack
...
~~~

Dòng trên là **mẫu thông điệp minh họa**; wording, location và bytecode offsets phụ thuộc JDK và classfile.

Thực hiện:

1. **Xác định chính xác binary name** và defining loader của class lỗi.
2. **Ghi JDK version/runtime** và classfile major version.
3. **Xác định artifact cuối cùng** chứa class bytes, không chỉ đọc Java source trong IDE.
4. **Dùng `javap -v -p`** xem method `Code`, frames, constant pool và descriptors.
5. **Kiểm tra bytecode transformer/agent** có sửa opcode mà không cập nhật StackMapTable hoặc max stack/locals không.
6. **So với build clean** trên đúng Java target và dependency versions; tránh JAR cũ không đồng bộ.
7. **Không catch VerifyError rồi gọi tiếp các API của class sai** như thể vấn đề chỉ là missing provider.
8. **Nếu plugin bắt lỗi**, disable plugin, log artifact hash/class name/JDK version nhưng không tiết lộ nội dung nhạy cảm cho user cuối.
9. **Phân biệt với `ClassFormatError`, `UnsupportedClassVersionError`, `NoClassDefFoundError` và `ExceptionInInitializerError`** để sửa đúng giai đoạn.
10. **Sau sửa, kiểm tra cả logic và policy**: việc không còn VerifyError chỉ xác nhận classfile được chấp nhận ở tầng bytecode, không chứng minh hành vi nghiệp vụ đúng.

Nếu cần inspect class trong JAR:

~~~bash
jar --list --file plugin.jar
javap -classpath plugin.jar -v -p com.example.Plugin
~~~

Đây là **lệnh mẫu**, giả sử plugin.jar và class tương ứng có thật. Không chạy `javap` trên một Java source file chưa biên dịch rồi kết luận bytecode runtime tương đương: luôn inspect artifact **đã đóng gói** mà loader thực tế đọc.

## 16. Checklist an toàn cho ứng dụng có class loading động

- [ ] Có xác thực artifact source/registry và danh sách binary names được phép.
- [ ] Có giới hạn kích thước classfile, số class, thời gian đọc và thời gian thực thi theo threat model.
- [ ] Có đường dẫn canonical và bảo vệ storage/symlinks/ZIP entries đúng cách.
- [ ] Có version pinning hoặc kiểm tra compatibility đối với plugin dependencies.
- [ ] Có class loader delegation policy minh bạch cho Java core và shared APIs.
- [ ] Có quy trình quan sát `ClassFormatError`, `VerifyError`, `LinkageError` và initialization errors.
- [ ] Không tắt bytecode verification để cố chạy artifact hỏng.
- [ ] Có sandbox ở **process/container/VM** khi thật sự chạy code không tin cậy.
- [ ] Có OS-level least privilege cho filesystem, network, credentials.
- [ ] Có business validation, testing, logging, incident response.
- [ ] Có giới hạn CPU/memory/thread và lifecycle cleanup cho plugin.
- [ ] Không xem “verify PASS” là chứng chỉ bảo mật của plugin.

## 17. Câu hỏi tự kiểm tra

**1. Bytecode verifier chủ yếu bảo vệ điều gì?**  
Tính hợp lệ cấu trúc và type-safety của bytecode theo quy tắc JVM: operand stack, locals, control flow, initialization state và instruction constraints.

**2. Mã Java gọi `Files.readString(path)` có thể qua verifier không?**  
Có. Verifier không phải policy kiểm soát file permission.

**3. `pop` khi operand stack rỗng thường dẫn tới lỗi gì?**  
`VerifyError` khi verification kiểm tra method, nếu classfile format còn hợp lệ.

**4. Sai magic classfile thường thuộc lỗi gì?**  
`ClassFormatError` hoặc một lỗi class-file format tương ứng, không phải ví dụ chuẩn của `VerifyError`.

**5. Vì sao `checkcast` có thể ném ClassCastException dù bytecode hợp lệ?**  
Tương thích với target Class phụ thuộc object runtime; verifier không biết mọi giá trị thực tế.

**6. `StackMapTable` lưu thông tin gì?**  
Verification types của operand stack và locals tại các bytecode offsets/frames, phục vụ type-state checking.

**7. Verification có phải initialization không?**  
Không. Initialization có thể chạy `<clinit>` và phát sinh lỗi riêng.

**8. Verifier có chứng minh code không gây deadlock/DoS không?**  
Không. Type-safe code vẫn có thể chạy vô hạn hoặc tiêu thụ tài nguyên không giới hạn.

**9. Có thể dùng ClassLoader để sandbox untrusted plugin chỉ vì bytes đã verify không?**  
Không. Cần OS/process/container boundary và chính sách phù hợp.

**10. `SecurityManager` trên Java 17 ở trạng thái gì?**  
Deprecated for removal. Đây là legacy access-control mechanism, không phải bytecode verifier.

**11. Khi một bytecode transformer gây VerifyError, nên làm gì?**  
Xem bytes cuối cùng, frames/max-stack, instruction/control-flow consistency và version; không tắt verification.

**12. Class đã verify có bảo đảm các method references đều tồn tại đúng version không?**  
Không. Resolution/Linkage và các dependencies có thể thất bại khi được sử dụng.

**13. Lỗi của plugin constructor có tự nói verifier sai không?**  
Không; constructor có thể ném exception hợp lệ trong quá trình execution/initialization.

**14. Vì sao cần giới hạn artifact size và source dù có verifier?**  
Vì verification không xác thực nguồn bytes, không quản lý IO bandwidth, byte allocation hoặc CPU/memory quotas cho ứng dụng.

# Phân biệt cô lập không gian tên với cô lập quyền thực thi

## 1. ClassLoader riêng không có nghĩa là sandbox bảo mật

Java có thể dùng nhiều `ClassLoader` để nạp cùng một binary class name thành những runtime types khác nhau. Điều này giúp hệ plugin tổ chức dependencies, tránh xung đột version, hoặc thay implementation mà không khởi động lại toàn ứng dụng. Nhưng từ đó **không được suy ra** plugin có quyền file, mạng, CPU hoặc heap bị tách riêng.

Có hai câu hỏi hoàn toàn khác nhau:

- **Cô lập không gian tên (namespace isolation):** khi code yêu cầu `com.example.Widget`, ClassLoader nào định nghĩa class ấy? Hai plugins có thể có các bản `com.example.Widget` khác nhau không? Loader nào nhìn thấy resource/JAR nào?
- **Cô lập quyền thực thi (execution/permission isolation):** code plugin được phép đọc/ghi file gì, kết nối tới đâu, gọi native APIs, thay đổi shared state, tạo process hoặc tiêu thụ bao nhiêu CPU/memory?

Ví dụ sơ đồ:

~~~text
                  Host JVM Process
+-------------------------------------------------+
| Application ClassLoader: host + shared API      |
|                                                 |
| Plugin Loader A: class codec.Parser (version 1) |
| Plugin Loader B: class codec.Parser (version 2) |
|                                                 |
|  => A.Parser != B.Parser (runtime class identity)|
|                                                 |
|  SHARED EXECUTION AUTHORITY:                     |
|  * JVM process / OS user                         |
|  * Process filesystem / network permissions     |
|  * Heap, CPU, threads, file descriptors         |
|  * Shared JDK classes, System properties        |
+-------------------------------------------------+
~~~

**Tóm tắt:** ClassLoader là công cụ **tìm/định nghĩa lớp và quản lý namespace**. Nó **không tự tạo một identity OS mới hay chính sách permission riêng cho bytecode plugin**.

Bài thuộc nhóm *Ranh giới bảo mật*, tập trung phân biệt type isolation với quyền thực thi. Bạn sẽ thực hành Java 17+ chứng minh một plugin class được nạp riêng vẫn đọc được file thử nghiệm mà JVM process có quyền đọc và thay đổi được một JVM-wide system property. Sau đó sẽ xem SecurityManager, JPMS, process/container isolation, threat model và cách xây plugin boundary thực tế.

## 2. ClassLoader bảo đảm điều gì?

### 2.1. Runtime class identity gắn với defining loader

Với ordinary Java classes, một runtime type thường được xác định bởi:

~~~text
(binaryName, definingClassLoader)
~~~

Hai object loader khác nhau `L1` và `L2` có thể cùng định nghĩa tên `plugin.impl.Worker`:

~~~java
Class<?> a = loaderA.loadClass("plugin.impl.Worker");
Class<?> b = loaderB.loadClass("plugin.impl.Worker");

System.out.println(a.getName().equals(b.getName())); // có thể true
System.out.println(a == b);                           // có thể false
~~~

Đây là snippet minh họa, không phải chương trình độc lập: hai loader phải có đường tìm classes thích hợp. Nếu cả hai ủy quyền cho **cùng parent**, `a == b` có thể là `true` vì parent trả cùng class.

Để phân biệt việc **loader nào thực sự định nghĩa** class với loader được gọi, dùng:

~~~java
ClassLoader defining = a.getClassLoader();
~~~

Một child loader có thể là *initiating loader* của class do parent định nghĩa theo mô hình delegation. Không phải mọi lần `child.loadClass` đều làm child tự gọi `defineClass`.

### 2.2. Những nhu cầu ClassLoader giúp giải quyết

| Nhu cầu | Cơ chế hợp lý | Phần ClassLoader không giải quyết |
|---|---|---|
| Plugin A cần phiên bản `codec-v1`, B cần `codec-v2` | Loader riêng theo plugin, phân chia namespace | Không cấp hai quyền đọc file/network khác nhau |
| Host không compile phụ thuộc implementation | Parent-shared API + loader dành cho implementation | Không ngăn plugin gọi public Java APIs |
| Reload plugin | Tạo loader mới, bỏ reference tới loader cũ khi an toàn | Không đảm bảo dừng code/threads đang chạy |
| Tìm provider | `ServiceLoader` với loader/layer thích hợp | Không tự chặn provider truy cập OS |
| Giữ hai classes trùng binary name | Hai defining loaders khác nhau | Không tạo OS identities khác nhau |
| Tổ chức named modules | JPMS/ModuleLayer + loader mapping | Không tự giới hạn quyền CPU/memory/network |
| Tránh xung đột resources | Phân bố JAR paths và delegation | Không tạo isolation chống code cố ý phá host |

Một ClassLoader hữu ích cho **đóng gói, sự tương thích và class lifecycle**. Chính các ranh giới này không đủ chống plugin độc hại trong cùng process.

### 2.3. Lỗi `ClassCastException` không phải dấu hiệu security boundary

Nếu interface `plugin.api.Service` được host và plugin loaders định nghĩa thành hai runtime classes:

~~~text
HostLoader     -> plugin.api.Service#H
PluginLoader   -> plugin.api.Service#P
~~~

thì một implementation của `Service#P` không nhất thiết cast được sang `Service#H`. Lỗi type identity như vậy phản ánh **hai definitions khác nhau**, không có nghĩa plugin đã bị hạn chế đọc file hay dùng network.

Thiết kế API xuyên boundary nên cho parent loader định nghĩa **một bản interface/DTO chung**, còn implementation/private dependencies do loader con nạp. Kể cả khi API isolation đúng, permission isolation vẫn là vấn đề độc lập.

## 3. Quyền thực thi nằm ở đâu?

### 3.1. Một JVM process có quyền OS nhất định

Trong một ứng dụng chạy bằng service account, các threads của host và plugin cùng thực thi **trong cùng process**. Nếu không có policy cưỡng chế riêng, các file/socket/process APIs chịu quyền của process đó.

Ví dụ capability cần kiểm soát:

- File: đọc, tạo, ghi, xóa và duyệt đường dẫn.
- Network: kết nối ra Internet/nội mạng, lắng nghe port, DNS.
- Process/native: tạo process con, JNI/FFM khi khả dụng và được cho phép theo runtime.
- CPU/RAM/threads: sử dụng tài nguyên chung của JVM.
- Secrets: environment variables, secret files, credentials cấp cho process.
- Process-wide configuration: `System.setProperty`, global logging, shared registries.
- Shared objects: callbacks, static singletons từ class do parent định nghĩa, caches.

**Quyền đọc một path không suy ra quyền đọc mọi path.** OS, tài khoản và policy cụ thể quyết định mỗi thao tác. Nhưng **ClassLoader khác nhau tự nó không làm những quyền ấy khác nhau**.

### 3.2. Shared classes có state chung

Mỗi runtime class riêng có **static fields riêng**, kể cả hai classes có cùng binary name nhưng defining loaders khác nhau.

Ngược lại, các class của Java platform và shared API được nạp chung vẫn có state chung. `java.lang.System` là ví dụ dễ kiểm chứng: JVM system properties được chia sẻ giữa code của host và plugins trong cùng process.

~~~java
System.setProperty("example.flag", "changed");
System.out.println(System.getProperty("example.flag"));
~~~

Đoạn snippet minh họa này không tạo một map riêng cho từng plugin. Nếu cần state độc lập, hãy truyền một context riêng hoặc đưa plugin sang process riêng. Cũng đừng truyền secrets vào một shared context rồi hy vọng loader ngăn plugin đọc.

### 3.3. Một namespace khác không đồng nghĩa một principal khác

Trong thiết kế bảo mật, **principal/security identity** là đối tượng mà chính sách ủy quyền áp dụng, ví dụ một OS user, process sandbox identity hoặc authenticated service principal. **ClassLoader object** không đương nhiên là principal mà OS dùng để kiểm tra quyền.

~~~text
ClassLoader identity:  "Ai định nghĩa class này?"
OS identity:           "Process nào/user nào đang thao tác?"
Application authz:     "Caller này được thực hiện operation nào?"
~~~

Cần có **đường cưỡng chế thật** giữa code và resource. Gắn nhãn `SandboxClassLoader` hoặc chọn URL riêng không đủ để kernel chặn file operations.

## 4. Ví dụ Java 17+ chạy độc lập: hai loader, một process

Ví dụ được giới hạn an toàn: host tạo **một file tạm chỉ chứa chuỗi MARKER_OK**, truyền `Path` cho plugin và sau đó xóa file. Plugin A chỉ đọc file này và sửa **một system property có tên riêng dành cho demo**; plugin B đọc lại property. Không yêu cầu internet, công cụ bên ngoài hoặc quyền đặc biệt.

### 4.1. Cấu trúc dự án

~~~text
demo/
├── src/
│   ├── plugin/
│   │   └── example/plugin/Probe.java
│   └── host/
│       └── BoundaryDemo.java
└── build/
    ├── plugin/
    │   └── example/plugin/Probe.class
    └── host/
        └── BoundaryDemo.class
~~~

Khi chạy chỉ thêm `build/host` vào application classpath. **Không đưa `build/plugin` vào `-cp`**, vì nếu parent tìm được `Probe` trước thì hai child loaders có thể nhận cùng class và phép so identity không còn chứng minh mong muốn.

### 4.2. Tệp `src/plugin/example/plugin/Probe.java`

~~~java
package example.plugin;

import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public final class Probe {
    public static String readMarker(Path path) throws IOException {
        return Files.readString(path, StandardCharsets.UTF_8);
    }

    public static String readSharedProperty() {
        return System.getProperty("demo.shared.flag");
    }

    public static void changeSharedProperty() {
        System.setProperty("demo.shared.flag", "PLUGIN_CHANGED");
    }
}
~~~

Đây là plugin implementation bình thường, không có custom permission hoặc API bỏ qua sandbox. `Files` và `System` là public JDK classes mà code plugin có thể sử dụng khi chạy trong JVM với quyền phù hợp.

### 4.3. Tệp `src/host/BoundaryDemo.java`

~~~java
import java.lang.reflect.Method;
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public final class BoundaryDemo {
    public static void main(String[] args) throws Exception {
        Path marker = Files.createTempFile("plugin-permission-", ".txt");
        try {
            Files.writeString(marker, "MARKER_OK", StandardCharsets.UTF_8);
            System.setProperty("demo.shared.flag", "HOST_INITIAL");
            URL pluginRoot = Path.of("build/plugin").toUri().toURL();
            ClassLoader parent = BoundaryDemo.class.getClassLoader();

            try (URLClassLoader loaderA =
                         new URLClassLoader(new URL[] {pluginRoot}, parent);
                 URLClassLoader loaderB =
                         new URLClassLoader(new URL[] {pluginRoot}, parent)) {

                Class<?> a = loaderA.loadClass("example.plugin.Probe");
                Class<?> b = loaderB.loadClass("example.plugin.Probe");

                System.out.println("sameBinaryName="
                        + a.getName().equals(b.getName()));
                System.out.println("differentRuntimeClasses=" + (a != b));
                System.out.println("differentDefiningLoaders="
                        + (a.getClassLoader() != b.getClassLoader()));

                Method read = a.getMethod("readMarker", Path.class);
                System.out.println("pluginCanReadHostFile="
                        + "MARKER_OK".equals(read.invoke(null, marker)));

                a.getMethod("changeSharedProperty").invoke(null);
                System.out.println("hostSeesPluginPropertyChange="
                        + "PLUGIN_CHANGED".equals(
                                System.getProperty("demo.shared.flag")));

                Method readSetting = b.getMethod("readSharedProperty");
                System.out.println("otherLoaderSeesSameProperty="
                        + "PLUGIN_CHANGED".equals(
                                readSetting.invoke(null)));
            }
        } finally {
            Files.deleteIfExists(marker);
            System.clearProperty("demo.shared.flag");
        }
    }
}
~~~

Giải thích:

- `URLClassLoader loaderA` và `loaderB` là **hai object khác nhau**, cùng trỏ tới một directory chứa bytecode. Mỗi loader tự định nghĩa `example.plugin.Probe` vì parent không nhìn thấy class đó.
- Host không compile với `Probe.java`; reflection gọi public static methods của class được load. Đây là kỹ thuật của demo, còn production có thể dùng shared SPI/interface.
- `Files.createTempFile` tạo file marker, `writeString` ghi text, `finally` xóa file khi xong.
- `Files.readString` chạy **trong cùng process** với host. ClassLoader khác không tự loại quyền đọc file mà process có.
- `System.setProperty` thay đổi JVM-wide state, nên host và plugin B đều quan sát được.
- `try-with-resources` đóng loader resources. Việc này không đồng nghĩa thu hồi mọi class đã define hoặc dừng tất cả threads.

### 4.4. Biên dịch và thực thi

Linux/macOS, chạy từ thư mục `demo`:

~~~sh
mkdir -p build/plugin build/host
javac --release 17 -d build/plugin src/plugin/example/plugin/Probe.java
javac --release 17 -d build/host src/host/BoundaryDemo.java
java -cp build/host BoundaryDemo
~~~

Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force build/plugin, build/host | Out-Null
javac --release 17 -d build/plugin src/plugin/example/plugin/Probe.java
javac --release 17 -d build/host src/host/BoundaryDemo.java
java -cp build/host BoundaryDemo
~~~

### 4.5. Stdout chính xác đã kiểm chứng

~~~text
sameBinaryName=true
differentRuntimeClasses=true
differentDefiningLoaders=true
pluginCanReadHostFile=true
hostSeesPluginPropertyChange=true
otherLoaderSeesSameProperty=true
~~~

Demo đã biên dịch bằng `javac --release 17` và chạy thành công với JDK trong môi trường thông thường không bật legacy SecurityManager hay OS policy đặc biệt cấm đọc file tạm. Output không phụ thuộc tên file tạm hoặc chuỗi định danh loader.

### 4.6. Đọc kết quả

| Output | Bằng chứng |
|---|---|
| `sameBinaryName=true` | Hai class có cùng binary name |
| `differentRuntimeClasses=true` | Hai class objects khác identity |
| `differentDefiningLoaders=true` | Loader A/B thật sự định nghĩa class riêng |
| `pluginCanReadHostFile=true` | Plugin A đọc được marker file do host tạo trong cùng process |
| `hostSeesPluginPropertyChange=true` | Plugin A thay đổi global JVM property, host thấy thay đổi |
| `otherLoaderSeesSameProperty=true` | Plugin B cũng thấy state mới dù implementation class của B khác |

**Không kết luận quá mức:** demo chỉ chứng minh code plugin có thể đọc **file marker được truyền path và được process cho phép**, không chứng minh có thể đọc mọi file trên máy; đó là việc của OS policy. Nó chứng minh **tách class identity không tự tách quyền của process**.

### 4.7. Các phép thử mở rộng

**Thử A — Thêm plugin vào system classpath:** parent có thể định nghĩa `Probe` thay hai child loaders, khiến `differentRuntimeClasses=false`. Quyền file OS không tự đổi.

**Thử B — Không gửi `Path` cho plugin:** plugin không có path cụ thể để gọi method trong ví dụ. Nhưng đây là **kiểm soát luồng dữ liệu theo hợp đồng**, không phải ranh giới an toàn chống code plugin có thể gọi public Java APIs khác.

**Thử C — Chạy plugin trong process riêng:** cấp cho plugin process một OS user/filesystem view không có quyền đọc marker. Nếu policy thực sự chặn, code dù biết path cũng không thể đọc. Chính **OS/process enforcement** tạo sự khác biệt.

**Thử D — Thêm static field vào `Probe`:** mỗi runtime class của A/B có static field riêng. Trong khi đó `System` là shared JDK class nên state của nó dùng chung. Cần phân biệt **statics per runtime class** và **globals của process/shared classes**.

## 5. Vì sao SecurityManager không phải lời giải mới cho plugin sandbox?

Trong các JDK cũ, một `SecurityManager` được bật cùng policy phù hợp có thể kiểm tra một số thao tác nhạy cảm qua `Permission`/`ProtectionDomain`. **Một ClassLoader riêng không tự bật cơ chế đó**; việc gán `CodeSource` hoặc `ProtectionDomain` cũng không khiến hệ điều hành cấp một bộ quyền độc lập.

Các mốc cần nhớ:

| Phiên bản | Hành vi cần lưu ý |
| --- | --- |
| **JDK 17** | JEP 411 đánh dấu `SecurityManager` là **deprecated for removal**; mã legacy còn phụ thuộc chính sách và cấu hình. |
| **JDK 17–23** | Khả năng bật/cài manager và cảnh báo thay đổi theo bản JDK; cần kiểm tra runtime cụ thể. |
| **JDK 24+** | JEP 486 **permanently disabled**: không thể bật qua startup flag hay `System.setSecurityManager`. |

`CodeSource` mô tả thông tin nguồn khi có; nó không phải xác thực artifact hoặc sandbox. Để tách quyền truy cập file, network, bí mật và tài nguyên giữa host và plugin không tin cậy, cần một ranh giới **process/OS** được cấu hình và kiểm thử thực tế.

Tài liệu: [JEP 411](https://openjdk.org/jeps/411), [JEP 486](https://openjdk.org/jeps/486), [Oracle JDK 24](https://docs.oracle.com/en/java/javase/24/security/security-manager-is-permanently-disabled.html). Bài **SecurityManager là cơ chế lịch sử và cần đối chiếu phiên bản JDK** phân tích cụ thể các API legacy, startup flags và migration.

## 6. JPMS strong encapsulation cũng khác sandbox tài nguyên

JPMS cung cấp:

- `requires`: module readability.
- `exports`: package nào được module khác truy cập theo Java access rules.
- `opens`: mở package cho deep reflection theo ngữ cảnh.
- `ModuleLayer`: ánh xạ named modules với loader(s) và module resolution.

Ví dụ descriptor:

~~~java
module plugin.api {
    exports plugin.api;
}
~~~

Ngăn deep reflection vào một package là **cô lập truy cập class/member**, không phải giới hạn OS operations. Một plugin module vẫn có thể gọi `java.nio.file.Files` nếu Java/module access hợp lệ và OS cho phép file operation.

Tương tự, cấu hình `--add-opens` hoặc `--add-exports` làm thay đổi phạm vi Java module access, không phải ACL mạng/file. `ModuleLayer` không tạo kernel namespace hoặc per-module CPU quota. Module graph và loader mapping là công cụ cấu trúc application, không phải container.

## 7. Chọn ranh giới theo mức độ tin cậy

### 7.1. Plugin nội bộ, được kiểm duyệt

Khi code do cùng nhóm phát triển và review, chạy cùng JVM với ClassLoader riêng có thể là lựa chọn hợp lý:

- Dễ gọi Java interface trực tiếp, ít chi phí IPC.
- Hỗ trợ multiple versions của libraries.
- Cho phép plugin lifecycle, nạp lại với loader mới.
- API chung được loader parent định nghĩa một lần.
- Cho phép `ServiceLoader`/module layers để discovery.

Tuy nhiên cần vẫn xử lý resource leaks, timeouts, exception propagation, shared state và version conflicts. **Tin cậy cao** không đồng nghĩa code không thể có bug hoặc ảnh hưởng host.

### 7.2. Plugin của bên thứ ba hoặc multi-tenant

Nếu plugin không cùng trust domain, ranh giới thực thi có thể là:

~~~text
Trusted host JVM
      |
      | IPC request/response + authz
      v
Isolated plugin runner process
  - dedicated OS identity / limited credentials
  - filesystem mounts / allowlists
  - network egress and ingress rules
  - CPU, memory, PID, FD quotas
  - timeout, restart, supervision
      |
      v
Plugin's own ClassLoader (nếu vẫn cần namespace isolation)
~~~

Host không chia sẻ tùy tiện object heap và process privileges với plugin. Một loader bên trong runner vẫn hữu ích cho dependencies, nhưng **quyền thực thi được bảo vệ tại process/OS boundary**.

### 7.3. Containers, sandbox và máy ảo

Container có thể cung cấp isolation hữu ích, nhưng mức an toàn phụ thuộc cấu hình:

- Không cấp quyền privileged, không mount host secrets/filesystem/Docker socket không cần thiết.
- Dùng OS user/capabilities tối thiểu; rootless/user namespace khi phù hợp.
- Giới hạn egress network, seccomp/AppArmor/SELinux, mounts, read-only paths theo môi trường.
- Áp quotas và restart policy; theo dõi logs và resource usage.
- Giữ kernel/runtime đã vá; xác minh image và dependencies.

Container thường chia sẻ kernel với host. Khi threat model yêu cầu cách ly mạnh hơn, cân nhắc VM/hypervisor, process isolation có kiểm soát hoặc dịch vụ thực thi riêng. Không có ranh giới nào an toàn chỉ nhờ tên gọi.

### 7.4. API allowlist là cách thiết kế tốt nhưng không đủ chống code đối nghịch

Một host có thể chỉ cung cấp:

~~~java
public interface PluginContext {
    byte[] readApprovedResource(String id) throws Exception;
    void emitOutput(String value);
}
~~~

Đây là contract minh họa. Với **code hợp tác**, giới hạn methods theo capabilities làm thiết kế rõ hơn. Nhưng nếu plugin bytecode tùy ý trong cùng JVM vẫn truy cập được public JDK APIs, nó **có thể bypass API do host đề xuất**. Muốn cưỡng chế với code không tin cậy, phải đặt policy ở boundary không thể bỏ qua (OS/process/IPC).

### 7.5. Bảng ra quyết định

| Tiêu chí | Một JVM, ClassLoader riêng | Process riêng + OS policy |
|---|---|---|
| Namespace/version isolation | Có thể thực hiện tốt | Có, thêm process boundary |
| Shared Java objects | Trực tiếp qua shared API | Dùng IPC/serialization |
| Chặn truy cập secret file của host | **Không tự làm được** | Có thể nếu user/mounts/credentials đúng |
| Network allowlist per plugin | **Không tự làm được** | Có thể nếu policy được cưỡng chế |
| CPU/memory quota per plugin | Không có quota tin cậy per loader | Có thể áp process/container quotas |
| Một plugin crash làm chết host | Không bảo đảm cô lập | Host có thể giữ process riêng hoạt động |
| Triển khai, debug, latency | Đơn giản hơn | Phức tạp hơn, IPC overhead |
| Plugin đáng tin | Thường đủ cho namespace | Cân nhắc nếu cần fault isolation |
| Plugin đối nghịch/untrusted | **Không đủ** | Cần ranh giới thực thi mạnh hơn |

**Tách namespace là mục tiêu kỹ thuật; tách permissions là mục tiêu bảo mật.** Chọn theo threat model, không chỉ theo cấu trúc code.

## 8. Các rủi ro ClassLoader không thể tự loại bỏ

### 8.1. File và network

Nếu JVM chạy bằng account có quyền đọc một secret file, class được định nghĩa bởi child loader **không tự mất quyền đó**. Plugin có thể gọi public file/network APIs, chịu OS permission checks như các threads khác trong process.

Nếu cần tách tenants: cấp secrets vào từng runner khác nhau hoặc thiết kế broker với authorization; đừng dùng `ClassLoader == tenantIdentity` thay ACL thực sự.

### 8.2. Shared state và can thiệp giữa plugins

Một plugin có thể tác động `System` properties, global logs, static shared caches, các callbacks/registries và mutable objects host truyền vào. Tạo ClassLoader riêng không tạo bản sao của shared JDK classes.

Thiết kế ít shared mutable state, dùng immutable DTOs và ranh giới interface rõ có thể giảm lỗi logic, nhưng với bytecode untrusted cần enforcement ngoài Java object conventions.

### 8.3. Denial of service

Một plugin có thể chiếm CPU, allocate quá nhiều memory, tạo threads hoặc giữ file descriptors. Không có quota CPU/heap/thread **theo ClassLoader** mặc định.

`Future.cancel(true)` hoặc `Thread.interrupt()` có ích khi code hợp tác, **không là kill switch chắc chắn** cho code bị lỗi hoặc đối nghịch. `Thread.stop()` không phải lựa chọn an toàn để sandbox. Process runner riêng có thể bị terminate/restart theo policy của hệ thống.

### 8.4. Class unloading không phải revocation

`URLClassLoader.close()` giải phóng resources loader, nhưng không đảm bảo tất cả loaded classes được unload ngay; instances, threads, `Thread Context ClassLoader`, caches và method handles có thể giữ chúng sống. Đóng loader **không tự thu hồi OS authority** của thread/plugin code đang chạy.

Nếu cần thu hồi quyền cưỡng chế, có thể ngừng/kill process riêng và thu hồi credentials/network policy; cách đó khác hoàn toàn với việc bỏ tham chiếu ClassLoader.

### 8.5. Type safety không đồng nghĩa authorization

JVM bytecode verifier và class loading rules bảo vệ tính nhất quán của type system. Một chương trình **type-safe** vẫn có thể thực hiện hành vi không mong muốn bằng các API hợp lệ với quyền process đã có.

**“JVM từ chối định nghĩa class trùng tên” không chứng minh JVM chặn mọi hành vi file/network của code plugin.**

## 9. Quy trình thiết kế và kiểm chứng plugin boundary

Bắt đầu bằng **threat model**, rồi chọn kỹ thuật theo đúng nguồn rủi ro:

1. **Ai kiểm soát bytecode?** Code nội bộ đã review, partner đã duyệt hay người dùng tùy ý? Kiểm tra publisher, artifact, dependency và khả năng bị thay trước khi chạy.
2. **Tài nguyên nào cần giữ riêng?** Secrets, database, filesystem, network, process lifetime hoặc quyền của những tenants khác. Xác định ai hiện có quyền OS đến chúng.
3. **Mục tiêu cô lập là gì?** Nếu chỉ để mỗi plugin dùng một library version, có thể dùng ClassLoader. Nếu phải chặn hành vi của code đối nghịch, cần process và chính sách OS.
4. **Giao tiếp qua ranh giới như thế nào?** Host phải thực hiện AuthN/AuthZ, validate inputs và outputs, giới hạn message size, timeout, retries và các operation cho phép; worker output vẫn là dữ liệu không tin cậy.
5. **Chứng minh quyền bị chặn ra sao?** Trong môi trường deploy thực, thử đọc file giả lập ngoài allowlist và kết nối test endpoint bị cấm; xác minh OS từ chối, cùng với quota CPU/memory và cleanup sau timeout.

```text
Artifact/source gate → ClassLoader/JPMS (namespace)
                     → Process/OS policy (permissions/quotas)
                     → IPC authorization & validation → Monitoring
```

Các tầng giải quyết các câu hỏi riêng. Một allowlist Java API do host cung cấp có ích với plugin hợp tác, nhưng không ngăn bytecode đối nghịch cùng JVM tự gọi public JDK APIs. Chi tiết supervisor, pipes, timeouts, process tree và IPC nằm trong bài **Tách tiến trình khi cần ranh giới bảo mật mạnh hơn ClassLoader**.

## 10. Những trường hợp dễ nhầm

### “Hai plugins có cùng tên class nhưng khác ClassLoader, vậy đã cô lập”

**Đúng một phần:** chúng có thể là hai runtime types khác nhau, giúp tránh namespace collision. **Sai nếu nói về quyền file/network**: các threads vẫn có thể cùng process authority.

### “JPMS không cho plugin reflect vào private field, vậy plugin không thể đọc secrets”

Không đủ. JPMS hạn chế Java module access, nhưng nếu secret tồn tại trong file/environment/IPC mà process vẫn có quyền đọc, cần chính sách riêng. Cũng đừng đưa secrets vào object graph shared một cách vô ý.

### “Plugin chỉ được cung cấp PluginContext nhỏ nên chắc chắn không thể gọi File APIs”

Không đúng với bytecode tùy ý trong cùng JVM nếu không có enforcement khác. Interface boundary tốt về thiết kế nhưng không tự chặn code không hợp tác.

### “JEP 411 chỉ deprecated; ta vẫn bật SecurityManager mãi được”

Sai: **JEP 486 ở JDK 24 đã vô hiệu hóa vĩnh viễn**. Thiết kế dựa trên `java.policy` không có hướng phát triển bền vững cho JDK mới.

### “Container là sandbox tuyệt đối”

Không. Container cần cấu hình ít quyền, mounts, secrets, egress, capabilities, quotas và cập nhật kernel phù hợp. Đối với threat model mạnh hơn, cân nhắc VM/hypervisor.

### “Đóng loader là dừng plugin”

Không. Loaded classes/instances/threads có thể vẫn tồn tại; tài nguyên OS của process không đổi. Cần lifecycle/shutdown logic, hoặc kill/restart process ở boundary riêng.

### “Signature của JAR cho phép plugin làm gì?”

Chữ ký chủ yếu phục vụ xác minh artifact integrity/origin, **không tự là policy giới hạn I/O**. Có provenance đáng tin không đồng nghĩa code không có lỗi hoặc không phá resource của process.

### “ClassLoader riêng có JVM heap/GC độc lập”

Sai: không có heap, garbage collector và CPU scheduler riêng theo ClassLoader mặc định. Tài nguyên có thể được đo/giới hạn theo process/container, chứ không tự theo loader.

## 11. Câu hỏi và bài tập tự kiểm tra

1. Namespace isolation trả lời câu hỏi gì? Permission isolation trả lời câu hỏi gì?
2. Runtime type identity của ordinary class gắn với những thành phần nào?
3. Vì sao hai ClassLoader khác nhau có thể vẫn trả cùng `Class<?>`?
4. Vì sao `ClassCastException` do loader khác nhau không phải bằng chứng sandbox đã hoạt động?
5. ClassLoader có tự tạo OS identity hoặc tài khoản file permission khác không?
6. Trong demo, vì sao hai runtime classes khác nhau nhưng đều nhìn thấy `System` properties?
7. Static field trong `Probe` do loader A định nghĩa có dùng chung với bản `Probe` của B không?
8. `pluginCanReadHostFile=true` chứng minh điều gì và **không** chứng minh điều gì?
9. Nếu plugin thật sự không được đọc secret file, cần boundary cưỡng chế ở đâu?
10. `ServiceLoader`/`URLClassLoader` giúp vấn đề discovery và dependency như thế nào?
11. `ModuleLayer` và `exports`/`opens` có tự ngăn network egress không?
12. JEP 411 liên quan phiên bản Java nào và JEP 486 liên quan JDK nào?
13. Vì sao `ProtectionDomain`/`CodeSource` không tự bảo đảm file/network sandbox trên JDK 24+?
14. Dùng API wrapper `PluginContext` có ích gì dù không đủ đối phó bytecode đối nghịch?
15. Vì sao plugin không hợp tác có thể làm timeout/cancellation trong cùng JVM thiếu tin cậy?
16. Tại sao URLClassLoader.close không bảo đảm dừng threads và thu hồi OS permissions?
17. Khi plugin A/B cần hai versions library, chọn ClassLoader riêng hay process riêng theo tiêu chí nào?
18. Những điều kiện nào cần kiểm soát ở container để không lộ host secrets?
19. Khi chuyển plugin sang IPC, host cần validate/authz những yếu tố nào?
20. Artifact được ký có thể vẫn chạy lỗi hoặc gây resource exhaustion không?
21. Đâu là nơi đặt CPU/memory quotas thực sự?
22. Vì sao cần test ranh giới quyền trên build/deploy thực tế chứ không chỉ trong IDE?
23. Với hệ multi-tenant, vì sao một ClassLoader mỗi tenant không bằng một security principal mỗi tenant?
24. Hãy vẽ lại sơ đồ ba tầng: classloader namespace, Java module access và OS/process permissions.
25. Nêu một tình huống mà ClassLoader riêng là **đúng giải pháp** và một tình huống mà nó **không đủ**.

**Tiêu chí hoàn thành:** chạy và giải thích được đủ sáu dòng stdout; chứng minh type identity có thể khác nhưng quyền process vẫn chia sẻ; phân biệt Java access control với OS authorization; biết trạng thái SecurityManager Java 17/JDK 24+; đề xuất cách tách quyền thực thi thực sự khi chạy untrusted plugins.

# Kiểm soát nguồn JAR, tính toàn vẹn và phụ thuộc được phép

Ứng dụng Java có thể nạp bytecode từ JAR thông qua `URLClassLoader`, plugin framework, `ServiceLoader` hoặc `ModuleLayer`. Tuy nhiên **“nạp được class” không có nghĩa “JAR đáng tin và được phép thực thi”**. Trước khi cho code từ bên ngoài chạy trong JVM, cần kiểm soát đồng thời **nguồn xuất bản**, **định danh artifact và phiên bản**, **tính toàn vẹn bytes**, **chuỗi phụ thuộc** và **quyền thực thi ở runtime**.

Đây là một vấn đề **ranh giới bảo mật và software supply chain**. Một JAR có checksum đúng vẫn có thể chứa mã độc hoặc CVE; một JAR ký số hợp lệ vẫn có thể được ký bởi người không được tổ chức phê duyệt; một JAR được phép nhưng mang theo dependency ngoài allowlist vẫn có thể khiến JVM thực thi code ngoài ý định.

**Nguyên tắc xuyên suốt:** Xây dựng **cổng kiểm tra artifact** trước class loading; chỉ tạo loader/define module từ **đúng bản bytes đã được chấp thuận**. Nếu một điều kiện không kiểm chứng được, **fail closed**, không fallback sang repository hoặc đường nạp khác để “chạy cho được”.

## 1. Ba lớp kiểm soát phải tách bạch

| Câu hỏi | Dữ liệu cần có | Điều nó không tự chứng minh |
| --- | --- | --- |
| **Nguồn JAR có được phê duyệt?** | Publisher, repository, tọa độ artifact, version, chính sách release | Nội dung có nguyên vẹn hay không |
| **Artifact có đúng bản đã duyệt?** | SHA-256 pin từ trusted policy, chữ ký và signer trust khi yêu cầu | Code không chứa lỗi hoặc hành vi độc hại |
| **Có được phép dùng các phụ thuộc này?** | Full resolved dependency graph, versions, hashes, scopes, allowlist runtime | Code không dùng reflection, native library hoặc tải thêm thứ khác |

Ba lớp này tạo một đường dẫn kiểm soát:

~~~text
Publisher / CI build đáng tin
            |
            v
   Repository được phép
            |
            v
    JAR + metadata phát hành
            |
            v
        POLICY GATE
        /    |      \
       v     v       v
   Origin   SHA-256  Graph dependency
       \     |       /
        \    |      /
         v   v     v
       staging được bảo vệ
               |
               v
      ClassLoader / ModuleLayer
               |
               v
       Runtime isolation + audit
~~~

Không được gộp ba câu hỏi thành một cờ `isTrusted=true` không rõ xuất xứ. Nếu JAR đi qua nhiều lớp (CI, artifact registry, cache triển khai, host plugin manager), mỗi lớp cần biết **ai là nguồn sự thật** cho digest/identity/phê duyệt và ai có quyền cập nhật.

### Những nguy cơ cần bao phủ

- **Tampering:** một file JAR bị thay đổi sau thời điểm build hoặc sau khi phê duyệt.
- **Publisher compromise:** tài khoản phát hành hoặc CI bị chiếm, tạo một bản trông hợp lệ về tên và phiên bản.
- **Dependency confusion:** artifact thuộc namespace nội bộ bị giải từ public repository do trùng tên hoặc mapping sai.
- **Typosquatting:** artifact có tên gần giống thư viện hợp lệ.
- **Transitive dependency ngoài ý muốn:** một dependency trực tiếp kéo theo package mới chưa được duyệt.
- **Version drift/downgrade:** phiên bản hoặc bytes thay đổi vì ranges, snapshot, mirror, cache hay lock thiếu.
- **Runtime graph drift:** `Class-Path` trong manifest, loader được thêm URL, service provider, native library hoặc downloader đưa thêm code vào process.
- **Vulnerability ở artifact nguyên vẹn:** JAR đúng hash nhưng phiên bản vốn có CVE, backdoor, rủi ro license hoặc quyền hoạt động vượt mức cần thiết.

HTTPS/TLS và repository nội bộ giảm nhiều nguy cơ, nhưng **không tự xác nhận publisher/artifact code an toàn**. Một endpoint có TLS hợp lệ vẫn có thể chứa bản phát hành bị đầu độc.

## 2. Chính sách nguồn (origin/identity allowlist)

Một cơ chế chấp nhận JAR không nên chỉ kiểm tra đuôi file `.jar` hoặc tên thư mục. Với Maven-style artifacts, cần ghi nhận **tọa độ và nguồn**:

~~~yaml
# Minh họa một chính sách tự thiết kế, KHÔNG phải schema Maven/Gradle.
artifact: com.acme.plugins:greeter:1.0.0
repository: internal-approved-registry
publisher: approved-release-identity
sha256: "digest-64-hex-được-lấy-từ-trusted-policy"
runtime_dependencies:
  - com.acme.api:plugin-contract:2.3.0
  - org.example:safe-parser:4.2.1
manifest_class_path: deny
native_libraries: deny
network_code_downloads: deny
~~~

Đây chỉ là **pseudocode cấu hình**, chuỗi `sha256` minh họa chỗ đặt digest đã duyệt, không phải digest thực. Policy thực tế cần schema và validator cụ thể, versioning, approver và quy trình cập nhật đáng tin.

**Cần chốt ít nhất:**

1. **Group/artifact/version/classifier** (nếu có), không chấp nhận một JAR có tên đẹp nhưng thiếu danh tính phát hành.
2. **Registry/repository được phép**, mapping namespace nội bộ rõ ràng, credential và quyền publish tối thiểu.
3. **Signer hoặc provenance identity**, nguồn evidence độc lập đủ mạnh để liên kết digest với bản phát hành đúng.
4. **SHA-256 của từng artifact** ở bản deploy, không chỉ metadata package.
5. **Allowlist cho toàn bộ dependency graph**, gồm direct, transitive, runtime và mọi thành phần được nhúng.
6. **Version và policy revocation**, để một bản từng được chấp nhận có thể bị gỡ khi phát hiện compromise hoặc CVE nghiêm trọng.
7. **Audit evidence**: ai đã approve, lúc nào, manifest đã kiểm tra, digest cuối, loader/plugin nào tiêu thụ.

### Không so đường dẫn bằng chuỗi thô

Sai về nguyên tắc:

~~~java
// Fragment sai: "/approved-evil/x.jar" cũng bắt đầu bằng "/approved".
if (jarPath.toString().startsWith("/approved")) {
    allow();
}
~~~

Đây là **fragment phản ví dụ**, không phải chương trình độc lập. Trong Java, nên kiểm tra đường dẫn đã canonical hóa bằng `Path.toRealPath()` và `Path.startsWith(Path)`, xem xét symlink, filesystem permissions và writable directories.

**Nhưng đường dẫn đúng chưa có nghĩa file không đổi:** Giữa lúc tính checksum và lúc `URLClassLoader` mở file có thể xảy ra **TOCTOU (time-of-check/time-of-use)**. Môi trường production cần **staging immutable/read-only do bên tin cậy kiểm soát**, bảo đảm loader đọc đúng bytes vừa verify; không cho một writer chưa được kiểm soát thay file giữa hai bước.

## 3. Kiểm tra tính toàn vẹn bằng SHA-256

Với JAR `greeter-1.0.jar`, tính digest trên **toàn bộ bytes JAR**:

~~~text
SHA256(actual-final-JAR-bytes) == trustedExpectedDigest
~~~

Một bản build khác có thể chứa bytecode tương đương nhưng ZIP metadata, timestamp hoặc thứ tự entry khác, khiến **hash toàn JAR khác nhau**. Điều này không nhất thiết là tấn công, nhưng **artifact cuối đã được pin** thì phải khớp toàn bộ bytes.

Trên Windows PowerShell:

~~~powershell
Get-FileHash .\approved\greeter-1.0.jar -Algorithm SHA256
~~~

Trên Linux:

~~~bash
sha256sum approved/greeter-1.0.jar
~~~

Trên macOS có thể dùng `shasum -a 256`. Các lệnh này **chỉ tính** digest hiện tại; tự chúng chưa quyết định hash ấy đáng tin hay không.

### Hash kỳ vọng phải đến từ đâu?

Đây là bẫy quan trọng nhất của checksum: Nếu kẻ tấn công kiểm soát endpoint phát tán và cung cấp cả `plugin.jar` lẫn `plugin.jar.sha256` thì việc hai file khớp nhau **không chứng minh điều gì về publisher**. Kẻ tấn công chỉ cần thay **cả hai**.

Giá trị kỳ vọng phải được lấy theo policy độc lập, chẳng hạn:

- Trusted build/release manifest do pipeline được phê duyệt tạo và ký, gắn với tọa độ artifact.
- Signed attestation với trust root và builder/publisher identity được tổ chức xác minh.
- Cơ sở dữ liệu triển khai có quyền ghi/phê duyệt chặt, chỉ lưu digest đã review từ quy trình tin cậy.
- Giá trị pin được truyền out-of-band qua kênh quản trị đã xác thực.

**Hash không phải chữ ký.** SHA-256 trả lời “bytes có đúng với pin hay không”, không trả lời “ai đã xuất bản” nếu pin không có provenance. `String.hashCode()`, CRC32 hay một file MD5 cũ không thay thế SHA-256 cho kiểm soát tính toàn vẹn đối kháng hiện đại.

### So trên artifact cuối

Nếu JAR bị repack, shaded, re-signed, stripped hoặc biến đổi sau khi hash, cần phê duyệt digest **đúng artifact được đưa vào loader**. Không dựa vào checksum của source JAR trước biến đổi để tuyên bố fat JAR mới đã được xác minh.

Nếu dependency có nhiều JAR, **mỗi JAR phải có artifact identity và digest**. Hash một file plugin không tự kiểm soát những thư viện bên ngoài mà nó sẽ nạp.

## 4. Chữ ký JAR: hợp lệ về mật mã chưa đủ “được tin”

Java JDK cung cấp `jarsigner` để ký và kiểm tra JAR. Với một JAR **có ký số**, có thể điều tra bằng:

~~~bash
jarsigner -verify -strict -verbose -certs approved/greeter-1.0.jar
~~~

Đây là lệnh tham khảo cho JAR có chữ ký và trust policy thực tế; JAR ví dụ ở phần 7 mặc định **chưa được ký**.

Cần kiểm tra **nhiều điều kiện**, không chỉ nhìn một dòng output:

- **Signature integrity:** dữ liệu và digest những entry được ký không bị thay; signature block xác minh đúng về mật mã.
- **Coverage:** mọi entry yêu cầu bảo vệ đã được ký chưa? Có entry bị thêm sau khi ký hoặc không được ký?
- **Signer identity:** certificate/public key có thuộc tổ chức publisher cho phép không? Có trust anchor/key pin thích hợp không?
- **Trust chain và thời hạn:** certificate chain, algorithm policy, key strength, timestamp và cảnh báo liên quan có thỏa quy tắc?
- **Artifact binding:** signer đã ký đúng version/digest và release channel được chấp nhận chưa?
- **Revocation/review:** có thông báo thu hồi hoặc incident liên quan signer/artifact không?

`-strict` có thể khiến cảnh báo nghiêm trọng ảnh hưởng exit status, nhưng lệnh kiểm tra và policy trust cần được thiết kế rõ. Một JAR **không được ký** không tự được approve chỉ vì tool không in lỗi tuyệt đối. Ngược lại, một chữ ký do bất kỳ certificate nào tạo cũng **không** đủ để mở quyền chạy.

**Đừng nhầm `new JarFile(file, true)` với một verifier toàn diện.** `JarFile` hỗ trợ verify chữ ký của các entry ký khi chúng được đọc. Nó không tự động đọc hết tất cả entry hoặc áp chính sách signer/trust của doanh nghiệp. Nếu muốn xác thực signer phải có một bước độc lập, đầy đủ và fail-closed.

| Cơ chế | Khả năng | Giới hạn |
| --- | --- | --- |
| SHA-256 + pin đáng tin | Khớp chính xác bytes đã duyệt | Không chứng minh code không có CVE, không xác nhận origin nếu pin không tin |
| Chữ ký JAR + trust policy | Ràng buộc chữ ký/entry với signer được phê duyệt | Không bao phủ dependency ngoài hay quyền runtime |
| Signed provenance | Bằng chứng đã xác minh về builder/source/release workflow | Không chứng minh mọi hành vi code là an toàn |
| SBOM + SCA | Inventory dependencies và phát hiện lỗ hổng đã biết | Có thể thiếu shaded/dynamic components; không thay checksum |
| Isolation/least privilege | Hạn chế tác động khi code chạy | Không tự chứng minh artifact nguyên vẹn |

## 5. Kiểm soát mọi dependency được phép

Một plugin có thể có đồ thị:

~~~text
com.acme:greeter-plugin:1.0.0
 ├─ com.acme:plugin-api:2.3.0
 ├─ org.example:parser:4.2.1
 │    └─ org.example:codec-core:1.8.0
 └─ org.example:logging:3.1.0
~~~

Nếu chỉ approve `greeter-plugin` và `parser`, phiên bản `codec-core` bắc cầu có thể vẫn được resolve và thực thi. **Policy phải bao phủ kết quả resolve cuối**, không chỉ khai báo direct dependency.

Các nguồn dependency cần quản lý:

1. **Build-time:** Maven/Gradle resolve POM, BOM, dependency substitutions, conflict resolutions và transitive graph.
2. **Runtime:** classpath/module path thực tế khi process chạy, bao gồm injected JAR ngoài kết quả build.
3. **Manifest:** thuộc tính `Class-Path` của JAR có thể mở rộng đường tìm class/resource của một `URLClassLoader`.
4. **Loader động:** `URLClassLoader.addURL`, custom loader, plugin resolver, `ModuleFinder`/`ModuleLayer`.
5. **Discovery:** `META-INF/services`, `ServiceLoader` hoặc framework reflection tạo provider triển khai.
6. **Code nhúng và native:** shaded/fat JAR, nested JAR, JNI, `System.load`/`System.loadLibrary` hoặc downloader tải mã trong runtime.

**Tên JAR không đủ làm dependency identity.** Cần version, coordinate, digest, source và scope tương ứng. Những thư viện shaded có thể không còn là JAR độc lập, nhưng vẫn cần inventory các component thực sự được đóng trong artifact.

### API chung giữa host và plugin

Host và plugin trao đổi object thông qua interface/DTO/exception type dùng chung. Với class/interface, **type identity = (binary name, defining class loader)**. Nếu plugin đóng gói và tự định nghĩa một bản `com.acme.api.Task` thay vì dùng định nghĩa API của host, host có thể gặp `ClassCastException` hoặc provider không hợp lệ dù cùng tên.

Một class loading policy thường có dạng:

~~~text
java.* / platform modules         → runtime/platform loaders
com.acme.api.*                    → shared/parent loader do host kiểm soát
plugin.impl.*                     → plugin loader đã phê duyệt
approved private dependencies     → loader plugin theo policy version
unknown packages/JAR providers    → reject hoặc lookup đã kiểm soát
~~~

Đây là **mô hình kiến trúc**, không phải behavior tự động của Java. Khi cần child-first cho implementation, vẫn phải bảo đảm parent-first cho API được chia sẻ. Ranh giới supply chain và type identity bổ sung cho nhau: JAR đúng hash nhưng nạp API sai loader vẫn có thể phá giao tiếp.

### Manifest Class-Path và dynamic lookup

`URLClassLoader` hỗ trợ các URL JAR, thư mục và cơ chế class/resource lookup. Một manifest có:

~~~text
Class-Path: lib/extra.jar
~~~

có thể đưa thêm dependency vào đường tra cứu của loader theo cách xử lý manifest của Java. Nếu hệ plugin không hỗ trợ kiểu mở rộng này, **từ chối JAR chứa thuộc tính `Class-Path`**; nếu hỗ trợ, resolve URL an toàn và verify **từng artifact phụ** trước khi nạp. Đừng tin rằng chỉ truyền một URL vào constructor là toàn bộ class loading graph chỉ có một file.

## 6. Quy trình phê duyệt từ build tới runtime

~~~text
Source + dependency policy được review
        |
        v
CI/toolchain/runner được kiểm soát
        |
        v
Resolve từ repository được phép
        |
        +-- pin direct/transitive versions
        +-- kiểm tra hashes/signers
        +-- SCA / license policy
        +-- SBOM / provenance metadata
        |
        v
Build artifact cuối
        |
        v
Promotion/approval, signed release manifest
        |
        v
Immutable artifact cache/staging
        |
        v
Check digest/signature + dependency closure
        |
        v
Instantiate ClassLoader / ModuleLayer
        |
        v
Runtime restrictions + audit + revocation
~~~

Các yếu tố quan trọng:

- **Reproducible build** giúp so sánh kết quả từ source và toolchain, nhưng vẫn phải kiểm soát build scripts và dependency artifacts.
- **SBOM** nên bao gồm thư viện direct, transitive, shaded hoặc bundled theo khả năng phân tích build và runtime. Nó có thể không thấy các dependency được nạp động.
- **SCA** nên liên tục kiểm tra advisory/CVE và chính sách sử dụng; lỗ hổng mới có thể khiến một artifact đã duyệt phải bị thu hồi.
- **Provenance/attestation** cần xác minh trust root, builder/publisher identity và artifact digest; không tin chỉ vì có tệp tên `provenance.json`.
- **Phê duyệt runtime** phải đối chiếu đúng bytes đã được đặt vào production, không chỉ lời khai rằng CI từng kiểm tra một bản tương tự.

Khi gate từ chối JAR, không được im lặng tìm bản khác ở public registry. Đó là đường đi phổ biến khiến **dependency confusion** hoặc downgrade.

## 7. Java 17 runnable: kiểm tra JAR trước URLClassLoader

Ví dụ học tập có các chính sách cụ thể:

- Chỉ nhận file `greeter-1.0.jar` trong thư mục `approved`.
- Canonicalize đường dẫn và xác nhận đúng vị trí.
- Stream toàn file để tính SHA-256, so với pin hex 64 ký tự do caller cung cấp.
- Từ chối manifest có `Class-Path`.
- Chỉ khi các điều kiện trên đều đạt mới tạo `URLClassLoader` và gọi class `plugin.Greeter`.
- Không có dependency ngoài `java.base`, vì vậy parent `ClassLoader.getPlatformClassLoader()` đủ cho mục tiêu demo.

**Giới hạn:** Chương trình chưa xác thực certificate/trusted signer, chưa validate transitive graph và chưa chống TOCTOU nếu thư mục có writer không tin cậy. Nó **không** tạo sandbox hoặc bảo vệ trước một plugin vốn đã độc hại. Đây là ví dụ về **thứ tự kiểm tra trước khi tải class**, không phải một trình quản lý supply chain production đầy đủ.

Cấu trúc file:

~~~text
jar-gate-demo/
├── JarGate.java
├── src/
│   └── plugin/
│       └── Greeter.java
├── classes/                     (thư mục output)
└── approved/
    └── greeter-1.0.jar          (JAR được tạo ở bước build)
~~~

### File 1: src/plugin/Greeter.java

~~~java
package plugin;

public final class Greeter {
    public static String message() {
        return "hello from pinned JAR";
    }
}
~~~

### File 2: JarGate.java

~~~java
import java.io.InputStream;
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Files;
import java.nio.file.LinkOption;
import java.nio.file.Path;
import java.security.MessageDigest;
import java.util.HexFormat;
import java.util.jar.Attributes;
import java.util.jar.JarFile;
import java.util.jar.Manifest;

public final class JarGate {
    private static final String APPROVED_FILE = "greeter-1.0.jar";

    private static byte[] sha256(Path file) throws Exception {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        try (InputStream input = Files.newInputStream(file)) {
            byte[] buffer = new byte[8192];
            int count;
            while ((count = input.read(buffer)) != -1) {
                digest.update(buffer, 0, count);
            }
        }
        return digest.digest();
    }

    private static void checkManifest(Path jar) throws Exception {
        try (JarFile file = new JarFile(jar.toFile())) {
            Manifest manifest = file.getManifest();
            if (manifest != null && manifest.getMainAttributes()
                    .getValue(Attributes.Name.CLASS_PATH) != null) {
                throw new SecurityException("manifest Class-Path not allowed");
            }
        }
    }

    private static void run(Path approvedDir, Path input,
                            String expectedHex) throws Exception {
        if (!expectedHex.matches("[0-9a-fA-F]{64}")) {
            throw new SecurityException("invalid pinned SHA-256");
        }

        Path root = approvedDir.toRealPath();
        Path jar = input.toRealPath();

        if (!Files.isRegularFile(jar, LinkOption.NOFOLLOW_LINKS)
                || !jar.startsWith(root)
                || !jar.getFileName().toString().equals(APPROVED_FILE)) {
            throw new SecurityException("source not allowlisted");
        }

        byte[] pinned = HexFormat.of().parseHex(expectedHex);
        byte[] actual = sha256(jar);
        if (!MessageDigest.isEqual(actual, pinned)) {
            throw new SecurityException("SHA-256 mismatch");
        }

        checkManifest(jar);
        System.out.println("Approved source: true");
        System.out.println("SHA-256 matches: true");
        System.out.println("Manifest Class-Path absent: true");

        try (URLClassLoader pluginLoader = new URLClassLoader(
                new URL[] { jar.toUri().toURL() },
                ClassLoader.getPlatformClassLoader())) {

            Class<?> plugin = Class.forName(
                    "plugin.Greeter", true, pluginLoader);

            System.out.println("Plugin result: "
                    + plugin.getMethod("message").invoke(null));
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 3) {
            System.out.println("Usage: java JarGate <dir> <jar> <sha256>");
            return;
        }

        try {
            run(Path.of(args[0]), Path.of(args[1]), args[2]);
        } catch (SecurityException denied) {
            System.out.println("DENIED: " + denied.getMessage());
        }
    }
}
~~~

**Chương trình đã được kiểm thử** trên OpenJDK với flag `--release 17`: một JAR hợp lệ được chấp nhận, còn pin hash sai bị từ chối. Dưới đây là cách tự chạy.

### Build project

Tạo thư mục output trước:

~~~bash
mkdir -p classes approved
javac --release 17 -d classes src/plugin/Greeter.java
jar --create --file approved/greeter-1.0.jar -C classes .
javac --release 17 JarGate.java
~~~

Khối trên dùng Bash/Linux/macOS. Trên Windows PowerShell, tạo thư mục bằng lệnh tương đương:

~~~powershell
New-Item -ItemType Directory -Force classes, approved | Out-Null
javac --release 17 -d classes src/plugin/Greeter.java
jar --create --file approved/greeter-1.0.jar -C classes .
javac --release 17 JarGate.java
~~~

### Trường hợp được chấp nhận

**Chỉ cho demo local**, tính pin từ JAR mà người học vừa tự build:

~~~powershell
$expected = (Get-FileHash .\approved\greeter-1.0.jar -Algorithm SHA256).Hash
java JarGate approved approved/greeter-1.0.jar $expected
~~~

Hoặc trên Bash:

~~~bash
expected=$(sha256sum approved/greeter-1.0.jar | cut -d' ' -f1)
java JarGate approved approved/greeter-1.0.jar "$expected"
~~~

**Stdout của lệnh Java:**

~~~text
Approved source: true
SHA-256 matches: true
Manifest Class-Path absent: true
Plugin result: hello from pinned JAR
~~~

**Cảnh báo:** Bước tính `$expected` hoặc `expected=$(sha256sum ...)` **chỉ phù hợp cho bài thực hành** khi tự build từ source đáng tin. Trong production không được lấy hash kỳ vọng từ **chính artifact chưa tin cậy**, rồi tuyên bố artifact đã được chứng thực. Giá trị `expectedHex` phải đến từ trusted release manifest / signed policy / pinned configuration độc lập.

### Trường hợp SHA-256 không khớp

Trên PowerShell:

~~~powershell
$wrong = '0' * 64
java JarGate approved approved/greeter-1.0.jar $wrong
~~~

**Stdout:**

~~~text
DENIED: SHA-256 mismatch
~~~

Không có `URLClassLoader` nào được tạo ở nhánh bị từ chối đó. Nếu đầu vào thuộc root không hợp lệ hoặc tên JAR không nằm trong allowlist, chương trình in `DENIED: source not allowlisted` sau khi path đã resolve thành công.

### Vì sao ví dụ kiểm tra trước Class.forName?

`Class.forName("plugin.Greeter", true, pluginLoader)` yêu cầu **load và initialize** class. Static initializer của code plugin (nếu có) có thể thực thi mã. Do đó gate phải thành công **trước khi tạo/tra cứu class plugin và trước khi kích hoạt initialization**, chứ không thể “load thử xem có an toàn không” rồi mới hash.

### Đọc code theo từng lớp kiểm soát

1. `Path.toRealPath` và `Path.startsWith(Path)` xác nhận canonical location trong thư mục đã duyệt. Tên JAR được so bằng exact equality.
2. `sha256` dùng `InputStream` và `MessageDigest` theo chunks nên không phải load toàn bộ JAR vào byte array chỉ để hash.
3. `HexFormat.of().parseHex` (Java 17) chuyển pin hex 64 ký tự thành 32 byte.
4. `MessageDigest.isEqual` so sánh digest thực với pin kỳ vọng.
5. `JarFile` kiểm tra manifest. Nếu có `Class-Path` thì từ chối để tránh một đường mở rộng URL dependency **trong thiết kế demo**.
6. `URLClassLoader` chỉ có một URL JAR được duyệt. `getPlatformClassLoader` là parent phù hợp cho ví dụ plugin độc lập; plugin host thật có thể cần một **shared API parent loader** khác.
7. `Class.forName` khiến class của JAR được load/initialize sau gate. Method `message()` trả kết quả cố định.
8. `try-with-resources` đóng URLClassLoader sau khi dùng. Điều này không bảo đảm unload tất cả class lập tức.

**Không suy rộng:** Tên file allowlist và SHA-256 của riêng JAR không đủ kiểm soát mọi dependency, vì code vẫn có thể truy cập những class do parent định nghĩa, thao tác file, mạng, native library hay loader khác. Đó là ranh giới của ví dụ.

## 8. Vấn đề TOCTOU và staging artifact

Một lỗi thiết kế tinh vi:

~~~text
T1: verifier mở file /approved/greeter.jar, hash khớp
T2: process khác thay /approved/greeter.jar
T3: URLClassLoader mở file theo path
T4: JVM nạp bytes khác với bản verifier kiểm tra
~~~

`toRealPath()` không chặn việc thay file. Một file có digest đúng ở thời điểm kiểm tra vẫn có thể bị thay bởi writer có quyền sau đó.

Các biện pháp thường cần trong hệ thống thực:

- Chỉ cho pipeline/artifact manager đáng tin **ghi** vào staged artifact directory; runtime chỉ **đọc**.
- Đặt file ở đường dẫn theo **content digest** và bảo vệ quyền thay/ghi, thay vì một tên JAR chung có thể bị overwrite.
- Download sang file tạm dưới quyền kiểm soát, xác minh đầy đủ, rồi **promote** sang kho release chỉ đọc theo thao tác atomic và policy ownership phù hợp.
- Đảm bảo class loader đọc đúng file staged đã xác minh, không tự lấy lại từ URL khác khi runtime.
- Re-verify lúc deployment/startup theo threat model; không dùng một bản allowlist không được bảo vệ.
- Audit digest của bản thật đã loaded và xử lý quy trình thu hồi khi phát hiện bản sai.

Không có **một lời gọi Java Path API đơn lẻ** nào tự mang tới end-to-end assurance nếu attacker vẫn có quyền sửa file hoặc thay artifact repository.

## 9. Maven: direct và transitive dependency

Với Maven, `pom.xml` có dependencies và `dependencyManagement`/BOM; Maven giải quyết graph dựa trên profiles, scopes, repositories và policies. Nên:

1. Pin versions bằng release manifest và tránh version ranges hoặc SNAPSHOT không kiểm soát trong production.
2. Quản lý artifact qua mirror/internal registry có namespace mapping, quyền publish rõ ràng.
3. Kiểm tra toàn bộ graph đã resolve:

~~~bash
mvn dependency:tree
~~~

Lệnh trên cần môi trường Maven và Maven Dependency Plugin tương ứng; output phụ thuộc project nên không có stdout cố định.

4. Áp dụng policy như Maven Enforcer `bannedDependencies`, `dependencyConvergence` hoặc `requireUpperBoundDeps` khi phù hợp để ngăn tọa độ/phiên bản xung đột hoặc bị cấm.
5. Phát hành resolved artifact list kèm versions, source repositories và hashes như một phần release manifest đã ký/phê duyệt.
6. Chạy SCA và license policy liên tục, review dependency changes qua pull request.

**BOM không tự là lockfile hash của toàn bộ artifact graph.** BOM giúp quản lý phiên bản nhưng không bảo đảm mọi dependency đã được pin, verify theo digest và từ đúng nguồn. Bản deploy phải đối chiếu **graph thực** và artifact bytes cuối.

Cũng đừng nhầm graph Maven với toàn bộ runtime nếu ứng dụng dùng server-injected libraries, `ModuleLayer` nạp động hoặc plugin manager bổ sung JAR sau build.

## 10. Gradle: lock phiên bản khác verify bytes

Gradle cung cấp hai nhóm tính năng khác nhau:

- **Dependency locking:** khóa các phiên bản đã resolved, tránh thay đổi không kiểm soát.
- **Dependency verification:** đối chiếu checksum/chữ ký artifact với verification metadata được quản lý.
- **Repository content filters/exclusive content:** giới hạn artifact coordinate có thể đến từ repository nào.

Một fragment Kotlin DSL ví dụ:

~~~kotlin
dependencyLocking {
    lockAllConfigurations()
}
~~~

Đây là **cấu hình minh họa**, không phải tệp Gradle build hoàn chỉnh. Để thực sự khóa, cần tạo và review lock state, bảo quản lockfiles trong version control và áp dụng đúng configurations.

Xem một resolved runtime graph phù hợp:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
~~~

Tên configuration có thể khác tùy plugin (Android, multi-project, custom runtime), nên phải chọn đúng graph được deploy. Bật locking mà không quản lý actual runtime configuration không bảo vệ toàn bộ artifact nạp sau này.

**Verification metadata phải được review**, đặc biệt khi tạo lần đầu hoặc khi dependency thay đổi. Nếu cho tool tự thêm hash của artifact tải từ nguồn bị đầu độc mà không có bước xác thực publisher/provenance độc lập, hệ thống chỉ khóa **bytes độc hại**.

~~~text
Repository policy   → artifact được lấy từ đâu?
Lockfile            → version nào được resolve?
Verification        → bytes/signatures nào được chấp nhận?
SCA/SBOM            → component nào và rủi ro đã biết nào?
Runtime loader gate → artifact cuối thực sự được nạp là bản nào?
~~~

Mỗi câu hỏi phải có câu trả lời riêng và bằng chứng kiểm thử.

## 11. SCA, SBOM, provenance và revocation

**SBOM (Software Bill of Materials)** cung cấp danh sách các thành phần của một bản phát hành. Nó hữu ích cho inventory, ứng phó CVE và truy ra transitive dependencies. Khi có fat JAR/shading, cần bảo đảm các thành phần nhúng vẫn được ghi nhận; khi runtime nạp JAR khác ngoài build, cần bổ sung nguồn inventory runtime.

**SCA (Software Composition Analysis)** so danh sách dependency với cơ sở dữ liệu advisory, phiên bản bị ảnh hưởng và chính sách tổ chức. Quét có thể có false positive/false negative, và CVE mới xuất hiện sau lúc release; vì vậy phải giám sát liên tục, không chỉ scan một lần.

**Provenance/attestation** có thể xác nhận claim về source, toolchain, builder, workflow và artifact digest. Nhưng validator phải kiểm tra **trust root, signer/builder identity, claim constraints và digest**, không chỉ parse một JSON tên `provenance`.

**Revocation:** Artifact từng đạt SHA-256 và chữ ký vẫn có thể bị thu hồi sau incident hoặc phát hiện lỗ hổng. Allowlist phải có cơ chế cập nhật và audit: ai gỡ pin, vì sao, deployment nào bị ảnh hưởng, cách rollback/patch ra sao.

Một chính sách mạnh sẽ tự động từ chối bản bị revoked, kể cả khi bytes còn khớp pin cũ — bởi vì **“bytes đúng” không đồng nghĩa “được phép hôm nay”**.

## 12. ClassLoader, ServiceLoader, ModuleLayer có kiểm tra trust không?

**URLClassLoader** tìm class/resource theo URLs và parent delegation. Nó không biết policy doanh nghiệp về nguồn JAR, signer hoặc artifact version. `loader.getURLs()` cũng không trình bày toàn bộ class có thể nhận từ parent hay những nguồn code động khác.

**ServiceLoader** tìm provider đã đăng ký ở `META-INF/services` hoặc `provides ... with ...` trong named module. Metadata có thể khiến framework instantiate code của provider. Phải xác nhận service contract thuộc API được phê duyệt, provider class từ artifact/loader được duyệt, và TCCL không vô tình chỉ về plugin cũ.

**ModuleLayer** cho phép định nghĩa dynamic named modules theo module graph. `ModuleFinder`, `Configuration.resolve` và `defineModules...` thực hiện module resolution/definition, **không tự thực thi allowlist publisher, integrity pin hay security sandbox**.

**CodeSource/ProtectionDomain** có thể giúp debug class đã nạp từ URL nào:

~~~java
Class<?> type = /* một Class<?> đã có */;
var domain = type.getProtectionDomain();
var source = domain == null ? null : domain.getCodeSource();

System.out.println(source == null
        ? "(unknown)"
        : source.getLocation());
~~~

Đây là **fragment**, chưa phải chương trình độc lập. `CodeSource` hữu ích cho quan sát nhưng không phải certificate of trust; custom loader có thể gán metadata không phản ánh toàn bộ lịch sử supply chain. Bootstrap classes và class sinh động có thể không có URL vật lý rõ ràng.

**Không dùng ClassLoader như security sandbox.** Class loader tổ chức namespace/type identity/lookup. Plugin bị coi là không tin cậy nên chạy trong **process/container cô lập** nếu cần ngăn truy cập secrets, filesystem, network, native code hoặc OS resources. Quyền OS, network policy, resource limits và monitoring là những lớp riêng.

## 13. Các phản ví dụ cần tránh

**“JAR có HTTPS download thành công nên được tin.”** Chưa chắc. TLS bảo vệ kết nối, không xác nhận build/publisher không bị compromise.

**“Hash của JAR và hash trong file cạnh nó khớp nên an toàn.”** Chưa chắc. Nếu cả hai từ nguồn bị kiểm soát, attacker có thể thay cả hai.

**“jarsigner verify thành công nên người ký được phép.”** Không đủ. Phải validate signer/trust/coverage và policy; chữ ký hợp lệ không tự bảo đảm code không độc hại.

**“Khớp SHA-256 nghĩa không có CVE.”** Sai. Digest chỉ ràng buộc bytes với bản được pin.

**“Chỉ cần allowlist dependency trực tiếp.”** Sai. Phải review **full closure** gồm transitive, shaded, runtime JARs và những cơ chế nạp động liên quan.

**“Một URLClassLoader có một URL sẽ chỉ dùng một JAR.”** Không bảo đảm vì parent, manifest `Class-Path`, module/service lookup và runtime loading khác.

**“Có Maven BOM là mọi bytes đã khóa.”** Sai. BOM quản lý versions, không tự pin toàn bộ binary artifacts và nguồn phát hành.

**“Tôi có thể sửa lỗi bằng cách fallback sang repository public khác khi SHA mismatch.”** Sai. Làm vậy phá fail-closed và tạo cơ hội dependency confusion/downgrade.

**“JAR được phê duyệt là an toàn để chạy ngay trong host process.”** Không. Một artifact đúng nguồn vẫn có thể có lỗi, quyền vượt mức hoặc bị khai thác; cần runtime isolation/monitoring theo threat model.

**“Chỉ canonicalize path là chống sửa file sau kiểm tra.”** Không. TOCTOU vẫn tồn tại nếu writer chưa tin cậy có thể thay bytes trước khi loader đọc.

## 14. Checklist trước khi nạp plugin JAR

1. Xác định **threat model**: plugin có tin cậy như host không? Nếu không, cần isolation ngoài class loader.
2. Allowlist **publisher/repository/group/artifact/version** và chặn namespace confusion.
3. Có release manifest **đã ký/phê duyệt** ràng buộc digest và dependency graph.
4. Tính SHA-256 trên **bản artifact cuối** và so với **pin độc lập/trusted**.
5. Nếu policy yêu cầu signer, validate chữ ký, trust chain, identity và entry coverage.
6. Review các dependencies **trực tiếp, bắc cầu, runtime, shaded và native** cùng versions/digests/sources.
7. Quét **SCA**, so SBOM và xử lý vulnerability/license policy.
8. Kiểm soát manifest `Class-Path`, loader URL expansion, TCCL/SPI và dynamic module loading.
9. Stage artifact **bất biến/chỉ đọc**, có quyền filesystem và ownership phù hợp; ngăn TOCTOU.
10. Chỉ sau đó mới tạo loader/module layer và chạy plugin; bảo toàn shared API class identity.
11. Ghi audit artifact ID, digest, nguồn, signer, policy version, quyết định allow/deny và thời gian.
12. Có kế hoạch update/revoke/rollback, shutdown plugin threads, cleanup TCCL và loader references.

## 15. Câu hỏi tự kiểm tra

**Câu 1.** Một server phát cả `plugin.jar` lẫn `plugin.jar.sha256` và hai file khớp nhau. Đã chứng minh nguồn publisher đúng chưa?

**Đáp án:** Chưa. Cả hai có thể bị thay cùng lúc. Hash pin phải đến từ trusted source độc lập/signed metadata.

**Câu 2.** Vì sao phải allowlist transitive dependencies chứ không chỉ direct?

**Đáp án:** Runtime có thể nạp code từ toàn bộ resolved graph. Một transitive artifact không được duyệt vẫn có thể thực thi.

**Câu 3.** JAR ký số hợp lệ nhưng signer không nằm trong policy. Cho chạy không?

**Đáp án:** Không. Chữ ký mật mã hợp lệ không tự đồng nghĩa publisher được cho phép.

**Câu 4.** JAR hash đúng nhưng chứa `Class-Path: lib/extra.jar`. Chắc chắn chỉ dùng JAR đầu không?

**Đáp án:** Không. Manifest có thể mở rộng đường tìm class/resource. Phải approve JAR phụ hoặc từ chối cơ chế Class-Path.

**Câu 5.** `Path.toRealPath` kiểm tra trước `URLClassLoader` có ngăn file bị thay trước lúc loader đọc không?

**Đáp án:** Không. Cần staging immutable và quyền ghi được kiểm soát để xử lý TOCTOU.

**Câu 6.** Một plugin đã qua gate có thể tải native library hoặc gọi network API không?

**Đáp án:** Nếu process có quyền, có thể. Class loader không phải sandbox; cần OS/process isolation và network restrictions.

**Câu 7.** Maven BOM/Gradle lockfile có bảo đảm mọi artifact có SHA-256 đúng policy không?

**Đáp án:** Không tự động. Lock version và verification hash/signature là các lớp kiểm soát khác nhau.

**Câu 8.** Vì sao phải duy trì revocation dù digest JAR không đổi?

**Đáp án:** Bản bytes từng được phê duyệt có thể bị phát hiện backdoor/CVE hoặc publisher compromise về sau. “Khớp pin” không đồng nghĩa luôn còn được phép.

## Ghi nhớ

**Nguồn hợp lệ, bytes khớp pin và dependency graph được phép là ba điều kiện độc lập.** Trước `URLClassLoader`/`ServiceLoader`/dynamic `ModuleLayer`, hãy kiểm tra artifact từ repository/publisher đã phê duyệt, SHA-256 từ trusted metadata, signer khi cần, toàn bộ transitive/runtime dependencies và staged bytes cuối. **Không tự pin hash từ chính JAR chưa tin**, không xem chữ ký là bằng chứng code vô hại và không xem class loader là sandbox. Khi có nghi ngờ, **fail closed**, audit và dùng runtime isolation phù hợp.

# Tránh lấy tên lớp hoặc đường dẫn tùy ý từ dữ liệu không tin cậy

## 1. Vấn đề và nguyên tắc an toàn

Một ứng dụng Java có plugin, ClassLoader, reflection hoặc xử lý file có thể nhận chuỗi từ HTTP request, tenant configuration, queue message hay metadata bên thứ ba. Chuỗi ấy trông vô hại khi còn là dữ liệu, nhưng trở thành **quyết định có quyền hạn** nếu chuyển trực tiếp vào `Class.forName`, `ClassLoader.loadClass`, `Files.readString`, `getResourceAsStream` hay `URLClassLoader`.

~~~java
// PHẢN VÍ DỤ: chỉ minh họa, không phải chương trình độc lập.
String className = request.getParameter("class");
Object plugin = Class.forName(className)
        .getConstructor().newInstance();

String path = request.getParameter("file");
String content = Files.readString(Path.of(path));
~~~

Đầu vào bên ngoài lúc này có thể chọn class để khởi tạo hoặc file để đọc, ngoài dự kiến nghiệp vụ. Java vẫn thực thi các quy tắc class loading và Java access control; tuy nhiên **khả năng tìm được class/file không tự chứng minh caller có quyền sử dụng nó**.

**Nguyên tắc:** Client chọn **mã chức năng hay ID tài nguyên đã cấp phép**, còn host quản lý ánh xạ đến implementation, ClassLoader, JAR, resource và đường dẫn thực.

Ví dụ tốt hơn:

~~~text
Client chọn "health" ──> AuthZ ──> Factory HealthJob đã đăng ký
Client chọn "guide"  ──> AuthZ ──> docs/guide.txt từ trusted registry
Client gửi FQCN hoặc ../../secret ──> từ chối
~~~

Chỉ kiểm tra cú pháp tên class, tên file hoặc regex **chưa phải** kiểm tra quyền nghiệp vụ.

## 2. Những đầu vào cần cảnh giác

| Input không tin cậy | API nhận input | Vấn đề |
|---|---|---|
| Tên binary class như `demo.plugin.Report` | `Class.forName(name)` | Input quyết định class được yêu cầu initialize |
| Tên class từ cấu hình ngoài | `loader.loadClass(name)` | Input quyết định class mà loader tìm |
| Tên provider | Reflection, dependency injection, `ServiceLoader` | Có thể khởi tạo code implementation không được phê duyệt |
| Resource name | `getResource` / `getResourceAsStream` | Đọc/tiết lộ resource nội bộ |
| File path | `Path.of(input)` và `Files.readString` | Path traversal, absolute path, symlink |
| URL nguồn class | `new URLClassLoader(urls, parent)` | Nạp bytecode từ artifact không đáng tin |
| URL cần mở | `URL.openStream()` | Truy cập nguồn bất ngờ/SSRF nếu ứng dụng cho phép |
| ZIP/JAR entry name | Giải nén file | Zip Slip, ghi file ngoài thư mục dự kiến |

Không phải các API trên tự nhiên có lỗ hổng; rủi ro là ứng dụng **trao quyền chọn đích cho untrusted input** mà thiếu kiểm soát nguồn và authorization.

## 3. Chọn chức năng qua allowlist, không qua FQCN

Thay vì cho user gửi `"java.lang.Runtime"`, `"demo.admin.ResetAll"` hoặc tên class bất kỳ, API nên chỉ nhận các **token đã định nghĩa** như `"health"` và `"version"`.

~~~java
// Mã minh họa, cần Job/HealthJob/VersionJob và các import.
Map<String, Supplier<Job>> allowed = Map.of(
        "health", HealthJob::new,
        "version", VersionJob::new
);
Supplier<Job> factory = allowed.get(userKey);
if (factory == null) {
    throw new IllegalArgumentException("Unsupported operation");
}
Job selected = factory.get();
~~~

Điểm an toàn đến từ **nguồn điều khiển map**: nếu client có thể gửi cả `key` lẫn FQCN rồi tự đăng ký entry mới, bảng này không còn là allowlist do host kiểm soát.

Đừng chỉ blacklist vài tên class nhạy cảm hoặc kiểm tra rằng một tên nằm dưới prefix `com.mycompany.plugins`. Một JAR không đáng tin có thể tự khai báo class cùng package đó. Nguồn bytecode, quyền đăng ký implementation và quyền chọn chức năng đều phải được kiểm soát.

Ngoài allowlist, vẫn cần AuthN/AuthZ: người dùng chỉ được thực thi các chức năng mà vai trò/tenant/scope của họ cho phép.

## 4. Chọn tài liệu qua key, không nhận raw path

Một endpoint tài liệu nên nhận `"guide"` hoặc `"rules"` thay vì `"docs/guide.txt"` hay `"../../config/secret.txt"` từ client.

~~~java
// Mã minh họa.
Map<String, String> documents = Map.of(
        "guide", "docs/guide.txt",
        "rules", "docs/rules.txt"
);
String allowedPath = documents.get(documentKey);
if (allowedPath == null) {
    throw new IllegalArgumentException("Unknown document");
}
~~~

Đường dẫn vật lý nằm trong config/registry chỉ host được quyền sửa. Nếu tài liệu chứa dữ liệu theo tenant, còn phải xác minh ID tài liệu thuộc tenant đã được xác thực. **Không nhận tenant ID từ query string mà không kiểm tra quyền**.

Ngay cả khi path đến từ allowlist, việc đọc vẫn nên kiểm soát root, symlink, loại file, dung lượng và vòng đời tài nguyên, nhất là khi nhiều bên có thể sửa filesystem.

## 5. Chương trình Java 17+ đầy đủ: factory và resource an toàn

Ví dụ độc lập sau tạo hai tác vụ, hai file trong thư mục tạm, kiểm tra token không hợp lệ và từ chối path traversal. Chương trình không dùng class name nhận từ client để nạp bytecode.

Tạo file **`SafeSelectionDemo.java`**:

~~~java
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.InvalidPathException;
import java.nio.file.Path;
import java.util.Map;
import java.util.function.Supplier;

public final class SafeSelectionDemo {
    private SafeSelectionDemo() {
    }

    interface Job {
        String run();
    }

    static final class HealthJob implements Job {
        @Override
        public String run() {
            return "HEALTH_OK";
        }
    }

    static final class VersionJob implements Job {
        @Override
        public String run() {
            return "VERSION_1";
        }
    }

    private static final Map<String, Supplier<Job>> JOBS = Map.of(
            "health", HealthJob::new,
            "version", VersionJob::new
    );

    private static final Map<String, String> DOCS = Map.of(
            "guide", "docs/guide.txt",
            "rules", "docs/rules.txt"
    );

    static Job selectJob(String key) {
        Supplier<Job> factory = JOBS.get(key);
        if (factory == null) {
            throw new IllegalArgumentException("Unknown job");
        }
        return factory.get();
    }

    static String selectDocument(Path root, String key)
            throws IOException {
        String relative = DOCS.get(key);
        if (relative == null) {
            throw new IllegalArgumentException("Unknown document");
        }
        return readConfinedFile(root, relative);
    }

    // Defense in depth, không chống tuyệt đối filesystem races.
    static String readConfinedFile(Path root, String input)
            throws IOException {
        if (input == null || input.isBlank()) {
            throw new SecurityException("Empty path");
        }

        final Path relative;
        try {
            relative = Path.of(input);
        } catch (InvalidPathException ex) {
            throw new SecurityException("Invalid path", ex);
        }

        if (relative.isAbsolute()) {
            throw new SecurityException("Absolute path denied");
        }

        Path base = root.toRealPath();
        Path candidate = base.resolve(relative).normalize();

        if (!candidate.startsWith(base)) {
            throw new SecurityException("Path escapes root");
        }

        Path step = base;
        for (Path part : base.relativize(candidate)) {
            step = step.resolve(part);
            if (Files.isSymbolicLink(step)) {
                throw new SecurityException("Symlink denied");
            }
        }

        Path real = candidate.toRealPath();
        if (!real.startsWith(base) || !Files.isRegularFile(real)) {
            throw new SecurityException("Not a confined regular file");
        }

        return Files.readString(real, StandardCharsets.UTF_8).strip();
    }

    public static void main(String[] args) throws Exception {
        Path root = Files.createTempDirectory("safe-selection-");
        Path docs = root.resolve("docs");
        Path guide = docs.resolve("guide.txt");
        Path rules = docs.resolve("rules.txt");

        try {
            Files.createDirectories(docs);
            Files.writeString(guide, "GUIDE_OK\n",
                    StandardCharsets.UTF_8);
            Files.writeString(rules, "RULES_OK\n",
                    StandardCharsets.UTF_8);

            System.out.println("job health: "
                    + selectJob("health").run());
            System.out.println("job version: "
                    + selectJob("version").run());

            boolean classDenied = false;
            try {
                selectJob("java.lang.Runtime");
            } catch (IllegalArgumentException expected) {
                classDenied = true;
            }
            System.out.println("arbitrary class rejected: "
                    + classDenied);

            System.out.println("document guide: "
                    + selectDocument(root, "guide"));
            System.out.println("document rules: "
                    + selectDocument(root, "rules"));

            boolean documentDenied = false;
            try {
                selectDocument(root, "../secret");
            } catch (IllegalArgumentException expected) {
                documentDenied = true;
            }
            System.out.println("unknown document rejected: "
                    + documentDenied);

            boolean traversalDenied = false;
            try {
                readConfinedFile(root, "../private.txt");
            } catch (SecurityException expected) {
                traversalDenied = true;
            }
            System.out.println("path traversal rejected: "
                    + traversalDenied);
        } finally {
            Files.deleteIfExists(guide);
            Files.deleteIfExists(rules);
            Files.deleteIfExists(docs);
            Files.deleteIfExists(root);
        }
    }
}
~~~

### Biên dịch và chạy

Dùng **JDK 17 trở lên**; mở terminal tại thư mục chứa file:

~~~bash
javac -encoding UTF-8 SafeSelectionDemo.java
java SafeSelectionDemo
~~~

Hai lệnh chạy trên Bash, PowerShell và Command Prompt khi JDK nằm trong `PATH`. Không cần thư viện ngoài.

**Stdout:**

~~~text
job health: HEALTH_OK
job version: VERSION_1
arbitrary class rejected: true
document guide: GUIDE_OK
document rules: RULES_OK
unknown document rejected: true
path traversal rejected: true
~~~

**Giải thích:** Hai factory được chọn qua key; `"java.lang.Runtime"` bị từ chối như một key không hợp lệ chứ không được truyền vào reflection. Tương tự, `"../secret"` không thuộc danh sách tài liệu; đoạn thử trực tiếp `readConfinedFile(root, "../private.txt")` phát hiện candidate thoát root sau chuẩn hóa và từ chối. Chương trình tạo/xóa dữ liệu thử trong thư mục tạm, không in đường dẫn phụ thuộc máy.

Ví dụ có chủ đích **không** nhận input thực từ mạng; nó tái hiện các giá trị caller có thể gửi để kiểm tra hành vi. Hàm path checking minh họa **một lớp bảo vệ bổ sung**, chưa phải giải pháp atomic chống thao túng filesystem đồng thời.

## 6. Vì sao normalize + startsWith chưa đủ?

Một cách kiểm tra hay thấy:

~~~java
// Minh họa: root và relative đã được cấu hình.
Path base = root.toAbsolutePath().normalize();
Path file = base.resolve(relative).normalize();

if (!file.startsWith(base)) {
    throw new SecurityException("Outside resource root");
}
~~~

Nó giúp từ chối path chứa `../` mà sau normalize thoát root, nhưng không giải quyết mọi tình huống:

- **Symlink:** `base/docs/link` có thể trỏ tới file/thư mục ngoài root; đường cú pháp vẫn có thể bắt đầu bằng `base`.
- **TOCTOU:** Giữa bước `Files.isSymbolicLink`/`toRealPath` và `Files.readString`, entry trên filesystem có thể bị thay.
- **Filesystem aliases:** Hard link, mount points, Windows drive/UNC path và case sensitivity có thể ảnh hưởng cách hiểu root.
- **Root bị attacker ghi:** Nếu adversary kiểm soát directory tree, họ có thể thay tên/entry ngay cả sau khi validation hoàn tất.

Demo gọi `toRealPath()`, từ chối symlink trong các thành phần dưới root và kiểm tra lại real path. Đây là **defense in depth**, không phải bảo đảm mạnh trước TOCTOU.

Đối với production, tốt nhất là **không cho untrusted caller kiểm soát filesystem root**. Nếu cần chống race trong directory được phép thay đổi, cân nhắc `SecureDirectoryStream` khi filesystem provider hỗ trợ hoặc cơ chế file descriptor/directory handle của OS. Có thể áp dụng process/container isolation với quyền chỉ đọc/ghi đúng thư mục đã cấp.

## 7. Những dạng path cần nhận diện

| Input | Vấn đề |
|---|---|
| `../secrets/data.txt` | Parent traversal |
| `/etc/passwd` | Absolute path Unix |
| `C:\Windows\...` | Drive path trên Windows |
| `\\server\share\...` | UNC network path |
| `docs/link/private.txt` | Symlink có thể thoát root |
| `%2e%2e%2fsecret` | Encoding của traversal nếu protocol decode |
| `..%252fsecret` | Double decoding giữa các tầng |
| `../../target.txt` trong ZIP | Zip Slip khi giải nén |

Không nên sửa bằng blacklist các chuỗi `..`, `%2e`, dấu `/` đơn thuần: cách decode, separators và Unicode normalization có thể thay đổi giữa các tầng. Decode ở đúng protocol boundary, validate **giá trị thực tế đưa vào filesystem**, ưu tiên chỉ nhận một ID nghiệp vụ thay vì path.

Nếu giải nén JAR/ZIP do người ngoài cung cấp, hãy kiểm soát mỗi destination theo root và xử lý symlink/overwrite đúng trước khi ghi file. Không ghép `entry.getName()` thẳng với target directory mà không kiểm soát.

## 8. ClassLoader resource visibility khác quyền người dùng

`ClassLoader.getResource(name)` tìm URL; `getResourceAsStream(name)` mở stream; `getResources(name)` có thể liệt kê nhiều resources cùng tên. Đây là **lookup API**, không phải phương thức authorization cho người dùng cuối.

~~~java
// Minh họa: cần InputStream và một biến loader hợp lệ.
try (InputStream input =
             loader.getResourceAsStream("internal/settings.json")) {
    // Có stream không có nghĩa được trả nội dung cho mọi HTTP caller.
}
~~~

Một loader có thể nhìn thấy resource nội bộ nhưng client **không có quyền** xem nó. Nếu bạn chuyển trực tiếp input `"internal/settings.json"` từ request vào `getResourceAsStream` và trả bytes ra ngoài, bạn có thể tạo đường tiết lộ dữ liệu.

Cũng cần nhớ:

- `ClassLoader.getResource("pkg/name.txt")` thường nhận path từ root, không có dấu slash đầu.
- `SomeClass.class.getResource("name.txt")` hiểu tên tương đối với package class, còn `"/pkg/name.txt"` là root-relative.
- Parent-first resource lookup có thể trả resource của parent khi trùng tên với child; named modules còn có encapsulation/`opens`.
- Việc loader tìm được file trong JAR **không** chứng minh user được truy xuất, kể cả khi tên file khó đoán.

**Cách an toàn:** Resource được chỉ định từ trusted map/config theo **ID và quyền**; tránh để caller chọn mọi resource mà loader nhìn thấy.

## 9. Không nhận URL plugin JAR từ request

Phản ví dụ:

~~~java
// KHÔNG AN TOÀN: input được phép quyết định nguồn code và class.
URL artifact = new URL(requestUrl);
try (URLClassLoader child = new URLClassLoader(
        new URL[] {artifact},
        ClassLoader.getSystemClassLoader())) {
    Object plugin = child.loadClass(requestClassName)
            .getConstructor().newInstance();
}
~~~

Đây là đoạn minh họa, không phải chương trình chạy độc lập. Nếu `requestUrl`/`requestClassName` đến từ nơi không tin cậy, host có thể nạp và chạy bytecode ngoài chính sách của ứng dụng.

Một chuỗi cấp phép tốt hơn:

~~~text
pluginId từ client
      |
      v
AuthN / AuthZ và tenant policy
      |
      v
Trusted registry do host quản lý
      |
      v
Artifact ID + version + content digest đã duyệt
      |
      v
Xác minh nguồn/chữ ký/checksum theo trust policy
      |
      v
Nạp loader từ artifact đã phê duyệt
      |
      v
Provider triển khai shared API của host
~~~

Không nên coi “JAR có chữ ký” là bằng chứng code không thể làm hại hệ thống. Chữ ký hỗ trợ xác minh nguồn gốc/toàn vẹn theo chính sách tin cậy, còn review, runtime permissions, update policy và isolation vẫn là vấn đề riêng.

## 10. Class.forName có thể khởi tạo class

Với overload:

~~~java
// Mã minh họa; typeName đã được chọn từ trusted registry.
Class<?> type = Class.forName(typeName);
~~~

Java yêu cầu initialization của class (nếu chưa initialize). Static initializers và static field initializers có thể thực thi, **trước cả bước gọi constructor tường minh**.

~~~java
// Mã minh họa, không phải class chính của demo.
public final class SampleComponent {
    static {
        System.out.println("Static initializer runs");
    }

    public SampleComponent() {
        System.out.println("Constructor runs");
    }
}
~~~

Overload `Class.forName(name, false, loader)` không yêu cầu initialization ngay nhưng **không phải authorization**: caller vẫn chọn class được tải, và việc instantiate/call về sau có thể chạy mã.

Không nên dùng phương pháp “chỉ cho phép tên class bắt đầu bằng `demo.trusted.`”. Tác giả JAR không tin cậy có thể tự tạo class với tên đó. **Source artifact và quyền triển khai** quan trọng hơn một tiền tố package.

## 11. ServiceLoader và discovery cũng cần nguồn tin cậy

`ServiceLoader.load(Service.class, trustedLoader)` tìm provider theo service descriptor, ví dụ `META-INF/services/demo.api.Service`. Nếu attacker có thể thay JAR/descriptor, họ có thể làm framework phát hiện một provider class khác.

`ServiceLoader` kiểm tra quy tắc provider/service type, nhưng **không đánh giá động cơ bảo mật của implementation**. Vì thế cần bảo vệ quyền cài plugin, sửa artifact, thay service registry và cấu hình loader. Nếu chỉ thay TCCL sang một loader chưa được tin cậy, mọi API dựa vào TCCL cũng có thể khám phá sai nguồn.

Shared interface/DTO nên được host/parent loader định nghĩa để tránh hai bản API class identity khác nhau. Đừng cho metadata của user tự chọn defining loader hoặc URL của service provider.

## 12. ClassLoader không phải sandbox

ClassLoader quản lý **loading, namespace, delegation, class identity và resource lookup**. Nó không mặc định chặn plugin gọi filesystem/network APIs theo quyền của JVM process, không giới hạn CPU/memory và không thu hồi mọi tác dụng của mã đã chạy khi `URLClassLoader.close()` được gọi.

- Parent-first delegation không tương đương “plugin ít quyền hơn”.
- JPMS `exports`/`opens` chủ yếu phục vụ encapsulation và reflective access, không thay thế OS isolation.
- Trong Java 17, `SecurityManager` đã **deprecated for removal**; không nên giả định một security manager tự động bảo vệ plugin trong JVM hiện đại.
- Với mã thực sự không tin cậy, cần **process/container isolation**, giới hạn quyền filesystem/network, resource quotas và giao tiếp qua API/IPC có xác thực.

Allowlist class/path là lớp phòng vệ cần thiết nhưng **không thể biến bất kỳ bytecode nào thành an toàn** nếu bạn cố thực thi nó với quyền của host.

## 13. Các lỗi thường gặp

| Sai lầm | Hậu quả | Cách sửa |
|---|---|---|
| `Class.forName(userInput)` | User chọn class được yêu cầu initialize | Token → trusted factory |
| Chỉ regex FQCN hoặc prefix package | Tên hợp lệ không chứng minh quyền và nguồn code | Trusted registry + artifact policy |
| `Path.of(userInput)` rồi đọc ngay | Absolute path, traversal, symlink | Document ID + root/OS permission |
| Chỉ dùng `normalize().startsWith(root)` | Không chống symlink/TOCTOU | Root ownership, directory-handle/isolation |
| Nhận tùy ý `getResourceAsStream(name)` | Có thể lộ resource nội bộ | Allowed resource names + AuthZ |
| Client tự cung cấp URL plugin | Có thể nạp bytecode không đáng tin | Approved artifact registry + version pin |
| Coi `ServiceLoader` là trust validator | Provider hợp lệ về type vẫn có thể độc hại | Kiểm tra source và quyền triển khai |
| Coi loader là sandbox | Code plugin có quyền process | Isolate khi không tin bytecode |
| Trả stack trace/path cho client | Rò thông tin filesystem/module | Error code chung, log nội bộ |
| Khi validation fail tự fallback rộng hơn | Fail-open, phá chính sách | Từ chối và ghi nhận lỗi |
| Để user sửa map key→class | User vòng qua allowlist | Cấu hình chỉ bên tin cậy được sửa |

## 14. Checklist bảo vệ ClassLoader boundary

1. **Nguồn dữ liệu:** class name/path/plugin URL có thể bị ai sửa?
2. **AuthZ:** caller/tenant được phép gọi tính năng, xem tài liệu hoặc cài plugin chưa?
3. **Registry:** map ID → class/resource/artifact có do bên tin cậy kiểm soát không?
4. **Class loading:** có chỗ nào dùng FQCN trực tiếp từ request với `Class.forName`/`loadClass` không?
5. **Artifact:** JAR được pin version/content digest và provenance không?
6. **Resource:** có thể dùng key thay vì raw path/resource name không?
7. **Filesystem:** root có thuộc quyền attacker không; có xử lý absolute/traversal/symlink/race không?
8. **Module:** có kiểm tra module encapsulation nhưng vẫn giữ authorization riêng không?
9. **Lifecycle:** stream, thread, TCCL, listener và loader có được dọn đúng không?
10. **Isolation:** cần tiến trình/container riêng nếu bytecode không đáng tin không?
11. **Observability:** các trường hợp reject có log đủ dùng nhưng không lộ secret không?
12. **Tests:** đã thử `../`, absolute path, symlink, key lạ, artifact chưa phê duyệt chưa?

## 15. Tự kiểm tra

**Câu 1.** Regex xác nhận `"java.lang.Runtime"` là tên lớp hợp lệ. Có thể truyền trực tiếp vào `Class.forName` từ request không?

**Đáp án:** Không. Hợp lệ cú pháp không phải quyền chọn implementation; dùng allowlist token và kiểm tra quyền.

**Câu 2.** Vì sao `Class.forName(name, false, loader)` không làm tên class tùy ý trở thành an toàn?

**Đáp án:** Nó chỉ tránh yêu cầu initialization ngay; việc nạp/chọn class vẫn do input quyết định, và code có thể chạy trong bước sử dụng về sau.

**Câu 3.** `normalize().startsWith(root)` đã chống mọi path escape chưa?

**Đáp án:** Chưa. Symlink và race giữa check/open là các giới hạn quan trọng; cần root ownership và hỗ trợ từ filesystem/OS.

**Câu 4.** Loader tìm thấy `internal/secret.json` có nghĩa HTTP user được xem file ấy không?

**Đáp án:** Không. Loader visibility khác với authorization của user.

**Câu 5.** Vì sao nên nhận `"guide"` thay vì `"docs/guide.txt"`?

**Đáp án:** Host tự chọn đường dẫn từ danh sách tài liệu được phê duyệt, thay vì cho client quyết định path.

**Câu 6.** Plugin JAR được tải qua `URLClassLoader` có tự bị hạn chế network/file permissions không?

**Đáp án:** Không. ClassLoader không phải sandbox; code không tin cậy cần process/container/OS isolation.

**Câu 7.** Cùng package prefix `com.trusted.plugins` có đủ xác minh class an toàn không?

**Đáp án:** Không. Package name do tác giả bytecode tự khai báo; phải kiểm soát artifact nguồn và quyền triển khai.

- [Java SE 17 — URLClassLoader](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/net/URLClassLoader.html): URLs và vòng đời loader.
- [Java SE 17 — ServiceLoader](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/ServiceLoader.html): provider discovery.
- [JEP 411 — Deprecate the Security Manager for Removal](https://openjdk.org/jeps/411): thay đổi SecurityManager ở Java 17.

**Ghi nhớ:** **Không để dữ liệu chưa tin cậy trực tiếp chọn tên class, đường dẫn resource/file hay URL nguồn plugin.** Dùng **business key + authorization + allowlist do host sở hữu**; kiểm soát filesystem traversal, symlink/TOCTOU và quyền OS khi cần file. ClassLoader tổ chức việc nạp class, **không phải ranh giới bảo mật cho mã tùy ý**.

# Rủi ro tải lớp từ nguồn mạng hoặc thư mục có thể bị thay đổi

## 1. Vấn đề: tìm thấy class không đồng nghĩa với tin cậy

`ClassLoader` cho phép ứng dụng Java tìm và định nghĩa các lớp từ classpath, JAR, thư mục plugin, module, dữ liệu sinh ra trong bộ nhớ hoặc nguồn tải qua mạng. Khả năng mở rộng đó mang theo một ranh giới bảo mật: **ai có quyền quyết định những bytes nào sẽ được JVM định nghĩa và thực thi?**

Giả sử host cần `plugin.SafeTask`. Nếu file `plugins/current/plugin/SafeTask.class` nằm trong thư mục có thể bị sửa bởi người dùng khác, một tiến trình bị xâm nhập, một job deploy không được bảo vệ hoặc một bước tải xuống không xác thực, nội dung class có thể khác với bản đã được phê duyệt.

Rủi ro không chỉ là nạp sai version hoặc `ClassNotFoundException`. Class có tên và cấu trúc hợp lệ vẫn có thể thực hiện hành vi không mong muốn trong static initializer, constructor hoặc method. Java bytecode verifier kiểm tra các ràng buộc định dạng/kiểu của bytecode, **không chứng minh nguồn gốc hay ý định của tác giả**.

**Nguyên tắc:** đừng coi class name, classpath, HTTPS URL, hash tự tính từ cùng thư mục, hoặc việc `loadClass` thành công là bằng chứng an toàn. Hãy xác định **trust anchor độc lập**, xác thực artifact, giữ snapshot đã xác thực và chỉ nạp từ dữ liệu ấy.

## 2. Threat model: những nguồn thay đổi nguy hiểm

| Nguồn class | Rủi ro | Biện pháp cần cân nhắc |
|---|---|---|
| JAR tải qua mạng | Endpoint/CDN bị xâm nhập, dependency confusion, artifact bị thay | TLS validation, signer/digest từ nguồn phê duyệt độc lập |
| Shared plugin directory | User/process khác ghi đè `.class` hoặc JAR | ACL/ownership, staging bất biến, integrity verification |
| Network filesystem | Nội dung thay giữa kiểm tra và mở file, cache không nhất quán | Snapshot được bảo vệ, kiểm tra bytes thực sự dùng |
| Artifact repository/cache | Poisoned cache, mutable `latest` tag, nhầm version | Digest pinning, immutable release coordinates |
| Parent classpath | Parent-first chọn một class trùng binary name ngoài ý muốn | Kiểm tra parent policy/defining loader, giữ private classes ngoài parent |
| Plugin metadata | `META-INF/services/...` bị đổi để nạp provider khác | Xác minh cả service metadata và provider artifacts |
| Resources/scripts | Config, XML, template, script hoặc native library bị thay | Whole-artifact verification và resource policy |
| Generated bytecode | Generator/input không đáng tin tạo hành vi sai | Kiểm soát nguồn input, build provenance, output approval |

Hai câu hỏi độc lập: **artifact có thực sự là bản đã được approve?** và **bản được approve có được phép thực thi với mức quyền hiện tại?** Tính toàn vẹn không chứng minh logic hoàn toàn an toàn.

### Classpath injection và shadowing

Một lỗi phổ biến là child loader có `findClass` đọc file plugin đã kiểm tra, nhưng `loadClass` mặc định làm **parent-first**:

```text
child.loadClass("plugin.SafeTask")
    -> findLoadedClass(name)
    -> parent.loadClass(name)  // nếu parent có cùng tên
    -> chỉ gọi child.findClass khi parent không tìm được
```

Nếu parent đã định nghĩa `plugin.SafeTask` khác, bước kiểm tra hash trong child `findClass` có thể **không được chạy**. Vì vậy, một kiểm soát integrity chỉ nằm trong `findClass` chưa đủ để bảo vệ namespace mà parent có thể cung cấp.

Cách xử lý: đặt private plugin implementation **ngoài** parent classpath, hoặc override `loadClass` **có chọn lọc** cho namespace private và kiểm tra hash trước `defineClass`. Không chuyển sang child-first cho mọi package: `java.*` và shared `api.*` cần giữ cơ chế chia sẻ/định danh kiểu chính xác.

## 3. ClassLoader, verifier và quyền thực thi: ba tầng riêng

Theo Java 17:

1. `ClassLoader.loadClass`/`findClass` tìm class hoặc bytes. `defineClass` định nghĩa runtime class từ bytecode.
2. JVM kiểm tra class-file format, verification, linking và các ràng buộc hệ kiểu. Class file không hợp lệ có thể gây `ClassFormatError`, `VerifyError` hoặc `LinkageError`.
3. Mã Java đã được chấp nhận có thể thực thi side effects trong phạm vi quyền của **tiến trình** và chính sách runtime. Việc bytecode hợp lệ không bảo đảm ý định lành tính.

`Class.forName(name, true, loader)` còn yêu cầu class initialization, có thể chạy `<clinit>`. Chỉ làm integrity check **sau khi** gọi `Class.forName(..., true, ...)` là quá muộn: mã đã có cơ hội thực thi.

`ClassLoader.getName()` là nhãn debug; `clazz.getClassLoader()` cho biết defining loader đối với class thông thường; `clazz.getProtectionDomain()` cung cấp metadata liên quan tới security-domain model. Không cái nào **tự** bảo đảm artifact được phê duyệt.

**Java 17 SecurityManager đã bị deprecated for removal** theo JEP 411. Đừng thiết kế sandbox mới cho untrusted Java bytecode chỉ bằng custom ClassLoader hoặc SecurityManager. Muốn chạy code không đáng tin, thường cần process/container isolation và quyền OS tối thiểu.

## 4. TOCTOU: kiểm tra tại T1, đọc bytes tại T2

TOCTOU (*time of check to time of use*) xuất hiện khi chương trình kiểm tra một đối tượng rồi mở lại một nguồn có thể bị sửa.

```text
T1: hash plugins/current/plugin.jar -> SHA-256 đúng
T2: actor không đáng tin thay plugin.jar
T3: tạo URLClassLoader từ cùng đường dẫn
T4: URLClassLoader mở file và lấy class bytes đã bị thay
T5: JVM define/initialize class mới
```

Không đủ để kiểm tra `Files.exists`, `size`, `lastModifiedTime`, `Path.normalize()` hoặc `toRealPath()` rồi tin file sẽ giữ nguyên. Symlinks và file contents có thể đổi giữa **check** và **open**, đặc biệt trong thư mục attacker có quyền ghi hoặc shared filesystem.

Một mẫu đáng tin hơn:

```java
byte[] bytes = Files.readAllBytes(classFile);
byte[] digest = MessageDigest.getInstance("SHA-256").digest(bytes);
if (!MessageDigest.isEqual(digest, approvedDigest)) {
    throw new SecurityException("Integrity failure");
}
Class<?> type = defineClass(binaryName, bytes, 0, bytes.length);
```

Đây là **snippet minh họa nằm trong subclass `ClassLoader`**, cần imports, variables và xử lý checked exceptions. Điểm then chốt: **cùng một byte array được hash và truyền vào `defineClass`**. Nếu file thay sau khi đọc, dữ liệu đã chụp trong byte array không thay theo. Nếu thay trong lúc đọc, bytes cuối cùng vẫn phải vượt qua digest check.

Với plugin gồm nhiều classes và resources, hash một class là **chưa đủ**. Nên tạo immutable snapshot của toàn artifact, xác thực manifest/chữ ký/digest trước rồi cho loader đọc chỉ từ snapshot đó.

## 5. SHA-256 pinning và câu hỏi quan trọng: tin digest nào?

So sánh `SHA256(bytes)` với một giá trị kỳ vọng chỉ có ý nghĩa bảo mật nếu **giá trị kỳ vọng đến từ trust root độc lập**. Chẳng hạn, dùng manifest phát hành đã được phê duyệt/ký và kiểm tra đúng signer; hoặc pin trong cấu hình triển khai chỉ bên tin cậy có quyền cập nhật. Không lấy checksum nằm cạnh file JAR/class trong cùng thư mục mutable làm nguồn tin: attacker có thể sửa cả file lẫn checksum.

Điểm riêng của **mutable class source** ở bài này là kết quả hash phải gắn với **đúng byte array sắp đưa vào `defineClass`**. Nếu hash tệp ở T1 nhưng `URLClassLoader` đọc lại cùng pathname tại T2, TOCTOU vẫn tồn tại. Ví dụ mục 6 chứng minh cách kiểm tra `readAllBytes → digest → defineClass` cho một class.

Pin digest chưa bảo đảm code vô hại, dependency graph sạch hoặc quyền runtime phù hợp. Việc xác minh toàn bộ JAR, signer, provenance, transitive dependencies và chính sách thu hồi được thực hành trong bài **Kiểm soát nguồn JAR, tính toàn vẹn và phụ thuộc được phép**.

## 6. Ví dụ Java 17 hoàn chỉnh: kiểm tra hash trước defineClass

Ví dụ có **một** class `plugin.SafeTask` trong thư mục riêng và một host không đưa thư mục plugin vào application classpath. Host nhận SHA-256 được phê duyệt từ môi trường build/release, đọc bytes một lần, kiểm tra rồi mới `defineClass`.

**Giới hạn của ví dụ:** nó minh họa integrity của **một class**; không tự xác thực transitive dependencies, resources, network transport hoặc ký số JAR; không phải security sandbox.

### 6.1. Cấu trúc

```text
src/
  plugin/
    plugin/
      SafeTask.java
  host/
    PinnedLoaderDemo.java
out/
  plugin/
  host/
```

File `src/plugin/plugin/SafeTask.java`:

```java
package plugin;

public final class SafeTask {
    public static String run() {
        return "safe-v1";
    }
}
```

File `src/host/PinnedLoaderDemo.java`:

```java
import java.io.IOException;
import java.lang.reflect.Method;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

public final class PinnedLoaderDemo {
    private static final String TARGET = "plugin.SafeTask";

    static final class PinnedLoader extends ClassLoader {
        private final Path classFile;
        private final byte[] expectedHash;

        PinnedLoader(Path classFile, byte[] expectedHash, ClassLoader parent) {
            super("pinned-plugin", parent);
            this.classFile = classFile;
            this.expectedHash = expectedHash.clone();
        }

        @Override
        protected Class<?> loadClass(String name, boolean resolve)
                throws ClassNotFoundException {
            if (!TARGET.equals(name)) {
                return super.loadClass(name, resolve);
            }

            synchronized (getClassLoadingLock(name)) {
                Class<?> found = findLoadedClass(name);
                if (found == null) {
                    found = findClass(name);
                }
                if (resolve) {
                    resolveClass(found);
                }
                return found;
            }
        }

        @Override
        protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            if (!TARGET.equals(name)) {
                throw new ClassNotFoundException(name);
            }

            byte[] bytes;
            try {
                bytes = Files.readAllBytes(classFile);
            } catch (IOException ex) {
                throw new ClassNotFoundException(name, ex);
            }

            byte[] actual;
            try {
                actual = MessageDigest.getInstance("SHA-256").digest(bytes);
            } catch (NoSuchAlgorithmException impossible) {
                throw new AssertionError(impossible);
            }

            if (!MessageDigest.isEqual(actual, expectedHash)) {
                throw new SecurityException(
                        "SHA-256 mismatch for " + name);
            }

            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: PinnedLoaderDemo <plugin-root> <trusted-sha256-hex>");
        }

        byte[] trustedDigest = HexFormat.of().parseHex(args[1]);
        if (trustedDigest.length != 32) {
            throw new IllegalArgumentException(
                    "Expected 32 SHA-256 bytes");
        }

        Path classFile = Path.of(args[0], "plugin", "SafeTask.class");
        PinnedLoader loader = new PinnedLoader(
                classFile,
                trustedDigest,
                PinnedLoaderDemo.class.getClassLoader());

        Class<?> type = Class.forName(TARGET, true, loader);
        Method run = type.getMethod("run");

        System.out.println("SHA-256 accepted: true");
        System.out.println("Defined by pinned loader: "
                + (type.getClassLoader() == loader));
        System.out.println("Task result: " + run.invoke(null));
    }
}
```

### 6.2. Vì sao override loadClass cho đúng một tên?

- Với `plugin.SafeTask`, code gọi `findLoadedClass`; nếu chưa có, bắt buộc qua `findClass` được bảo vệ bởi SHA-256. Parent không thể trả bản `plugin.SafeTask` khác rồi bỏ qua bước kiểm tra.
- Với mọi class name khác, code giữ `super.loadClass` để không tùy tiện child-first các shared API và class JVM.
- `synchronized (getClassLoadingLock(name))` bảo vệ kiểm tra → định nghĩa cho cùng tên khỏi race nhiều thread.
- `MessageDigest.isEqual` so sánh bytes digest; nếu mismatch, `SecurityException` được ném **trước** khi `defineClass`.
- `Class.forName(..., true, loader)` chỉ làm initialization sau khi loader đã trả class hợp lệ.

Với plugin nhiều class, phải mở rộng policy để kiểm tra **tất cả private classes và dependencies**. Không dùng một loader chỉ kiểm tra `SafeTask` rồi giả định phần còn lại đã trusted.

Bash trên Linux/macOS:

```bash

javac -d out/host src/host/PinnedLoaderDemo.java
```

### 6.4. Pin digest từ môi trường phát hành đáng tin

Tại thời điểm build/release khi source và builder đã được phê duyệt, tính digest:

```bash
sha256sum out/plugin/plugin/SafeTask.class
```

Hoặc PowerShell:

```powershell
(Get-FileHash out/plugin/plugin/SafeTask.class -Algorithm SHA256).Hash
```

Lưu **64 ký tự hex** trong manifest được ký hoặc configuration được bảo vệ riêng. **Không** hash lại file ở thư mục mutable mỗi lần load rồi coi hash mới là giá trị expected đáng tin.

### 6.5. Chạy

Thay `TRUSTED_SHA256_HEX` bằng đúng digest đã được phê duyệt:

```bash
java -cp out/host PinnedLoaderDemo out/plugin TRUSTED_SHA256_HEX
```

Với bytes ban đầu và đúng digest, stdout:

```text
SHA-256 accepted: true
Defined by pinned loader: true
Task result: safe-v1
```

Lệnh chạy có **`-cp out/host`**, không có `out/plugin`. Điều này giữ plugin ngoài application classpath và minh họa rõ nơi class được định nghĩa.

### 6.6. Thử thay file nhưng giữ digest cũ

Đổi literal `"safe-v1"` trong `SafeTask.java` thành `"safe-v2"`, biên dịch lại class plugin và vẫn chạy bằng digest của bản đã phê duyệt trước đó:

```bash
javac -d out/plugin src/plugin/plugin/SafeTask.java
java -cp out/host PinnedLoaderDemo out/plugin TRUSTED_SHA256_HEX
```

Chương trình từ chối trước `defineClass`. Dòng lỗi chính:

```text
java.lang.SecurityException: SHA-256 mismatch for plugin.SafeTask
```

Đó là **dòng nhận diện lỗi**, không phải toàn bộ stderr cố định; stack trace có method/file/line numbers tùy build. Không đổi expected thành digest mới chỉ để “sửa lỗi” trừ khi version mới thực sự đã được phê duyệt.

**Xác minh thực tế:** mã demo này đã được biên dịch/chạy trong môi trường thử độc lập bằng JDK 21 với API tương thích Java 17. Trường hợp đúng digest in chính xác ba dòng thành công; trường hợp sửa source/biên dịch lại nhưng giữ digest cũ ném `SecurityException` trước khi thực thi method.

### 6.7. Những gì demo không bảo vệ

- Ai kiểm soát **CLI digest** cũng có thể quyết định bytes nào được chấp nhận; thực tế cần một trust channel cho digest.
- Checksum chỉ áp dụng cho class đích, không phải mọi dependency/JAR/resource.
- Nếu file thay trong lúc `readAllBytes`, nội dung chụp được vẫn phải khớp hash; nên tránh đọc từ filesystem cho phép người lạ can thiệp liên tục và staging cần quyền nghiêm ngặt.
- Nếu class đã được định nghĩa trong loader, lần `loadClass` sau nhận lại class cũ; thay file sau đó không khiến loader tự định nghĩa lại. Với release mới, dùng loader/snapshot mới.
- Integrity không phải static code analysis hoặc behavioral sandbox.
- `SecurityException` là lỗi bảo mật; **không** catch rồi tự fallback sang bytes chưa xác thực.

## 7. JAR ký số, jarsigner và CodeSource

Một JAR có `META-INF/*.SF` hoặc có thể chạy `jarsigner -verify` chưa tự chứng minh **signer được phép phát hành**: còn phải kiểm tra chain/key pin, trust policy, các entry được ký và phiên bản artifact. Khi custom loader đọc class file từ mutable directory rồi tự gọi `defineClass`, không có bước chứng thực signer tự động cho file ấy.

`CodeSource`/`ProtectionDomain` là metadata có ích để chẩn đoán nguồn/loader nhưng **không phải** bằng chứng URL đã được xác thực hay bytecode đáng tin. Ở JDK 24+, SecurityManager bị vô hiệu hóa vĩnh viễn, nên không thể dùng metadata này làm sandbox quyền file/network.

Với JAR thực tế, xác minh signer/trust **trước khi cho loader nạp từ snapshot bất biến**, cùng kiểm tra toàn bộ dependencies và resources. Bài về **kiểm soát nguồn JAR** giải thích quy trình kiểm duyệt JAR, SHA-256, chữ ký và allowlist chi tiết.

## 8. Nạp từ mạng: bảo vệ transport và provenance

Một download pipeline nên:

1. Chọn artifact ID/version từ danh mục cho phép; không thực thi plugin theo URL tùy ý của request.
2. Sử dụng HTTPS/TLS đúng: validate hostname/certificate, không tắt TLS verification để xử lý lỗi.
3. Giới hạn host, redirects, DNS/egress, size và timeout. URL do attacker chọn có thể tạo thêm rủi ro SSRF trong một số kiến trúc.
4. Tải dữ liệu về staging location mà untrusted actor không ghi được.
5. Xác thực release manifest/chữ ký hoặc digest đã pin từ một nguồn độc lập.
6. Kiểm tra dependency closure và resource/service metadata theo cùng release policy.
7. Chuyển artifact thành snapshot được bảo vệ, rồi mới tạo class loader.
8. Ghi audit artifact/version/digest/signing identity/loader khi hợp lý, không ghi secrets.
9. Có quy trình rollback và thu hồi nếu phát hiện compromised artifact hoặc signing key.

**TLS không thay thế artifact authorization.** Một repository hoạt động qua HTTPS vẫn có thể phân phối phiên bản sai hoặc artifact không được tổ chức phê duyệt.

Các đường dẫn theo content digest như `store/sha256/<digest>/plugin.jar` có ích cho lưu trữ immutable, nhưng tên thư mục **không tự chứng minh** nội dung đúng. Vẫn phải verify bytes từ trust root.

## 9. Nạp từ thư mục mutable: staging và snapshot

Một cách bố trí rõ ràng:

```text
incoming/            <- artifact vừa nhận, chưa tin cậy
quarantine/          <- kiểm tra format/size/manifest
verified/            <- snapshot đã xác thực, ACL ghi hạn chế
active/              <- chỉ tới version đang hoạt động
```

Đây là kiến trúc minh họa, không phải các thư mục phải tạo ngay trong workspace.

Điểm quan trọng:

- **Không dùng active directory làm nơi copy dần** các file `.class` của bản mới khi loader đang đọc.
- Tạo version directory mới hoàn chỉnh, verify **tất cả** files/whole artifact, sau đó activate.
- Nếu dùng `Files.move(..., ATOMIC_MOVE)`, kiểm tra filesystem support và xử lý `AtomicMoveNotSupportedException`; atomic rename không phổ quát giữa volumes/network shares.
- Giữ version cũ bất biến cho loaders đang chạy, không sửa JAR dưới chân chúng.
- Với hot reload, dùng loader mới cho version mới; dừng task, unregister listeners và đóng resources của loader cũ đúng lifecycle.

### Path traversal và symlink

`Path.normalize()` xử lý `.`/`..` trong chuỗi path, **không chứng minh** đường dẫn cuối cùng nằm trong trusted root nếu có symlink/junction. `toRealPath()` giải quyết path ở một thời điểm nhưng một attacker có thể thay symlink ngay sau check nếu có quyền.

Không ghép user-supplied class/resource name bất kỳ trực tiếp vào filesystem path. Cần kiểm tra namespace, root containment, archive entry names, symlink handling, filesystem permissions và thời điểm sử dụng. Với threat model nghiêm ngặt, sử dụng snapshot/file handles được bảo vệ thay vì check rồi mở lại mutable path.

Khi giải nén JAR/ZIP, kiểm tra entry path trước khi ghi để tránh **Zip Slip**, tránh file nằm ngoài staging root; giới hạn kích thước giải nén và số lượng entries để giảm DoS.

## 10. Resources, dependencies và SPI cũng phải tin cậy

Một plugin gồm nhiều thứ hơn `Entry.class`:

- Các class private và transitive dependencies.
- `META-INF/services/...` chỉ định service providers.
- Resource/config files, XML, template, embedded script.
- JNI/native libraries.
- Module descriptors, manifest/classpath metadata.

Ví dụ:

```java
ClassLoader pluginLoader = pluginInstance.getClass().getClassLoader();
java.net.URL config = pluginLoader.getResource("plugin/config.properties");
```

Snippet cần `pluginInstance` thực tế. Nếu config được đọc từ mutable filesystem hoặc parent resource bất ngờ, plugin có thể thay behavior dù class đã được pin. Vì thế cần snapshot cả resources và kiểm tra lookup policy.

Với `ServiceLoader.load(Service.class)`, provider discovery thường dùng TCCL của thread; một container worker có TCCL khác plugin đích có thể tìm provider sai. Khi biết provider loader, sử dụng overload `ServiceLoader.load(Service.class, pluginLoader)` và xác thực provider artifact/descriptor, đồng thời bảo đảm service interface type được parent/shared loader định nghĩa thống nhất.

**Parent-first và resource lookup cũng có visibility rules**: đừng giả định chỉ vì đã chọn plugin loader thì chắc chắn class/resource đến từ plugin URL thay vì parent.

## 11. Giới hạn an toàn: ClassLoader không phải sandbox

Custom loader có thể giúp:

- Cô lập runtime class identities của plugin A và B.
- Nạp từ artifact đã verified.
- Chọn source/namespace cụ thể.
- Cung cấp lookup policy nhất quán cho ứng dụng.

Nhưng nó **không tự** hạn chế CPU/memory, network/file permissions, subprocess, native code, process-wide system properties hoặc threads. Nếu plugin thực sự không đáng tin, cân nhắc chạy trong **process/JVM riêng**, với user/permissions tối thiểu, sandbox/container OS thích hợp, resource quotas và protocol giao tiếp kiểm soát đầu vào.

Đặc biệt với Java 17, tránh thiết kế một “plugin sandbox” mới chỉ dựa trên SecurityManager, vì JEP 411 đã deprecated tính năng đó for removal. Chữ ký/hash trả lời “bytes có đúng bản phê duyệt không?”, **không** trả lời “được phép chạy trong cùng trust boundary với host không?”.

## 12. Những lỗi thường gặp

| Lỗi | Vì sao nguy hiểm | Hướng xử lý |
|---|---|---|
| Hash file rồi mở lại path mutable | TOCTOU | Verify chính bytes dùng để define hoặc immutable snapshot |
| Tính hash expected ngay tại runtime từ cùng file | Attacker sửa cả content và digest | Trusted manifest/pin độc lập |
| Chỉ pin một entry class | Helper/resources/providers vẫn bị thay | Whole-artifact + dependency verification |
| Chỉ kiểm tra class name | Cùng tên có thể là bytes khác | Digest/signature + defining loader audit |
| Chỉ check trong `findClass` | Parent-first có thể bypass check | Namespace/loader policy và preflight parent |
| Dùng child-first cho mọi package | Tạo bản sao shared APIs | Selective policy, preserve shared API identity |
| Tin vào bytecode verifier như antivirus | Valid code vẫn có thể độc hại | Trust/approval + least privilege |
| Thấy `META-INF` signature file liền tin JAR | Chưa chắc signature/signer được verify | jarsigner/đường kiểm tra đáng tin |
| Dùng TLS rồi bỏ version approval | TLS không chọn artifact được phép | Pin artifact ID/version/digest |
| Copy nhiều `.class` vào active directory | Loader có thể lấy nửa v1 nửa v2 | Staging complete snapshot và atomic activation |
| Catch `SecurityException` rồi fallback | Bypass fail-closed control | Từ chối và điều tra |
| Tăng quyền hệ thống cho plugin tùy ý | ClassLoader không cách ly permissions | Separate process/OS least privilege |
| Gọi `System.gc()` để “loại bỏ code đã load” | Class unloading không tức thì và không là security revocation | Stop process/teardown plugin theo thiết kế |

## 13. Chẩn đoán và kiểm thử bảo mật

**Đừng chỉ test trường hợp plugin đúng tải thành công.** Cần test những tình huống thất bại:

| Test | Kỳ vọng |
|---|---|
| Class bytes đúng, digest từ trusted release | Load/initialize/invoke thành công |
| Class đổi một byte, giữ trusted digest | Từ chối trước `defineClass` |
| Attacker sửa đồng thời file và checksum cùng thư mục | Không chấp nhận checksum tại nguồn untrusted |
| Parent có class trùng tên | Không bypass pin policy cho protected target |
| Private dependency bị sửa | Whole-artifact verification từ chối |
| SPI descriptor hoặc resource thay | Manifest/verification policy phát hiện |
| Symlink thoát trusted root | Không cho vượt ranh giới source |
| Source bị thay trong lúc copy | Chỉ activate snapshot đúng digest |
| Concurrent requests tới cùng binary name | Không define trùng class, lock đúng |
| Một loader đã load class rồi file thay | Class đã load không tự hot-reload |
| Release v2 được phê duyệt | Tạo snapshot/loader mới và quản lý old lifecycle |

Trong logs có thể in:

```java
System.out.println(type.getName());
System.out.println(type.getClassLoader());
System.out.println(type.getModule());
```

Đây là snippet cần biến `type`. Các metadata đó hữu ích khi điều tra shadowing, nhưng **không thay thế integrity validation**.

Các lỗi JVM phân biệt:

- `ClassNotFoundException`: lookup không thấy tên.
- `ClassFormatError` hoặc `VerifyError`: class data/verification không hợp lệ.
- `LinkageError`: ví dụ identity/constraint/API không nhất quán.
- `NoClassDefFoundError`: dependency/runtime resolution hoặc initialization trước thất bại.
- `SecurityException` trong demo: **explicit digest verification failure**.

Không che mọi nguyên nhân bằng một câu “plugin load fail” rồi tự fallback sang artifact khác.

## 14. Bài tập tự kiểm tra

**Câu 1.** SHA-256 của JAR khớp với file checksum được đặt cạnh JAR trong cùng một thư mục có quyền ghi cho attacker. Có bảo đảm an toàn không?

**Đáp án:** Không. Attacker có thể sửa cả JAR và checksum. Cần expected digest/chữ ký từ trust root độc lập.

**Câu 2.** Bytecode verifier chấp nhận class; có nghĩa class không làm điều nguy hiểm không?

**Đáp án:** Không. Verifier bảo vệ quy tắc class/bytecode, không chứng minh behavior đáng tin.

**Câu 3.** Vì sao kiểm tra SHA ở T1 rồi để `URLClassLoader` đọc lại file ở T2 vẫn có rủi ro?

**Đáp án:** TOCTOU: file có thể bị thay giữa hai thời điểm. Dùng verified immutable snapshot hoặc verify cùng byte[] sẽ đưa vào `defineClass`.

**Câu 4.** Nếu attacker thay class file sau khi `readAllBytes` trả về nhưng trước `defineClass` dùng chính array đã hash, có sửa được nội dung array từ đĩa không?

**Đáp án:** Không. Array trong bộ nhớ là snapshot đã được hash. Tuy nhiên file khác/resources có thể bị đọc sau; cần whole-artifact policy.

**Câu 5.** Tại sao chỉ override `findClass` để check hash có thể chưa đủ?

**Đáp án:** Parent-first `loadClass` có thể trả class từ parent trước, không gọi `findClass`. Cần điều phối namespace/lookup để protected class không bị bypass.

**Câu 6.** Plugin class đã pin an toàn nhưng `META-INF/services` trỏ provider độc hại. Điều gì sai?

**Đáp án:** Đã bỏ sót service metadata/provider artifact ngoài phạm vi integrity. Cần verify toàn artifact và provider discovery.

**Câu 7.** JAR signature hợp lệ đồng nghĩa plugin không có vulnerability?

**Đáp án:** Không. Signature chứng minh artifact được ký dưới một khóa và nội dung không đổi theo chữ ký, không chứng minh behavior không có lỗi. Còn phải kiểm tra trusted signer/approval và code security.

**Câu 8.** `ClassLoader` riêng có ngăn plugin đọc file hệ thống hoặc tạo network connections không?

**Đáp án:** Không chỉ nhờ việc cách ly tên lớp. Quyền OS/process và sandbox phù hợp mới là cơ chế kiểm soát hành vi khi plugin không đáng tin.

**Câu 9.** Khi deploy, vì sao không nên chép tuần tự các class mới lên active directory đang dùng?

**Đáp án:** Các lượt nạp có thể thấy bản trộn nhiều versions, dẫn đến sai behavior hoặc `NoSuchMethodError`/`LinkageError`. Sử dụng snapshot version đã hoàn chỉnh và activation có kiểm soát.

**Câu 10.** Trong ví dụ, vì sao mismatch được phát hiện **trước** khi `SafeTask.run()` chạy?

**Đáp án:** Loader hash và so sánh byte array trước `defineClass`. Nếu mismatch, ném `SecurityException` ngay ở `findClass`; `Class.forName` chưa nhận được class để initialize.

## 15. Checklist triển khai

- [ ] Đã xác định threat model và ai có quyền phát hành/sửa artifacts.
- [ ] Artifact được chọn qua ID/version/allowlist rõ ràng.
- [ ] Network transport dùng TLS validation đúng và có giới hạn nguồn/redirects/size.
- [ ] Hash/chữ ký được xác thực bằng trust root độc lập với mutable source.
- [ ] Tất cả classes, resources, provider metadata và dependencies liên quan nằm trong phạm vi kiểm tra.
- [ ] Có verified immutable snapshot/staging với permissions/ownership thích hợp.
- [ ] Không có TOCTOU giữa verify và bytes thực sự được define.
- [ ] Parent delegation không bypass integrity cho protected namespaces.
- [ ] Shared API types không bị duplicate khi áp dụng selective child-first.
- [ ] Có fail-closed error handling, logging/audit không lộ secrets.
- [ ] Có atomic/transactional activation và rollback logic.
- [ ] Có cleanup loader/resources/tasks khi cập nhật plugin.
- [ ] Với untrusted plugins, dùng process isolation và least privilege thay vì coi classloader là sandbox.
- [ ] Có tests tampering, partial updates, symlink/path attacks, service injection và lifecycle.

## 16. Tóm tắt và tài liệu chuẩn

**Nắm chắc sáu ý:**

1. **Bytecode đúng cú pháp không đồng nghĩa đáng tin.** Class loading chỉ xác định định nghĩa, không phê duyệt tác giả hoặc hành vi.
2. **Mutable source dẫn tới TOCTOU.** Không kiểm tra một file rồi cho loader mở lại đường dẫn có thể bị sửa mà không có snapshot/integrity mới.
3. **Hash phải gắn với trusted expected digest.** Tính lại digest trên nguồn không đáng tin không cung cấp trust.
4. **Xác thực toàn artifact/dependencies**, không chỉ entry class; SPI/resources có thể thay behavior.
5. **Kiểm soát parent delegation** để tránh bypass nhưng đừng làm vỡ shared API identities bằng child-first tùy tiện.
6. **ClassLoader không phải sandbox.** Với untrusted code, phải giới hạn quyền ở mức process/OS.

- [MessageDigest API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/security/MessageDigest.html): SHA-256, `digest` và `isEqual`.
- [JarFile API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/jar/JarFile.html): JAR entries và verification.
- [jarsigner tool](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jarsigner.html): kiểm tra chữ ký JAR.
- [SecureClassLoader API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/security/SecureClassLoader.html): liên hệ `CodeSource`, `ProtectionDomain`.

# SecurityManager là cơ chế lịch sử và cần đối chiếu phiên bản JDK

**`java.lang.SecurityManager` là cơ chế kiểm soát quyền truy cập tài nguyên mang tính lịch sử của Java; không phải công cụ sandbox được khuyến nghị cho ứng dụng Java hiện đại.** Khi đọc tài liệu cũ về `ClassLoader`, plugin, `ProtectionDomain` hoặc `java.security.Policy`, rất dễ gặp ví dụ cài `SecurityManager` để giới hạn quyền đọc file, mở socket hay tạo class loader. Những ví dụ đó cần được hiểu theo **đúng phiên bản JDK**, vì Java đã thay đổi chính sách rất lớn.

Các mốc quan trọng:

- **JDK 8–16:** `SecurityManager` là một phần của mô hình bảo mật truyền thống, có thể được cấu hình trong những điều kiện cụ thể. Không nên mặc định tất cả chương trình đều kích hoạt nó.
- **JDK 17:** **JEP 411** đánh dấu `SecurityManager` cùng nhiều API liên quan là **deprecated for removal**. Cơ chế cũ vẫn còn, nhưng ứng dụng mới không nên dựa vào nó.
- **JDK 17–23:** còn giai đoạn tương thích lịch sử; khả năng bật/cài động và thông báo cảnh báo **phụ thuộc phiên bản và cấu hình**. Không lấy hành vi của một JDK trong khoảng này làm hợp đồng cho JDK sau.
- **Từ JDK 24:** **JEP 486** làm `SecurityManager` **permanently disabled**. Không thể bật nó lúc khởi động hoặc cài một custom manager lúc runtime. Các API liên quan còn tồn tại để tương thích trong một số phiên bản nhưng nhiều phương thức đã đổi semantics; bản thân API được dự kiến loại bỏ trong tương lai.

**Ý chính của bài học:** Class loader quy định **tìm và định nghĩa lớp nào trong namespace nào**; SecurityManager lịch sử là một cơ chế **kiểm tra quyền thao tác**; JPMS quy định **ranh giới module và quyền truy cập API/reflective access**. Chúng không thay thế cho nhau. Để chạy plugin không đáng tin, phải thiết kế **ranh giới bảo mật ngoài JVM hoặc process isolation**, thay vì chỉ tạo một `ClassLoader` riêng.

## 1. SecurityManager từng giải quyết vấn đề gì?

Trong những ứng dụng Java lịch sử, hệ thống có thể muốn chạy code đến từ nguồn ít tin cậy hơn và hạn chế những hành động nhạy cảm:

- Đọc, ghi hoặc xóa tệp trên filesystem.
- Mở kết nối mạng, lắng nghe socket.
- Tạo subprocess hoặc yêu cầu JVM thoát.
- Tạo class loader, thay đổi system properties hoặc một số cấu hình runtime.
- Truy cập package, reflection hoặc các thao tác nhạy cảm theo những `Permission` tương ứng.

Ý tưởng tổng quát:

```text
Code gọi một API nhạy cảm
         |
         v
Java library/runtime (trong môi trường có SecurityManager)
         |
         v
SecurityManager.checkPermission(permission)
         |
         +-- quyền cho phép -> API tiếp tục
         |
         +-- quyền bị từ chối -> SecurityException
```

Những classes/khái niệm xuất hiện trong tài liệu lịch sử:

| Thành phần | Vai trò lịch sử |
|---|---|
| `SecurityManager` | Entry point kiểm tra quyền với các `check...` methods |
| `Permission` | Biểu diễn yêu cầu quyền, ví dụ `FilePermission` hoặc `SocketPermission` |
| `Policy` | Nguồn cấu hình những quyền được cấp |
| `ProtectionDomain` | Gắn class/code với domain, code source và quyền |
| `AccessControlContext` | Ngữ cảnh kiểm tra quyền ở call stack |
| `AccessController` | Kiểm tra quyền và thao tác `doPrivileged` trong mô hình cũ |
| `ClassLoader` | Tải/định nghĩa class, ảnh hưởng code source và `ProtectionDomain` khi dùng overload phù hợp |

**Điều kiện then chốt:** Trong JDK lịch sử, những kiểm tra đó chỉ có tác dụng khi SecurityManager thực sự được bật/cài đặt và thư viện/runtime gọi đúng điểm kiểm tra. Chỉ tồn tại `Permission` hoặc `ProtectionDomain` **không tự động khiến ứng dụng bị sandbox**.

## 2. Các phiên bản JDK và những thay đổi phải ghi nhớ

| Dòng JDK | Trạng thái SecurityManager | Điều cần hiểu |
|---|---|---|
| **JDK 8–16** | Cơ chế bảo mật truyền thống còn khả dụng | Cấu hình/việc cài manager và policies quyết định hành vi; không mặc nhiên bật |
| **JDK 17** | **Deprecated for removal** theo JEP 411 | Các API vẫn có để tương thích; có cảnh báo deprecation và cảnh báo khi sử dụng |
| **JDK 18–23** | Tiếp tục lộ trình deprecation/giảm hỗ trợ | Đừng giả định property/default startup và khả năng `setSecurityManager` giống JDK 17 |
| **JDK 24 trở lên** | **Permanently disabled** theo JEP 486 | Không được bật/install; các API liên quan có behaviors bị thu hẹp hoặc thay đổi |
| **Một phiên bản JDK tương lai** | API có thể bị loại bỏ | Việc API còn compile ở một release không bảo đảm tồn tại ở mọi release sau |

Đây là **bảng định hướng**, không thay cho migration guide của chính vendor/runtime đang triển khai. Đặc biệt, những cụm “deprecated” và “disabled” mang nghĩa **khác nhau**.

### Deprecated for removal khác permanently disabled

- **Deprecated for removal:** compiler và tooling cảnh báo không nên dùng và API có kế hoạch bị loại bỏ; ở JDK 17, một số use cases lịch sử vẫn có thể hoạt động khi cấu hình cho phép.
- **Permanently disabled:** kể từ **JDK 24**, manager không thể được kích hoạt để thực thi policy cũ, dù API `SecurityManager` có thể vẫn hiện diện trong class library cho mục đích tương thích.
- **Removed:** API không còn trong một phiên bản; đây **không phải** mô tả tương đương với việc “bị disable” trong JDK 24. Khi gặp báo cáo lỗi, phải ghi đúng phiên bản và trạng thái.

**Tránh câu sai:** “SecurityManager đã bị xóa khỏi Java 17” — Java 17 **deprecated for removal**, chứ không xóa. Cũng tránh “SecurityManager vẫn dùng bình thường ở mọi JDK mới vì class còn tồn tại” — từ JDK 24 cơ chế kiểm soát đó **không hoạt động như trước**.

## 3. Khi Java 17 còn cho cấu hình SecurityManager

Trong Java SE 17, SecurityManager có thể được cài khi khởi động trong các cấu hình được hỗ trợ. Một ví dụ tài liệu lịch sử:

```bash
# CHỈ mang ý nghĩa nghiên cứu ứng dụng cũ trên JDK 17;
# không dùng làm cách sandbox plugin mới.
java -Djava.security.manager=default -jar legacy-app.jar
```

Một cơ chế khác của Java 17 là khai báo chính sách quyền qua file policy và các code source/protection domains. Các cấu hình này có ngữ nghĩa và hạn chế riêng; không thể chỉ viết một file `.policy` rồi mặc nhiên mọi code trong JVM bị cô lập.

Theo Java SE 17 API, `java.security.manager` có các giá trị như `allow` và `disallow` cùng những giá trị lịch sử kích hoạt manager. Ví dụ:

- `disallow`: không cài manager lúc startup và ngăn cài động, khiến `System.setSecurityManager(...)` ném `UnsupportedOperationException`.
- `allow`: không cài manager lúc startup nhưng cho phép thử cài động theo contract của JDK 17 và policy đang áp dụng.
- `default` (hoặc cấu hình lịch sử tương ứng): có thể cài default manager khi khởi động JDK 17.

**Không mang nguyên các quy tắc property ở JDK 17 áp sang JDK 24+.** Trên JDK 24, một tùy chọn cố bật/cho phép SecurityManager lúc khởi động là **lỗi khởi tạo JVM**, không phải chỉ cảnh báo deprecation.

### JDK 24+: bật SecurityManager là lỗi startup

Ví dụ lệnh trên Bash:

```bash
java -Djava.security.manager=allow -version
```

Trên **Windows PowerShell 5.1**, nên đặt argument `-D...=...` trong dấu nháy để tránh cách shell phân tích dấu bằng:

```powershell
java '-Djava.security.manager=allow' -version
```

Với OpenJDK 24, JVM không khởi động được và thông báo chính gồm:

```text
Error occurred during initialization of VM
java.lang.Error: A command line option has attempted to allow or enable the Security Manager. Enabling a Security Manager is not supported.
```

Đây là **hai dòng nội dung chính**; stack trace và số dòng `System.java` thay đổi theo patch release/vendor. Lệnh kết thúc với mã lỗi (trong phép thử OpenJDK 24 là **exit code 1**). Không dùng exit code/thông báo đó làm contract xử lý nghiệp vụ; nó minh họa rằng tính năng không thể bật nữa.

Ở JDK 24+, `System.setSecurityManager(...)` luôn ném **`UnsupportedOperationException`**. Đừng thiết kế chương trình mới gọi nó rồi bắt lỗi để bật sandbox dự phòng.

## 4. Ví dụ Java 17+ chạy được: kiểm tra phiên bản, manager và host API

Ví dụ dưới đây minh họa ba điều không nên lẫn:

1. Kiểm tra **phiên bản Java runtime thực tế**, không chỉ phiên bản mà source được biên dịch nhắm tới.
2. Quan sát liệu có SecurityManager đang cài hay không — **không tự cố cài một manager**.
3. Host API có thể chủ động từ chối thao tác theo contract nghiệp vụ mà **không phụ thuộc** vào SecurityManager.

Lưu một file **`SecurityBoundaryDemo.java`**:

```java
public final class SecurityBoundaryDemo {

    interface HostApi {
        String readSetting();
        void changeSetting(String value);
    }

    static final class ReadOnlyHostApi implements HostApi {
        @Override
        public String readSetting() {
            return "safe-config";
        }

        @Override
        public void changeSetting(String value) {
            throw new SecurityException(
                    "Host API forbids this operation");
        }
    }

    @SuppressWarnings("removal")
    static boolean oldManagerInstalled() {
        return System.getSecurityManager() != null;
    }

    public static void main(String[] args) {
        int feature = Runtime.version().feature();

        System.out.println("Java feature: " + feature);
        System.out.println("SecurityManager present: "
                + oldManagerInstalled());

        System.out.println("Status: " + (feature >= 24
                ? "permanently disabled"
                : "legacy, check runtime configuration"));

        HostApi api = new ReadOnlyHostApi();
        System.out.println("Read via host API: "
                + api.readSetting());

        try {
            api.changeSetting("new-config");
            System.out.println("Unexpected host API success");
        } catch (SecurityException expected) {
            System.out.println("Write via host API: denied");
        }
    }
}
```

Biên dịch trên Java 17+:

```bash
javac --release 17 SecurityBoundaryDemo.java
java SecurityBoundaryDemo
```

Đầu ra đã kiểm chứng trên **OpenJDK 24**, biên dịch đích **Java 17**:

```text
Java feature: 24
SecurityManager present: false
Status: permanently disabled
Read via host API: safe-config
Write via host API: denied
```

Nếu chạy trên **JDK 17–23**, dòng `Java feature` và `Status` sẽ khác; `SecurityManager present` có thể thay đổi theo việc manager có được bật hay không. Ví dụ **không bảo đảm stdout y hệt trên mọi JDK**. Cũng không nên suy đoán feature version khi dùng runtime vendor tùy biến: hãy quan sát giá trị chương trình in ra.

### Tại sao có @SuppressWarnings("removal")?

`System.getSecurityManager()` được đánh dấu deprecated for removal từ Java 17. Annotation ở ví dụ chỉ nhằm **giữ compiler output gọn cho bài kiểm tra compatibility**. Nó **không** làm phương thức trở lại thành API nên dùng, không thay đổi runtime behavior và **không được xem là giải pháp migration**.

Trong production code mới, nếu bạn không tích hợp legacy code nào, tốt nhất **không cần gọi `getSecurityManager()`**. Hãy tập trung vào security boundary thật sự do ứng dụng/hạ tầng thiết kế.

### Vì sao ReadOnlyHostApi không phải sandbox?

Method `changeSetting` chủ động ném `SecurityException`. Đây chỉ là **hạn chế do host API đặt ra với caller tuân thủ contract**.

Một plugin tùy ý chạy trong **cùng JVM** vẫn có thể cố gọi `java.nio.file.Files`, `java.net.Socket` hoặc APIs khác bằng chính code của nó. `ReadOnlyHostApi` không chặn được các lối truy cập ấy chỉ vì nó ném exception trong một method.

Do đó **không dùng API wrapper đơn thuần làm ranh giới thực thi mã độc**. Nó hữu ích cho ứng dụng/plugin đáng tin và thiết kế least-authority ở tầng nghiệp vụ; với code không đáng tin cần **OS/process isolation**.

## 5. ClassLoader và SecurityManager giải quyết hai câu hỏi khác nhau

`ClassLoader` chủ yếu trả lời: **Lớp nào được tìm/định nghĩa, bởi loader nào và dưới namespace nào?**

`SecurityManager` lịch sử trả lời: **Thao tác nhạy cảm này có được policy cho phép trong ngữ cảnh đang thực thi không?**

Ví dụ:

```text
CustomClassLoader
    |
    +--> findClass("plugin.Worker")
    |       |
    |       +--> defineClass(bytecode)
    |                 |
    |                 +--> runtime class identity
    |
    +--> loadClass("shared.api.Plugin")
            |
            +--> delegate to parent
```

Việc loader tạo namespace riêng cho `plugin.Worker` không tự hạn chế quyền đọc tệp hoặc gọi subprocess. Dù plugin nằm trong một loader riêng, code của nó vẫn chạy trong **cùng process** nếu không có boundary khác.

| Cơ chế | Nó làm tốt điều gì? | Điều không thể tự đảm bảo |
|---|---|---|
| Parent delegation | Dùng chung kiểu nền tảng và shared API | Không bảo đảm plugin không truy cập filesystem/network |
| Defining ClassLoader riêng | Class identity, dependency isolation, loader lifecycle | Không phải sandbox OS/runtime permissions |
| `ProtectionDomain`, `CodeSource` | Ghi nhận provenance/metadata và hỗ trợ các cơ chế tương ứng | Không tự biến class thành untrusted/sandboxed ở JDK mới |
| SecurityManager lịch sử | Một số permission checks khi được bật trong JDK hỗ trợ | Không là security boundary khả dụng từ JDK 24 |
| JPMS `exports` / `opens` | Kiểm soát truy cập giữa named modules và reflection/package resources | Không phải chặn hệ thống tệp, network hay mọi native APIs |
| Process/container/OS policy | Có thể áp đặt các quyền ở ranh giới hệ điều hành phù hợp | Cần cấu hình thật, không tự an toàn chỉ vì chạy trong container |

**Điểm rất dễ nhầm:** “Một plugin một loader” có thể giúp các phiên bản `com.vendor.Library` sống song song, nhưng không có nghĩa mỗi plugin có một tập OS permissions riêng.

## 6. ProtectionDomain, CodeSource và Permission vẫn xuất hiện — hiểu đúng ngữ cảnh

Các ví dụ custom loader lâu năm thường viết:

```java
ProtectionDomain domain =
        new ProtectionDomain(codeSource, permissions, loader, null);

Class<?> type = defineClass(
        binaryName, bytes, 0, bytes.length, domain);
```

Đây là **snippet minh họa**, cần có biến và imports thực tế trong một subclass `ClassLoader`.

Trong thiết kế lịch sử, `ProtectionDomain` có thể mang `CodeSource` (URL, certificates) và collection `Permission` được cấp; SecurityManager/AccessController dùng ngữ cảnh để đánh giá nhiều access checks.

Nhưng:

- **Tạo ProtectionDomain không tự bật SecurityManager**.
- Truyền `PermissionCollection` vào `defineClass` **không bảo đảm** JDK 24 áp dụng sandbox trên mỗi thao tác Java API.
- Với JDK 24, nhiều APIs từng phục vụ SecurityManager có behavior “degraded”; ví dụ theo hướng dẫn Oracle JDK 24/25, `Policy` không còn dùng để cấp quyền thực thi như mô hình cũ.
- `ProtectionDomain.getCodeSource()` vẫn hữu ích trong một số tác vụ provenance/diagnostics, nhưng provenance **khác** authorization.
- Lấy URL code source không chứng minh bytecode là đáng tin, không xác minh chữ ký và không thay thế bảo vệ supply chain.

Nếu đọc source/framework cũ có `SecureClassLoader`, `ProtectionDomain` hoặc permission checks, **không lập tức kết luận rằng nó an toàn như bản triển khai cũ ở JDK 8/11**. Phải xem phiên bản runtime và lớp bảo vệ khác của deployment.

## 7. AccessController.doPrivileged và checkPermission không còn đồng nghĩa kiểm soát quyền

Trong mô hình lịch sử, `AccessController.doPrivileged(...)` thường xuất hiện ở code thư viện cần thực hiện một thao tác được cấp quyền có kiểm soát, trong bối cảnh stack-based permission checking.

Ví dụ cũ:

```java
// Mẫu legacy để nhận diện khi đọc code; không khuyến nghị dùng mới.
return AccessController.doPrivileged(
        (java.security.PrivilegedAction<String>)
        () -> System.getProperty("example.setting"));
```

Đây là **snippet minh họa trong method** có kiểu `AccessController` được import; không phải chương trình độc lập.

**Trên JDK 24+:**

- Các `AccessController.doPrivileged(...)` variants còn tồn tại **chạy action trực tiếp**, như khi không có SecurityManager trong các phiên bản cũ.
- `AccessController.checkPermission(...)` theo đặc tả đã thay đổi sẽ **luôn ném `AccessControlException`**.
- `SecurityManager.check...` variants có thể **luôn ném `SecurityException`** trong API đã bị degraded.
- `System.getSecurityManager()` luôn trả **`null`**.
- `System.setSecurityManager(...)` luôn ném **`UnsupportedOperationException`**.

**Không suy diễn sai hai chiều:**

1. Vì `doPrivileged` còn chạy, **không** có nghĩa security policy cũ còn có hiệu lực.
2. Vì `checkPermission` ném exception, **không** có nghĩa toàn hệ thống đang được bảo vệ bởi policy; gọi trực tiếp API legacy đã đổi semantics không phản ánh access control của filesystem/network.

Từng API có behavior riêng. Đừng tự tổng quát “tất cả SecurityManager APIs đều no-op”; ở JDK 24 có phương thức no-op, phương thức trả `null`, và phương thức luôn ném exception.

## 8. SecurityException không chứng minh đã bật SecurityManager

`SecurityException` là loại exception phổ biến của Java được dùng cho nhiều ràng buộc **không phụ thuộc** việc có installed SecurityManager.

Ví dụ trong class loading:

```java
// Bên trong một custom ClassLoader subclass:
return defineClass("java.fake.Reserved", bytes, 0, bytes.length);
```

Đây là **snippet minh họa** (cần class-file bytes phù hợp). `ClassLoader#defineClass` có quy tắc riêng: custom/application loader thông thường không được định nghĩa class có tên bắt đầu `java.`. `SecurityException` có thể xảy ra **ngay cả khi `System.getSecurityManager() == null`**.

Một số nguyên nhân khác cần phân biệt:

- Không nhất quán signer certificates khi cùng loader định nghĩa classes trong một package.
- Custom library/framework tự ném `SecurityException` theo chính sách riêng.
- Một API/loader kiểm tra namespace/package/bytecode/môi trường và từ chối.
- Trên JDK lịch sử, SecurityManager thực sự từ chối một Permission.

Do đó chẩn đoán phải đọc **stack trace, nguyên nhân và JDK version**, không chỉ tên `SecurityException`.

### Một bảng so sánh ngắn

| Triệu chứng | Có chắc do SecurityManager? | Hướng kiểm tra |
|---|---|---|
| `ClassNotFoundException` | Không | Tên, classpath/module path, defining loader, parent delegation |
| `SecurityException: Prohibited package name: java...` | Không | Quy tắc `ClassLoader#defineClass` dành cho `java.*` |
| `IllegalAccessError` | Không | Java access rules, runtime package và module access |
| `InaccessibleObjectException` | Không | Reflection/JPMS `opens` và caller module |
| `UnsupportedOperationException` ở `System.setSecurityManager` (JDK 24+) | Có liên quan API legacy bị vô hiệu hóa | Nâng cấp thiết kế, không tìm flag bật lại |
| Startup error khi `-Djava.security.manager=allow` trên JDK 24+ | Có liên quan cơ chế bị vô hiệu hóa | Xóa cấu hình legacy và thay cách ly khác |

Đừng “chữa” các lỗi này bằng cách cài SecurityManager mới. Điều đó không giải quyết class/module identity và từ JDK 24 cũng không khả thi.

## 9. JPMS là một ranh giới khác, không phải sandbox cho plugin

Java 9+ có **Java Platform Module System (JPMS)**, khai báo:

```java
module host.api {
    exports host.api;
}
```

```java
module plugin.alpha {
    requires host.api;
}
```

Đây là **hai file `module-info.java` minh họa ở hai modules khác nhau**, không ghép thành một file nguồn.

JPMS giúp:

- Tổ chức dependencies qua `requires`.
- Chỉ định public packages được truy cập từ module khác bằng `exports`.
- Quy định reflection/deep access qua `opens`.
- Phát hiện một số module graph/split package conflicts.
- Quản lý plugin modules trong `ModuleLayer` khi kiến trúc phù hợp.

Nhưng nếu plugin code trong `plugin.alpha` được chạy **trong cùng JVM process**, JPMS không tự ngăn nó gọi các API filesystem/network mà module đó có thể truy cập. Một module descriptor hợp lệ **không phải policy tài nguyên kiểu SecurityManager**.

### ClassLoader không tự “mở” mọi package của module

Một custom loader có thể tìm được class file, nhưng việc gọi reflection vào private members của một named module vẫn chịu quy tắc `opens`. Ngược lại, thêm `--add-opens` có thể cấp một phạm vi reflective access, **không** biến custom loader thành sandbox hoặc cấp một bộ quyền file độc lập.

Vì vậy ba câu hỏi phải tách biệt:

1. Loader nào tìm/định nghĩa class?
2. Caller module có quyền truy cập package/member không?
3. Code/process có được phép dùng tài nguyên hệ điều hành không?

Ba câu trả lời này thuộc những lớp kiểm soát khác nhau.

## 10. Những gì ứng dụng Java hiện đại nên làm thay vì SecurityManager

### A. Code đáng tin: dùng contract rõ và kiểm soát ở tầng ứng dụng

Nếu các plugin được **tin cậy và phát hành cùng tổ chức**, thiết kế:

- Shared SPI/DTO với API nhỏ và versioning rõ ràng.
- Host API chỉ cung cấp các thao tác plugin thật sự cần.
- Access checks ở service boundary (tenant, user, RBAC, quota, audit).
- Input validation, authentication/authorization ở các điểm tiếp nhận.
- Secrets không phát tán qua global static fields/system properties.
- Logging và exception handling nhất quán.

Đây là kiến trúc sạch và dễ kiểm thử, nhưng **không phải ranh giới chống plugin độc hại khi cùng process**. Code tùy ý vẫn có thể gọi APIs khác nếu môi trường cho phép.

### B. Plugin không đáng tin: process isolation

Nếu cần chạy code của khách hàng hoặc third-party không tin cậy, cân nhắc:

```text
Host Process
  |
  | validated RPC/IPC messages
  v
Plugin Worker Process
  |
  +-- OS user/permissions riêng
  +-- filesystem mounts hạn chế
  +-- network policy/egress hạn chế
  +-- CPU/memory/process quotas
  +-- short-lived credentials
  +-- timeout và kill/restart
```

Các biện pháp có thể gồm **containers**, VM isolation/hypervisors, Linux namespace/seccomp, Windows sandbox/job objects hoặc những cơ chế macOS phù hợp. Không một công nghệ nào tự an toàn bằng tên gọi; cần cấu hình và kiểm thử quyền thực tế.

Hãy thiết kế host↔plugin interface bằng dữ liệu đơn giản hoặc schema (JSON, Protobuf...) để tránh lộ object references nội bộ và dễ giới hạn tài nguyên.

### C. Least privilege ở OS/cloud boundary

- Không chạy plugin process với quyền administrator/root nếu không cần.
- Chỉ mount các thư mục phải đọc/ghi; phân tách read-only và writable storage.
- Giới hạn network egress, DNS, socket/listening ports theo yêu cầu.
- Dùng credentials thời hạn ngắn và scope hẹp.
- Giới hạn CPU, memory, số process/thread và thời gian chạy.
- Cô lập secrets và log dữ liệu nhạy cảm có kiểm soát.
- Xác minh chữ ký/artifact provenance, dependency scanning và update policy.

**SecurityManager không còn là nơi triển khai những yêu cầu đó trên Java 24+.**

## 11. Khi đang bảo trì framework/plugin cũ

Một số code đã viết từ JDK 8/11 có thể:

```java
@SuppressWarnings("removal")
static void legacyCheck() {
    SecurityManager sm = System.getSecurityManager();
    if (sm != null) {
        sm.checkPermission(
                new java.io.FilePermission(
                        "config.properties", "read"));
    }
}
```

Đây là **snippet legacy minh họa**, không phải biện pháp authorization cho code mới.

- Trên JDK 17 khi có SecurityManager thật, check có thể từ chối thao tác theo policy hiện hành.
- Trên JDK 24+, `System.getSecurityManager()` luôn trả `null`, nên nhánh `if` sẽ không chạy. Không có permission gate nào ở đoạn code đó.
- Nếu một thư viện tự gọi `AccessController.checkPermission` không điều kiện trên JDK 24+, nó có thể **ném exception không điều kiện**, khiến chương trình hỏng theo cách khác.
- Với code chứa `doPrivileged`, behavior vẫn có thể là chạy action ngay, nhưng không có mô hình stack-based permission gating cũ.

**Việc code cũ vẫn compile/runs không chứng minh mô hình bảo mật còn giữ nguyên.** Cần kiểm tra chính xác tác dụng của từng API trên JDK target.

### Kế hoạch migration thực tế

1. **Chốt runtime hiện tại và mục tiêu:** `java -version`, JDK vendor, patch release, options startup.
2. **Tìm cấu hình lịch sử:** `-Djava.security.manager`, `-Djava.security.policy`, policy files, custom `SecurityManager` classes.
3. **Tìm API deprecated:** `System.getSecurityManager`, `System.setSecurityManager`, `SecurityManager`, `AccessController`, `Policy` và các `Permission` checks.
4. **Phân loại mục đích:** code thật sự dùng enforcement, chỉ kiểm tra sự hiện diện, hay dùng `doPrivileged` vì compatibility?
5. **Xác định threat model:** code từ nguồn không tin cậy, sandbox tài nguyên, ngăn `System.exit`, restrict filesystem/network hay chỉ permission ở nghiệp vụ?
6. **Chọn cơ chế thay:** process/OS boundary cho mã không tin cậy; authorization/capability API cho code tin cậy; bytecode instrumentation nếu use case là intercept APIs trong một môi trường kiểm soát, với hạn chế riêng.
7. **Thử nghiệm JDK 24+:** không sử dụng startup flags bị cấm; test các code paths formerly secured.
8. **Dọn deprecated calls:** không chỉ tắt warnings; thay assumptions bị lỗi và update tests/runbooks.
9. **Kiểm tra security sau migration:** xác minh không mở thêm quyền ngoài dự kiến và không tạo bypass khi `getSecurityManager() == null`.
10. **Theo dõi phiên bản tiếp theo:** API có thể bị loại bỏ trong tương lai, nên tránh tích lũy code chỉ chạy vì compatibility tạm thời.

### Các lệnh hỗ trợ kiểm kê

```bash
java -version
javac -version

# Quét class/JAR được biên dịch để phát hiện APIs deprecated
# (tham số/khả năng hỗ trợ phụ thuộc phiên bản công cụ).
jdeprscan --release 17 path/to/application.jar
```

Lệnh `jdeprscan` là **ví dụ chẩn đoán**; thay `path/to/application.jar` bằng artifact thực. Kết quả phụ thuộc file được quét và JDK chứa công cụ. Không nên chỉ quét một JAR rồi kết luận mọi dynamic/reflection use of SecurityManager đã được tìm thấy; hãy kết hợp source/config search và kiểm thử.

Đừng dùng `jdeps --jdk-internals` như cách kiểm tra toàn bộ deprecated SecurityManager APIs; nó có mục đích khác (phân tích sử dụng internal JDK APIs).

## 12. Có thể dùng Java agent để chặn System.exit không?

Một use case từng dùng SecurityManager là chặn plugin gọi `System.exit(int)`. Theo tài liệu Oracle cho JDK 24+, khi SecurityManager đã bị vô hiệu hóa, có thể dùng **agent/bytecode instrumentation** trong những trường hợp cần kiểm soát calls:

```text
Class loading
    |
    +--> ClassFileTransformer
             |
             +--> tìm bytecode gọi System.exit(int)
             +--> thay bằng một đoạn ném RuntimeException
    |
    +--> JVM định nghĩa class đã được transform
```

Đây là mô hình công cụ, không phải giải pháp sandbox tổng quát.

**Cảnh báo:** Instrumentation có thể bị bỏ qua qua các lối gọi khác (native code, reflection, method handles, alternate APIs, attach/agent configuration, dynamic class loading...) nếu threat model không được xử lý đầy đủ. Nếu mã plugin thực sự **không đáng tin**, một agent chặn vài method **không thay thế OS isolation**.

Khi cần bảo vệ điều kiện “một plugin không thể kết thúc JVM của host”, giải pháp robust thường là **chạy plugin ở process riêng** để process-level actions không đồng nghĩa hủy cả host.

## 13. Lưu ý về bản thân ClassLoader và bytecode security

`ClassLoader` có ích cho namespace và plugin lifecycle, nhưng vẫn có những **ràng buộc nội tại** của JVM:

- Không phải loader ứng dụng nào cũng được `defineClass` tùy ý trong namespace `java.*`.
- JVM verifier/linker kiểm tra class-file format và type safety theo quy tắc JVM.
- Runtime class identity dựa trên **(binary name, defining loader)**.
- Runtime package identity dựa trên **(package name, defining loader)**, ảnh hưởng package-private access.
- JPMS `exports`/`opens` và module resolution vẫn áp dụng.
- Security-sensitive native libraries/OS privileges có những chính sách riêng.

Những quy tắc này vẫn quan trọng ở JDK 24 **mà không cần SecurityManager**. Nhưng sự tồn tại của verifier, `java.*` restriction hoặc module encapsulation **không biến ClassLoader thành sandbox quyền file/network**.

Ví dụ, `ClassLoader#defineClass` có thể ném `SecurityException` khi một custom loader cố định nghĩa `java.fake.Reserved`; sự kiện đó không nói rằng permission policy JDK 8 đã quay lại.

### Kết luận về các lớp bảo vệ

```text
Untrusted plugin code
    |
    +--> ClassLoader: namespace/classes/delegation
    |
    +--> JVM verifier, linking, type identity
    |
    +--> JPMS: modules/API/reflection access
    |
    +--> Host API authorization: business contract
    |
    +--> Process/OS/cloud controls: security boundary thực tế
```

Các lớp bảo vệ **bổ sung** cho nhau nhưng không cùng vai trò. Với JDK mới, **không đặt SecurityManager vào sơ đồ như một bước enforcement còn hoạt động**.

## 15. Câu hỏi tự kiểm tra

**1. JDK 17 đã làm gì với SecurityManager?** Đánh dấu **deprecated for removal** theo JEP 411; không phải loại bỏ ngay.

**2. Từ phiên bản nào SecurityManager bị permanently disabled?** Từ **JDK 24**, theo JEP 486.

**3. `System.getSecurityManager()` trả gì trên JDK 24+?** `null` theo API behavior mới.

**4. `System.setSecurityManager(...)` trên JDK 24+ có thể cài manager nếu cấu hình `allow` không?** Không. Method ném `UnsupportedOperationException`; flag cho phép/bật manager tại startup gây lỗi khởi tạo JVM.

**5. `AccessController.doPrivileged` có tự nâng quyền trên JDK 24 không?** Không. Nó thực thi action như khi không có SecurityManager, không cung cấp cơ chế permission-based escalation cũ.

**6. `AccessController.checkPermission(...)` trên JDK 24 có thể dùng để thay permission service nội bộ không?** Không. API này có behavior bị thay đổi, có thể ném `AccessControlException` không điều kiện; cần thiết kế authorization riêng.

**7. Một plugin có ClassLoader riêng có bị chặn đọc file tự động không?** Không. Loader quản lý nạp/định danh classes, không phải sandbox OS.

**8. `ProtectionDomain` có đủ để cấm plugin mở socket không?** Không, đặc biệt với SecurityManager bị vô hiệu hóa; cần boundary runtime/OS thực sự được enforce.

**9. `SecurityException` khi `defineClass("java.fake.X", ...)` có chứng minh SecurityManager đang bật không?** Không. Quy tắc namespace `java.*` của `defineClass` độc lập với installed manager.

**10. JPMS và SecurityManager có cùng nhiệm vụ không?** Không. JPMS giải quyết module/API access; SecurityManager lịch sử nhắm tới permission checks của một số thao tác tài nguyên.

**11. Khi migrate từ Java 8/11 sang JDK 24+, tìm những gì?** Startup flags/policy files, custom manager, calls tới `get/setSecurityManager`, `AccessController`, `Policy` và các lớp bảo vệ dự kiến còn hiệu lực.

**12. Cách an toàn hơn để chạy plugin không đáng tin trên JDK hiện đại là gì?** Cô lập bằng process/container/OS policy với quyền tối thiểu, resource limits, IPC contract và kiểm thử threat model.

# Tách tiến trình khi cần ranh giới bảo mật mạnh hơn ClassLoader

`ClassLoader` là một công cụ **nạp và cô lập tên kiểu Java**, không phải sandbox đáng tin cậy cho mã tùy ý. Nếu host nạp plugin bằng `URLClassLoader`, plugin vẫn **chạy trong cùng tiến trình JVM** với host: cùng heap/process, thường cùng quyền hệ điều hành, có thể tác động tới các tài nguyên dùng chung và không được cô lập khỏi sự cố JVM-level như làm cạn bộ nhớ hoặc dừng tiến trình.

Khi plugin, bộ xử lý tài liệu, script engine hoặc thư viện của đối tác **không hoàn toàn tin cậy**, một phương án mạnh hơn là **đưa phần chạy rủi ro sang JVM/tiến trình riêng**, giao tiếp với host qua một giao thức có kiểm soát, và áp dụng **giới hạn của hệ điều hành hoặc môi trường container/VM**. Tuy nhiên, **chỉ gọi `ProcessBuilder.start()` không biến chương trình con thành sandbox**. Nếu JVM con chạy cùng tài khoản OS, thấy cùng thư mục/secrets và không bị giới hạn mạng/CPU/bộ nhớ, ranh giới bảo mật vẫn yếu.

Bài Knowledge này thuộc **Java core – classloader / Ranh giới bảo mật**. Trọng tâm là **khi nào tách tiến trình, những gì ranh giới mới ngăn được và không ngăn được, cách thiết kế IPC, lifecycle, timeout, giới hạn tài nguyên, kiểm thử và cách áp dụng Java 17+**.

## 1. Phân biệt bốn mức cô lập

| Cơ chế | Cô lập chính | Không tự bảo đảm |
| --- | --- | --- |
| **Một `ClassLoader` khác trong cùng JVM** | Namespace class, phiên bản dependency, runtime class identity, một phần static state | Heap/process/OS permissions/secrets, chống mã độc, giới hạn CPU/RAM |
| **Một JVM process riêng** | Không gian địa chỉ/heap JVM riêng, GC và JVM crash phần lớn không trực tiếp phá heap host, luồng và exit status riêng | Quyền file/network, CPU/RAM toàn máy, dữ liệu bí mật nếu cùng OS identity |
| **Process riêng dưới OS account/sandbox/container có chính sách hạn chế** | Có thể giới hạn filesystem, network, CPU/memory/process count, credentials/capabilities | Không tự tuyệt đối: kernel/container escape, cấu hình sai, IPC vulnerabilities |
| **VM/máy riêng và policy mạng/storage nghiêm ngặt** | Biên giới kernel/máy độc lập hơn, blast radius có thể giảm mạnh | Không loại trừ lỗ hổng hypervisor, OS, protocol hoặc quyền cấu hình |

**Ranh giới không phải boolean.** Cần nhìn vào **threat model**: đối thủ kiểm soát bytecode, input, plugin dependency, payload giao thức hay chỉ là một thư viện có khả năng lỗi? Họ có thể đọc file nào, gọi mạng ra đâu, truy cập thông tin gì và gây thiệt hại tài nguyên ở mức nào?

Nếu mục tiêu chỉ là dùng hai phiên bản thư viện khác nhau trong một ứng dụng đáng tin cậy, `ClassLoader` có thể là lựa chọn nhẹ hơn. Nếu mục tiêu là **ngăn mã có thể độc hại đọc token của host hoặc gọi OS resources**, chỉ thay loader là không đủ.

## 2. Tại sao ClassLoader không phải boundary bảo mật hoàn chỉnh?

Một class được nạp qua child loader:

```java
Class<?> pluginType = pluginLoader.loadClass("plugin.Task");
Object plugin = pluginType.getDeclaredConstructor().newInstance();
```

Đây là **snippet**, giả định biến `pluginLoader` đã khai báo và caller xử lý các exceptions. Dù `pluginType.getClassLoader()` là loader riêng, code plugin vẫn thực thi **trong JVM process hiện tại**.

Những điều có thể xảy ra nếu plugin có khả năng gọi các API phù hợp với quyền runtime:

- Đọc/ghi những file và thư mục mà **process host** có quyền truy cập.
- Gọi network tới những destinations mà network policy cho phép.
- Xem system properties/environment variables được truyền vào process.
- Tạo thread/executor, giữ thread sống, sử dụng CPU và memory.
- Gọi `System.exit(...)` để yêu cầu dừng **JVM host**.
- Dùng reflection/method handles, native interfaces hoặc khả năng runtime khác trong những giới hạn thực tế của JDK và môi trường.
- Gây `OutOfMemoryError`, giữ các object references, khiến garbage collection hoặc JVM process bị quá tải.
- Giữ `ThreadLocal`/TCCL/callback references làm class loader không thể unload, gây memory leak.

Có thể giới hạn API mà host **tự trao qua interface**, nhưng đừng nhầm “API capability do host định nghĩa” với việc loại bỏ những OS/JDK capabilities mà plugin code đã có khi được chạy trong cùng process.

### Security Manager không còn là phương án sandbox lâu dài

Ở **JDK 17**, Security Manager đã **deprecated for removal** (JEP 411), không nên thiết kế sandbox mới phụ thuộc vào nó. Từ **JDK 24**, Security Manager đã **bị vô hiệu hóa vĩnh viễn** (JEP 486), không thể bật để khôi phục mô hình cấp quyền Java cũ.

Vì thế, khi cần một ranh giới thực sự cho code không đáng tin, hãy suy nghĩ tới **OS process identity, sandbox, container, VM, permission, firewall và giao thức giới hạn**, thay vì một `SecurityManager` do host cài trong JVM.

## 3. Khi nào nên chuyển plugin ra một tiến trình riêng?

Những tình huống có lý do rõ ràng:

1. **Chạy code của bên thứ ba có mức tin cậy thấp**: plugin từ marketplace, script hoặc bytecode do đối tác cung cấp.
2. **Phân tích input không tin cậy** bằng thư viện phức tạp: parser tài liệu, ảnh, media hoặc công cụ converter có khả năng crash/hang.
3. **Tác vụ có CPU/RAM khó dự đoán**: chạy thuật toán của khách hàng, máy chấm bài, batch processing.
4. **Cần giảm blast radius** khi native library, JNI, FFM hoặc JVM component lỗi: crash worker không làm sập luôn heap host.
5. **Tách credentials và network access**: worker chỉ được đọc dữ liệu được đưa qua IPC; host giữ database tokens/payment secrets trong môi trường khác.
6. **Giới hạn phiên bản runtime độc lập**: worker có thể chạy JDK/dependency versions khác trong một deployment được kiểm soát.
7. **Muốn thay/restart plugin độc lập**: có health check, process supervision, graceful shutdown và restart theo policy.

Những trường hợp **chưa chắc cần** tách tiến trình:

- Plugin nội bộ đáng tin, chỉ xung đột hai phiên bản JSON library.
- Call path cực kỳ nhạy latency và phụ thuộc nhiều object references đồng bộ.
- Cần chia sẻ object graph lớn, JVM heap state, `synchronized` monitors, không dễ thiết kế giao thức chuyển dữ liệu.
- Cơ chế phân quyền yêu cầu không quá mạnh và toàn bộ code đã được review.

Tách tiến trình có **chi phí startup, memory riêng, serialization, IPC latency, deployment/lifecycle**. Chỉ định threat model và giới hạn đáp ứng trước khi chọn kiến trúc.

## 4. Kiến trúc chuẩn: host giữ quyền, worker chỉ nhận job tối thiểu

```text
                        HOST PROCESS
             ┌──────────────────────────────┐
request ---> │ AuthN/AuthZ, business rules  │
             │ secrets / DB credentials     │
             │ validate + rate limit        │
             └────────────┬─────────────────┘
                          │ request đã thu hẹp
                          │ IPC có framing, size/time limits
                          ▼
             ┌──────────────────────────────┐
             │ WORKER PROCESS / JVM riêng    │
             │ low-privilege OS identity     │
             │ filesystem/network allowlist │
             │ CPU, memory, process quotas   │
             │ chạy plugin/parser/library   │
             └────────────┬─────────────────┘
                          │ kết quả không tin cậy
                          ▼
             ┌──────────────────────────────┐
             │ HOST: parse / validate       │
             │ policy check / persist       │
             └──────────────────────────────┘
```

**Nguyên tắc quyền tối thiểu:** worker không cần quyền trực tiếp tới database production, secret store hay host source tree để xử lý một đoạn text. Host có thể truyền **nội dung input đã giới hạn** thay vì mount toàn bộ filesystem chứa file gốc.

**Dữ liệu từ worker không tự đáng tin** chỉ vì worker là process con do host khởi động. Nếu worker chạy code không đáng tin, output phải được parse/validate như input từ một bên ngoài.

### Gợi ý về capability

Thay vì trao “đường dẫn file hệ thống” rồi để worker tự mở tùy ý, có thể thiết kế API:

```text
Host → Worker:
  job_id = "task-42"
  op = "parse-text"
  bounded_input = <nội dung có size limit>
  format = "plain"

Worker → Host:
  job_id = "task-42"
  status = "ok" | "error"
  bounded_result = <kết quả>
```

Đây là **mô hình giao thức**, không phải wire format đã triển khai. Bản production cần framing, validation, versioning, encoding, timeout và cơ chế xác thực/ủy quyền tương ứng kênh giao tiếp.

## 5. `ProcessBuilder` tạo một subprocess, không tự sandbox

Java SE cung cấp `java.lang.ProcessBuilder`:

```java
ProcessBuilder builder =
        new ProcessBuilder(javaExecutable, "-cp", classPath,
                           "worker.Main", "job-123");
Process process = builder.start();
```

Đây là **snippet**, cần các biến và xử lý `IOException`. Mỗi argument là **một phần tử riêng** của danh sách command, không phải ghép một shell command string rồi hy vọng dấu cách/quote được giải đúng.

Những cấu hình quan trọng:

- **`command(...)`**: executable và từng argument. Không chạy qua `cmd /c` hoặc `sh -c` trừ khi thực sự cần shell; truyền user input vào shell gây nguy cơ command injection.
- **`directory(File)`**: working directory của child, không phải sandbox root.
- **`environment()`**: map biến môi trường child. Mặc định là **bản sao** environment từ parent. Cần loại bỏ secrets và allowlist các biến thực sự cần, nhưng một vài biến hệ thống có thể cần để chạy.
- **`redirectInput`/`redirectOutput`/`redirectError`**: chỉ định nguồn/đích streams.
- **`redirectErrorStream(true)`**: trộn stderr vào stdout; tiện khi đọc log, **không phù hợp nếu stdout là giao thức máy đọc**.
- **`start()`**: khởi động subprocess, có thể ném `IOException`.
- **`Process.waitFor()`**, `waitFor(timeout, unit)`, `exitValue()`, `isAlive()`, `destroy()`, `destroyForcibly()`: quản lý lifecycle.
- **`ProcessHandle`**: PID, status và descendants ở mức API; việc quản lý **cả process tree** phụ thuộc hệ điều hành và chính sách sandbox.

**Cực kỳ quan trọng:** `ProcessBuilder` khởi động một tiến trình **với credentials/quyền OS mà launcher cung cấp**. Java không tự đổi sang user ít quyền hơn, tự bật seccomp, tự giới hạn network hay memory khi gọi `start()`. Những giới hạn đó cần đến cấu hình OS/container/orchestrator đáng tin cậy.

## 6. Thực hành A — JVM host gọi JVM worker độc lập

Bài này chứng minh luồng **launch → stdout → exit status** của một process Java riêng. Nó **không phải ví dụ sandbox**, chỉ đặt nền tảng về IPC/lifecycle.

Cấu trúc:

```text
process-lab/
└── src/
    └── demo/
        ├── EchoWorker.java
        └── ProcessHost.java
```

**`src/demo/EchoWorker.java`:**

```java
package demo;

public final class EchoWorker {
    public static void main(String[] args) {
        if (args.length != 1 || !"PING".equals(args[0])) {
            System.err.println("invalid request");
            System.exit(2);
        }

        System.out.println("PONG");
    }
}
```

**`src/demo/ProcessHost.java`:**

```java
package demo;

import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.nio.charset.StandardCharsets;
import java.nio.file.Path;
import java.util.Locale;

public final class ProcessHost {
    private static String javaExecutable() {
        boolean windows = System.getProperty("os.name")
                .toLowerCase(Locale.ROOT).startsWith("windows");
        String file = windows ? "java.exe" : "java";
        return Path.of(System.getProperty("java.home"), "bin", file)
                .toString();
    }

    public static void main(String[] args) throws Exception {
        String classes = Path.of("out").toAbsolutePath().toString();

        Process process = new ProcessBuilder(
                javaExecutable(), "-cp", classes,
                "demo.EchoWorker", "PING")
                .redirectErrorStream(true)
                .start();

        String reply;
        try (BufferedReader reader = new BufferedReader(
                new InputStreamReader(
                        process.getInputStream(),
                        StandardCharsets.UTF_8))) {
            reply = reader.readLine();
        }

        int exit = process.waitFor();

        System.out.println("worker says=" + reply);
        System.out.println("exit=" + exit);
    }
}
```

Biên dịch và chạy từ thư mục `process-lab` với **JDK 17+**:

```sh
javac --release 17 -d out src/demo/EchoWorker.java src/demo/ProcessHost.java
java -cp out demo.ProcessHost
```

**Stdout của host trên hệ thống cho phép khởi động tiến trình con:**

```text
worker says=PONG
exit=0
```

### Điều bài thực hành chứng minh

1. Host và worker là **hai JVM processes**; worker có `main`, heap, threads và process exit status riêng.
2. `ProcessBuilder` nhận đường dẫn tới executable `java` từ `java.home` của host, tránh phụ thuộc `PATH` shell. Tên file khác trên Windows và Unix-like platforms.
3. `-cp` trỏ tới **đường dẫn tuyệt đối của `out`**, nên worker thấy `demo.EchoWorker`.
4. `"PING"` là argument cố định. `EchoWorker` xác thực nó rồi trả `PONG` ra stdout.
5. `ProcessHost` đọc một dòng UTF-8, chờ child kết thúc và in exit code 0.
6. Dữ liệu được đưa qua **stdout pipe**, **không phải gọi trực tiếp method trong cùng heap**.

**Giới hạn chủ động:** ví dụ chỉ có một dòng output nhỏ từ worker tin cậy. Với worker tùy ý, `readLine()` **không có giới hạn độ dài**, và đọc đến EOF có thể block nếu worker không đóng stdout. Cần size limit, timeout, pumping stdout/stderr, quy tắc hủy/cleanup như phần sau.

**Lưu ý về deployment:** việc tìm `java.home/bin/java` hoạt động trong nhiều JDK/JRE thông thường; container/custom runtime image có thể không kèm executable hoặc không cho phép exec. Application thực tế cần đường dẫn worker runtime **được cấu hình và xác thực**, không tự giả định luôn có đủ quyền spawn process.

## 7. Vì sao không truyền Java object references trực tiếp qua process?

Ở **cùng JVM**, host có thể gọi:

```java
String result = pluginService.execute(request);
```

Đây là snippet minh họa. Host và plugin cùng dùng object references, heap và runtime types tương ứng.

Ở **hai JVMs**, một object reference kiểu `MyRequest` **không thể** được dereference trực tiếp ở process kia. Cần **serialization/protocol**:

- JSON/CBOR/Protobuf/Avro theo schema được phiên bản hóa;
- newline-delimited messages cho demo đơn giản;
- length-prefixed binary frames khi cần chính xác và giới hạn kích thước;
- HTTP/gRPC qua Unix domain sockets/loopback có authentication phù hợp;
- file/queue được kiểm soát về quyền và lifecycle nếu job có dung lượng lớn.

**Không mặc định Java native serialization `ObjectInputStream` là lựa chọn an toàn** cho dữ liệu không tin cậy; nó có bề mặt deserialization nguy hiểm và phụ thuộc class versions. Ưu tiên schema nhỏ, validation rõ và tránh tự instantiate các classes do đối phương chọn.

### Giao thức tối thiểu phải quy định

| Thuộc tính | Câu hỏi cần chốt |
| --- | --- |
| **Framing** | Một message dài bao nhiêu, kết thúc/length-prefix ở đâu? |
| **Encoding** | UTF-8, cấm/làm rõ ký tự newline, NUL, invalid UTF-8 ra sao? |
| **Version** | Phải đổi client/server thế nào khi schema thay đổi? |
| **IDs** | Ghép response đúng request nào, tránh replay/cross-tenant confusion? |
| **Validation** | Field bắt buộc, range, length, enum, payload limits? |
| **Errors** | Phân biệt bad input, worker crash, timeout, protocol violation? |
| **Authentication** | Ai được kết nối tới IPC endpoint? Dựa vào peer identity hay credential nào? |
| **Resource bounds** | Giới hạn message count, bytes, nested objects, parsing time? |

Một process riêng **giảm shared-memory attacks**, nhưng **IPC parser của host** là bề mặt tấn công mới. Giữ nó đơn giản, có giới hạn và fuzz/test với malformed messages.

## 8. Thực hành B — giao thức stdin/stdout không trộn log

Ví dụ sau chạy một worker lâu hơn một request. Giao thức text chỉ chấp nhận `PING`, `UPPER:...` và `QUIT`; stdout chỉ dùng cho **protocol replies**, còn diagnostics thuộc stderr.

Cấu trúc:

```text
ipc-lab/
└── src/demo/
    ├── ProtocolWorker.java
    └── ProtocolHost.java
```

**`src/demo/ProtocolWorker.java`:**

```java
package demo;

import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.io.PrintWriter;
import java.nio.charset.StandardCharsets;
import java.util.Locale;

public final class ProtocolWorker {
    public static void main(String[] args) throws Exception {
        try (BufferedReader input = new BufferedReader(
                new InputStreamReader(
                        System.in, StandardCharsets.UTF_8));
             PrintWriter output = new PrintWriter(
                        System.out, true, StandardCharsets.UTF_8)) {

            output.println("READY 1");

            String request;
            while ((request = input.readLine()) != null) {
                if ("PING".equals(request)) {
                    output.println("PONG");
                } else if (request.startsWith("UPPER:")
                           && request.length() <= 106) {
                    String value = request.substring(6);
                    output.println("DATA:" +
                            value.toUpperCase(Locale.ROOT));
                } else if ("QUIT".equals(request)) {
                    output.println("BYE");
                    break;
                } else {
                    output.println("ERR");
                }
            }
        }
    }
}
```

**`src/demo/ProtocolHost.java`:**

```java
package demo;

import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.io.PrintWriter;
import java.nio.charset.StandardCharsets;
import java.nio.file.Path;
import java.util.Locale;

public final class ProtocolHost {
    static String executable() {
        boolean windows = System.getProperty("os.name")
                .toLowerCase(Locale.ROOT).startsWith("windows");
        return Path.of(System.getProperty("java.home"), "bin",
                        windows ? "java.exe" : "java")
                .toString();
    }

    public static void main(String[] args) throws Exception {
        String cp = Path.of("out").toAbsolutePath().toString();
        ProcessBuilder builder = new ProcessBuilder(
                executable(), "-cp", cp, "demo.ProtocolWorker");

        // stderr là diagnostics riêng, không lẫn vào stdout protocol.
        builder.redirectError(ProcessBuilder.Redirect.INHERIT);
        Process process = builder.start();

        try (BufferedReader fromWorker = new BufferedReader(
                    new InputStreamReader(
                            process.getInputStream(),
                            StandardCharsets.UTF_8));
             PrintWriter toWorker = new PrintWriter(
                    process.getOutputStream(), true,
                    StandardCharsets.UTF_8)) {

            System.out.println(fromWorker.readLine());

            toWorker.println("PING");
            System.out.println(fromWorker.readLine());

            toWorker.println("UPPER:java");
            System.out.println(fromWorker.readLine());

            toWorker.println("QUIT");
            System.out.println(fromWorker.readLine());
        }

        System.out.println("exit=" + process.waitFor());
    }
}
```

Biên dịch/chạy từ thư mục `ipc-lab`:

```sh
javac --release 17 -d out src/demo/ProtocolWorker.java src/demo/ProtocolHost.java
java -cp out demo.ProtocolHost
```

**Stdout khi worker và host chạy theo đúng giao thức:**

```text
READY 1
PONG
DATA:JAVA
BYE
exit=0
```

### Phân tích

- Worker in `READY 1` (protocol version) rồi chờ request trên stdin.
- `PrintWriter(..., true, UTF_8)` auto-flush sau `println`, tránh host đợi message chưa được flush.
- Host ghi từng request, đọc một reply tương ứng, đóng streams và chờ exit code.
- `redirectError(INHERIT)` cho worker diagnostics đi tới stderr của host process; stdout tiếp tục chỉ có protocol.
- `Locale.ROOT` làm phép uppercase cho command data không phụ thuộc locale mặc định của máy.
- `QUIT` khiến worker trả `BYE` rồi thoát bình thường.

**Không dùng giao thức demo này cho input bất kỳ mà chưa harden:** `BufferedReader.readLine()` có thể nhận dòng quá dài trước khi code kiểm tra `request.length()`; đây **không phải giới hạn RAM thật sự**. Production phải giới hạn **số bytes trước hoặc trong lúc đọc**, dùng bounded parser/frame, deadline, schema, request ID và quy tắc EOF/partial response.

**Không dùng stdout cho debug print trong worker** nếu stdout là protocol. Một thư viện vô tình `System.out.println("debug")` có thể làm host coi log là reply và phá state machine. Log đi stderr hoặc kênh riêng.

## 9. Bảo vệ stdout/stderr pipes để tránh deadlock

Một lỗi phổ biến:

```java
Process process = builder.start();
int code = process.waitFor();
byte[] output = process.getInputStream().readAllBytes();
```

Đây là **mẫu dễ deadlock**, không phải khuyến nghị production. Nếu child liên tục ghi stdout/stderr và pipe buffer đầy, child có thể block khi ghi, còn host đang chờ child exit trong `waitFor()`. Kết quả là cả hai cùng chờ.

Cách thiết kế:

1. **Drain stdout và stderr liên tục** bằng threads/async tasks; hoặc redirect đến file/đích phù hợp.
2. Đặt **giới hạn output** theo bytes, không chỉ số dòng; cắt/kill nếu quá quota.
3. Đặt **deadline tổng thể** cho job, không chỉ `readLine` hoặc `waitFor` riêng lẻ.
4. Khi stdout là protocol, **không merge stderr vào stdout**; xử lý/ghi log stderr riêng.
5. Đóng stdin khi không cần gửi thêm requests để worker nhận EOF.
6. Nếu child cần tiếp tục xử lý, đọc output qua **bounded queues** và backpressure rõ ràng.
7. Đừng giữ toàn bộ output bằng `readAllBytes()` khi worker có thể xuất vô hạn dữ liệu.

Có thể dùng `redirectOutput(ProcessBuilder.Redirect.DISCARD)` nếu output **không cần**, hoặc `redirectOutput(file)` trong môi trường đã giới hạn dung lượng file/log. Redirect tới file mà không có quota vẫn có thể làm đầy disk.

### Chi tiết về charset

Text protocol phải thống nhất UTF-8 trên **cả hai chiều**. `InputStreamReader(..., UTF_8)` và `PrintWriter(..., UTF_8)` tránh phụ thuộc platform default charset. Nhưng UTF-8 **không tự xác thực cấu trúc JSON/message**; vẫn cần parser, schema và length limits.

## 10. Timeout là điều kiện cần, nhưng không đủ

Một worker có thể:

- treo do deadlock hoặc vòng lặp;
- mất kết nối;
- bị OS scheduler trì hoãn;
- fork thêm child processes;
- tiêu thụ CPU/memory trước khi host phát hiện timeout;
- hoàn tất tác vụ nhưng không gửi response do protocol error.

`Process.waitFor(long timeout, TimeUnit unit)` trả **`boolean`**: `true` khi process đã kết thúc trong khoảng chờ; `false` khi hết thời gian. Nó **không tự kill worker**.

Pattern lifecycle:

```java
boolean finished = process.waitFor(2, TimeUnit.SECONDS);
if (!finished) {
    process.destroy();
    if (!process.waitFor(500, TimeUnit.MILLISECONDS)) {
        process.destroyForcibly();
        process.waitFor();
    }
    throw new java.util.concurrent.TimeoutException(
            "Worker exceeded deadline");
}
int exitCode = process.exitValue();
```

Đây là **snippet**, cần import `TimeUnit`, biến `process` và caller xử lý `InterruptedException`. Với input/output streams còn mở, host vẫn phải có **đọc/ghi có giới hạn và cleanup**. Không đọc một dòng blocking mãi rồi mới bắt đầu chờ timeout, vì như vậy `waitFor(timeout)` có thể không bao giờ được gọi.

`destroy()` yêu cầu dừng theo cơ chế của nền tảng; `destroyForcibly()` là yêu cầu mạnh hơn nhưng quá trình kết thúc có thể không xảy ra tức thời. Sau đó nên `waitFor`/cleanup, kiểm tra lifecycle thực tế.

## 11. Thực hành C — giết worker vượt deadline

Ví dụ độc lập này **không chờ stdout**. Child cố ngủ lâu, host có timeout ngắn, làm sạch process rồi báo trạng thái.

**`src/demo/SlowWorker.java`:**

```java
package demo;

public final class SlowWorker {
    public static void main(String[] args) throws Exception {
        Thread.sleep(30_000);
    }
}
```

**`src/demo/TimeoutHost.java`:**

```java
package demo;

import java.nio.file.Path;
import java.util.Locale;
import java.util.concurrent.TimeUnit;

public final class TimeoutHost {
    static String javaExecutable() {
        boolean windows = System.getProperty("os.name")
                .toLowerCase(Locale.ROOT).startsWith("windows");
        return Path.of(System.getProperty("java.home"), "bin",
                        windows ? "java.exe" : "java").toString();
    }

    public static void main(String[] args) throws Exception {
        String cp = Path.of("out").toAbsolutePath().toString();

        Process process = new ProcessBuilder(
                javaExecutable(), "-cp", cp, "demo.SlowWorker")
                .redirectOutput(ProcessBuilder.Redirect.DISCARD)
                .redirectError(ProcessBuilder.Redirect.DISCARD)
                .start();

        boolean finished = process.waitFor(
                250, TimeUnit.MILLISECONDS);

        if (!finished) {
            process.destroyForcibly();
            process.waitFor();
        }

        System.out.println("timed out=" + !finished);
        System.out.println("alive after cleanup=" +
                process.isAlive());
    }
}
```

Biên dịch/chạy từ thư mục chứa `src/demo`:

```sh
javac --release 17 -d out src/demo/SlowWorker.java src/demo/TimeoutHost.java
java -cp out demo.TimeoutHost
```

**Stdout dự kiến trong điều kiện không có can thiệp từ ngoài:**

```text
timed out=true
alive after cleanup=false
```

Tại sao?

- `SlowWorker` ngủ 30 giây nếu không bị dừng.
- Host chỉ chờ tối đa 250 ms, nên trong môi trường bình thường worker chưa thoát.
- `destroyForcibly()` yêu cầu dừng child process, `waitFor()` đợi cleanup hoàn tất.
- `isAlive()` sau `waitFor()` là `false`.
- `Redirect.DISCARD` tránh tồn tại pipe output chưa được drain trong ví dụ worker không trả dữ liệu.

**Lưu ý tính thực nghiệm:** timeout 250 ms là giá trị để quan sát, **không phải SLA hay ngân sách khởi động JVM được khuyên dùng**. Máy rất chậm hoặc process bị can thiệp có thể cho hiện tượng khác; production dùng deadline phù hợp, xử lý launch failure/interrupt và có thể dùng process supervisor. Một tiến trình con cũng có thể **spawn descendants** mà việc kill một PID không dọn sạch hết; cần group/job/cgroup/process-tree policy của OS.

## 12. Giới hạn CPU/RAM không nên chỉ dựa vào flags Java

Dù worker là một JVM riêng, cùng host vẫn có thể tranh tài nguyên vật lý. Các biện pháp:

| Rủi ro | Kiểm soát mạnh hơn |
| --- | --- |
| Dùng heap quá lớn | `-Xmx` giới hạn Java heap, cộng với **OS/container memory limit** cho native/off-heap/metaspace/stacks |
| CPU dùng vô hạn | CPU quota/cgroups/job limits và timeout/watchdog |
| Sinh quá nhiều threads/processes | pids/task quotas, process/job limits, runtime worker pool |
| Ghi output/log không giới hạn | quota disk/output bytes, bounded pipes, log rotation |
| Mở quá nhiều file/socket | file descriptor limits, network policy, quotas |
| Đọc secrets/host files | OS permissions, mount read-only/allowlist, tách UID/credential |
| Gọi mạng ngoài không kiểm soát | egress firewall/network namespace/allowlist |
| Fork bomb/descendant escape | process groups/cgroups/container PID namespace, supervisor dọn cả cây |
| Gây nghẽn IPC | kích thước frame, request deadline, backpressure, concurrent-job quota |

**`-Xmx256m` không có nghĩa tiến trình Java chỉ dùng 256 MB RAM**: heap không gồm mọi native memory, thread stacks, metaspace, JIT/code cache và một số memory mappings. Cần giới hạn **toàn process/container** ở OS layer.

Ví dụ command **minh họa** khi khởi động worker:

```text
java -Xmx256m -cp worker.jar worker.Main
```

Đây chỉ là **cấu hình heap**. Nó không cấp network/filesystem sandbox và không tạo CPU quota. Đặt flags phù hợp JVM version, load và kiểm tra `java -XshowSettings:vm -version` khi debug thực tế.

## 13. Quyền hệ điều hành: tách process cùng user vẫn nguy hiểm

So sánh:

```text
Host PID 1000, user=app-prod
Worker PID 1001, user=app-prod
```

Dù heap khác nhau, nếu OS permissions cho `app-prod` đọc `/srv/secrets`, worker chạy cùng user cũng có thể đọc những files đó. Worker còn có thể hưởng environment variables, home directory và những mount/network routes của host.

Muốn **ranh giới quyền mạnh hơn**, triển khai có thể cần:

- User/UID riêng chỉ có quyền với các files cần thiết.
- Work directory và writable filesystem riêng, read-only root khi phù hợp.
- Chặn kế thừa credentials/environment không cần thiết.
- Không mount Docker socket, host root directory, SSH keys hoặc cloud credentials vào worker.
- Network egress deny-by-default, chỉ allow đúng endpoints.
- Giảm Linux capabilities, bật `no-new-privileges`, sandbox policy như seccomp/AppArmor/SELinux nếu nền tảng hỗ trợ.
- Windows: dùng identity/token/job objects/app container hoặc cơ chế tương đương theo threat model.
- Resource controls cấp OS (cgroups/rlimits/Windows Job Objects), giới hạn pids và thời gian.
- Isolate worker có nguy cơ cao bằng VM hoặc máy riêng khi container không đạt mức tin cậy cần thiết.

**Không có một lời gọi Java SE 17 chuẩn duy nhất** tự bật tất cả các cơ chế này trên mọi OS. Chúng là trách nhiệm của **launcher đáng tin, hệ điều hành và hạ tầng triển khai**.

### Một cấu hình “có process riêng” nhưng vẫn sai

```text
Host và worker:
  user = root
  volume = toàn bộ /var/run và /etc
  cloud env keys được copy đầy đủ
  network = unrestricted
  không có memory/pids quotas
```

Đây là ví dụ **cấu hình cần tránh**. Trong đó tách JVM giảm rủi ro corruption của heap host, nhưng worker vẫn có quyền quá lớn tới máy/hạ tầng. Đừng đánh dấu nó “sandbox an toàn” trong review.

## 14. Environment và tham số: không vô tình đưa bí mật sang worker

Mặc định `ProcessBuilder.environment()` bắt đầu từ một **bản sao môi trường của parent**. Nếu host chứa `DATABASE_PASSWORD`, `CLOUD_TOKEN` hoặc proxy credentials trong environment, worker có thể thừa hưởng chúng.

```java
ProcessBuilder builder = new ProcessBuilder(command);
java.util.Map<String, String> env = builder.environment();

// Chỉ minh họa; chính sách allowlist cần hiểu các biến OS cần thiết.
env.remove("DATABASE_PASSWORD");
env.remove("CLOUD_TOKEN");
```

Đây là **snippet**, cần `command` đã khai báo. Loại vài biến tên biết trước là chưa đủ: có thể còn `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`, `HOME`, `PATH`, `SSH_AUTH_SOCK`, credentials do thư viện tự tạo và những giá trị cần để runtime/loader hoạt động.

Trong triển khai thật:

1. Xác định **danh sách biến tối thiểu** worker phải nhận.
2. Tạo môi trường đã kiểm soát, giữ những biến hệ điều hành/runtime cần thiết.
3. Tránh đưa secrets vào **command-line arguments** vì process listing/logs có thể nhìn thấy.
4. Nếu cần secret cho worker, cung cấp **secret riêng phạm vi hẹp, TTL ngắn** qua kênh phù hợp.
5. Kiểm tra cả **inherited file handles, working directory, volumes, container service account và network routes**.
6. Không tin rằng `environment().clear()` làm worker thành sandbox; process vẫn có OS identity và quyền filesystem/network.

`ProcessBuilder.directory(...)` chỉ đổi working directory, **không hạn chế worker đi ra các đường dẫn khác**. Cần OS/filesystem policy cho điều đó.

## 15. IPC authentication, authorization và request validation

Với một pipe riêng do host tạo cho child, người dùng thường có ít nguy cơ client ngoài kết nối nhầm, nhưng protocol vẫn phải chống output không hợp lệ và worker giả mạo thành công. Với **Unix domain socket, TCP localhost hoặc HTTP/gRPC**, vấn đề authentication và authorization càng quan trọng:

- Chỉ endpoint đáng tin được kết nối.
- Mỗi request có tenant/job identity và giới hạn quyền riêng.
- Messages có version, type và length hợp lệ.
- Worker chỉ được yêu cầu một **tập operation allowlisted**.
- Output được kiểm tra signature/schema khi cần; không coi response là source of truth cho authorization.
- Host không làm việc nguy hiểm chỉ vì worker trả `"allow": true`.
- Có cơ chế rate limit, replay protection và mTLS/peer credentials nếu hạ tầng đòi hỏi.
- Loại bỏ input control characters hoặc dùng encoding/framing an toàn để tránh log/protocol injection.

### Không biến IPC thành remote shell

Một API nguy hiểm:

```text
Host → Worker: {"command": "execute arbitrary OS command"}
```

Nếu worker hoặc caller có thể tùy ý định nghĩa command, sandbox rất dễ bị phá vỡ trong phạm vi quyền hiện có. Thay vì generic exec, cho phép các operation tường minh như `CONVERT_DOCUMENT`, `PARSE_METADATA`, `VALIDATE_JSON` với typed arguments và size quotas.

Ngay cả khi worker đã bị giới hạn quyền, **đừng cấp generic commands nếu không cần**. Nguyên tắc least authority nên áp dụng cho cả OS permissions lẫn protocol capabilities.

## 16. Quan hệ ClassLoader bên trong worker và process isolation

Tách JVM không loại bỏ nhu cầu class loading:

```text
HOST JVM
  HostAppLoader → host API, business code

WORKER JVM
  WorkerAppLoader
       └── optional PluginURLClassLoader → plugin.jar, private deps
```

Worker vẫn có thể dùng `URLClassLoader` để cô lập các phiên bản library **trong worker**. Tuy nhiên, ý nghĩa security vẫn đến từ **process/sandbox boundary**; URLClassLoader chỉ tổ chức namespace nội bộ.

**Không chia sẻ trực tiếp `Class<?>` hoặc `Method` giữa hai JVMs.** Host có thể biết tên service trong giao thức, nhưng không có cùng runtime class identity với worker:

- `Class<?>` chỉ có ý nghĩa trong JVM của nó.
- Plugin implementation trong worker không thể được host ép kiểu trực tiếp sang host `api.Plugin`.
- Cách giao tiếp nên qua **serialized request/response**, không qua Java object references.
- Có thể dùng **shared protocol schema** được compile độc lập cho hai JVMs, nhưng bytes/messages mới là đường truyền, không phải cùng object.
- Worker có thể chạy JDK/runtime mới hơn nhưng protocol phải tương thích.

**So sánh chi phí:** class loader trong cùng JVM có method invocation gần như trực tiếp nhưng thiếu security boundary mạnh; IPC giữa tiến trình tốn serialization/copy/scheduling, đổi lại kiểm soát failure domain và quyền rõ hơn.

## 17. ClassLoader identity, serialization và vấn đề type confusion

Trong một JVM, hai `ClassLoader` định nghĩa `com.example.Message` có thể khiến cast lỗi vì type identity khác. Khi tách process, vấn đề đổi dạng:

- Type `Message` phía host và type `Message` phía worker là **hai runtime types** độc lập ngay cả khi source giống nhau.
- Protocol cần xác định **schema** và mapping, ví dụ JSON object với `type`/`version` được allowlist.
- Không giải mã một chuỗi tên class từ worker rồi gọi `Class.forName(userSuppliedName)` để tự instantiate arbitrary types trong host.
- Không dùng Java serialization của object do worker trả nếu bạn không kiểm soát chặt whitelist/filter và gadget surface.
- Kiểm tra maximum nesting/depth, collection counts, scalar ranges, integer overflow, Unicode normalization khi cần.

Nếu worker trả metadata về tệp nguy hiểm, host vẫn cần kiểm chứng trước khi lưu hoặc thực hiện thao tác hệ thống. Process boundary giúp tách quyền, không thay thế **input validation**.

## 18. Lifecycle: restart, cancellation và graceful shutdown

Một worker dài hạn có thể xử lý nhiều requests. Host phải có trạng thái vận hành:

```text
CREATED → STARTING → READY → BUSY → IDLE
                     │       │
                     ▼       ▼
                   FAILED   STOPPING
                              │
                              ▼
                            EXITED
```

Các bước:

1. Khởi động worker với **cấu hình quyền và resource quotas trước khi giao job**.
2. Thực hiện handshake `READY` có protocol version và timeout.
3. Dùng bounded queue để không nhận vô hạn jobs.
4. Theo dõi per-job deadline, overall worker age và health.
5. Khi timeout/cancel: gửi graceful cancel nếu protocol hỗ trợ; nếu không phản hồi, kill theo policy.
6. Với worker sinh con, supervisor phải xử lý **process group/tree** và hậu quả process orphan.
7. Kiểm tra exit status, stderr bounded logs, và phân biệt crash với lỗi business.
8. Không restart vô hạn theo vòng lặp nóng; dùng backoff, giới hạn attempts và alert.
9. Không reuse worker đã vi phạm protocol hoặc tình trạng memory/FD vượt quota.
10. Khi nâng phiên bản, tạo **new worker process** với artifact mới, drain worker cũ rồi dừng.

**Không hứa “kill là rollback toàn bộ side effects”.** Worker có thể đã ghi file hoặc gọi network trước khi bị kill. Nếu cần atomicity, host phải dùng transaction, staging directory, temp files/rename và idempotency keys.

## 19. Theo dõi lỗi: exception vs exit code vs timeout

| Tình huống | Host nhận được gì? | Cách xử lý |
| --- | --- | --- |
| Provider Java trong cùng JVM ném exception | Java exception, cùng stack/call | Phân loại lỗi và cô lập ở application layer |
| Worker subprocess chủ động báo lỗi nghiệp vụ | Structured response, exit có thể vẫn 0 hoặc nonzero theo protocol | Parse code/message; không suy thành lỗi hạ tầng |
| Worker JVM bị crash hoặc bị OS kill | Exit code, EOF/pipe broken, có thể thiếu response | Fail job, giữ diagnostics an toàn, supervisor restart |
| Worker treo | Không nhận response trước deadline | Timeout, cancel/kill, dọn process tree, báo service unavailable |
| Host–worker protocol sai | Malformed/extra/missing frames | Reject, không tiếp tục state machine không an toàn |
| Host không spawn được worker | `IOException` từ `ProcessBuilder.start()` | Kiểm tra executable, permission, cwd, quota |
| Output vượt size quota | Bounded reader phát hiện | Cắt/hủy job, không nạp toàn bộ bytes vào heap host |
| Worker trả hợp lệ nhưng nội dung sai | Business/schema validation failure | Không commit, báo lỗi có context |
| Worker cố truy cập file bị sandbox deny | OS-level permission failure | Coi là policy violation, kiểm tra audit |
| Container OOM killed | Exit hoặc orchestration reason, không nhất thiết Java `OutOfMemoryError` | Resource metrics, quota, design input |

**Đừng chỉ đọc exit code bằng `waitFor()` rồi suy rằng kết quả an toàn.** Cần cả validation của nội dung và tiêu chí business; worker có thể cố tình trả exit 0 với dữ liệu sai.

### Observability tối thiểu

Ghi log có kiểm soát: `jobId`, worker generation, image/JDK version, sandbox policy version, duration, exit status, deadline, input/output sizes và mã lỗi. Không log raw secrets hay nguyên văn input nhạy cảm theo mặc định. Giới hạn stderr và sanitize log để tránh newline/control-character injection.

## 20. Giới hạn của process separation trong cùng host OS

Process riêng vẫn chia sẻ **kernel** với host. Nếu cả hai chạy chung node:

- Worker có thể làm đầy disk hoặc network throughput nếu không có quotas.
- Một lỗ hổng kernel/container có thể vượt isolation.
- CPU/memory pressure trên toàn máy có thể ảnh hưởng host nếu resource controls chưa đủ.
- Docker/container mặc định có các quyền/mount/network khác nhau tùy cấu hình; “đã dùng Docker” **không tự chứng minh** sandbox an toàn.
- Các tài nguyên được host intentionally share qua mount/socket/credentials có thể trở thành đường tấn công.
- Nếu host chạy với quyền root rồi khởi động worker cùng quyền, privilege boundary hầu như không được cải thiện.

**VM riêng** có kernel khác và có thể tăng mức cách ly, nhưng vẫn phụ thuộc cấu hình, patching, networking, secrets handling. Với hostile code, defense in depth là cần thiết: VM/namespace, allowlist network, OS permissions, quotas, logging và protocol validation.

### Tránh “security theater”

`new ProcessBuilder(...).start()` cộng với `-Xmx` và timeout là **điều kiện tốt để tăng khả năng phục hồi**, nhưng chưa đủ để gọi “mã không tin cậy không thể truy cập tài nguyên host”. Đánh giá riêng **confidentiality, integrity, availability**.

## 21. Deployment patterns: one-shot, worker pool và remote worker

| Mẫu | Ưu điểm | Hạn chế | Phù hợp |
| --- | --- | --- | --- |
| Một JVM cho mỗi request | Cleanup bằng process exit, dễ giới hạn thời gian/memory theo job | Startup/GC overhead lớn | Tác vụ hiếm, độ rủi ro cao, batch |
| Worker JVM dài hạn | Amortize startup, cache parser/JIT/dependencies | State leak, lifecycle phức tạp, nhiều requests chung tiến trình | Throughput cao, input tin cậy hơn |
| Pool N workers hạn chế | Kiểm soát concurrency, chọn version, rolling restart | Scheduler/queue/health complexity | Service production tải vừa/lớn |
| Container/VM mỗi job | Isolation/quotas tường minh hơn nếu OS cấu hình đúng | Cold start, resource/orchestration cost | Thực thi code khách hàng ít tin cậy |
| Remote worker trên node khác | Tách cả máy/kernel, có network policy rõ | Network/ops latency, mTLS, service discovery | Boundary mạnh, dữ liệu và quyền cần cách ly |

Một worker pool vẫn phải chặn **cross-tenant state leakage** giữa jobs: state static trong worker JVM, temp files, cached data hoặc những token còn trong RAM có thể rò sang job tiếp theo. Nếu yêu cầu multi-tenant isolation cao, cân nhắc **mỗi tenant/job một process/VM riêng** thay vì reuse worker toàn cục.

## 22. Những nhầm lẫn phổ biến

- **“Custom ClassLoader sandbox được plugin.”** Sai: nó quản lý loading/namespace, không tự đặt quyền OS.
- **“Plugin không thấy host package thì không gọi file/network được.”** Sai: visibility class khác OS capabilities; nhiều JDK APIs vẫn có sẵn.
- **“Chạy JVM con đã an toàn tuyệt đối.”** Sai nếu cùng UID/mount/network/secrets và không có quotas.
- **“`-Xmx128m` giới hạn tổng memory process ở 128 MB.”** Sai: còn native/off-heap/metaspace/thread stacks.
- **“`directory(...)` khiến worker không thể truy cập đường dẫn khác.”** Sai: nó chỉ đặt current working directory.
- **“`environment().clear()` tạo process không quyền.”** Sai: OS identity và các permissions khác vẫn còn.
- **“`ProcessBuilder` nên nhận một chuỗi shell command có nối user input.”** Không; dùng argument list và tránh shell injection.
- **“Chỉ `waitFor()` rồi mới đọc stdout luôn ổn.”** Sai nếu pipes đầy và child block.
- **“Có timeout nghĩa Java tự kill worker.”** Sai: `waitFor(timeout)` chỉ báo kết quả chờ; cần cleanup.
- **“`destroyForcibly()` tự kill toàn bộ descendants.”** Không bảo đảm; cần OS process group/job handling.
- **“Stdout worker có thể vừa log vừa trả JSON không sao.”** Không nếu stdout là kênh protocol có framing nghiêm ngặt.
- **“Đã có process isolation thì không cần validate response.”** Sai: worker output vẫn không tin cậy.
- **“Java serialization là lựa chọn IPC mặc định an toàn.”** Không nên mặc định dùng cho untrusted data.
- **“Security Manager sẽ thay thế OS sandbox trên JDK mới.”** Sai; JDK 24 đã permanently disable Security Manager.
- **“Kill worker sẽ rollback mọi thay đổi nó thực hiện.”** Sai: external side effects có thể đã xảy ra.
- **“Docker mặc định tương đương VM riêng.”** Sai: container thường chia sẻ kernel và quyền phụ thuộc cấu hình.
- **“Tách process khiến Java ClassLoader không còn cần thiết.”** Sai: worker vẫn có classpath/module loading riêng.
- **“Hai JVM có thể truyền trực tiếp `Class<?>`/object reference.”** Sai: phải có serialization/protocol và schema.

## 23. Checklist trước khi đánh dấu một worker là ‘isolated’

**Threat model và quyền:**

1. Input/code nào được xem là không tin cậy?
2. Worker có chạy dưới OS identity **khác host** không?
3. Worker có nhìn thấy host secrets, config, mounts, sockets không?
4. Network policy có **deny-by-default** nếu workload không cần network không?
5. Có giới hạn CPU/memory/PIDs/FD/disk/output bytes thực sự ở OS/orchestrator không?
6. Có quyền chỉnh sửa host filesystem hoặc dùng Docker socket không?

**IPC và hành vi:**

7. Protocol có version, bounded framing, schema validation và request ID không?
8. Có chặn command injection, deserialization gadgets, path traversal và log injection không?
9. Host coi **mọi response là dữ liệu không tin cậy** và xác thực lại không?
10. Stdout protocol có tách stderr diagnostics, cả hai đều bounded không?
11. Timeout có bao trùm spawn, handshake, request, read/write và shutdown không?
12. Worker có thể spawn grandchildren; OS policy có dọn cả process group/cgroup không?
13. Retry có idempotency/transaction để tránh double side effects không?

**Vòng đời và vận hành:**

14. Có startup readiness, health, cancellation, versioning và exit reason không?
15. Có audit logs/metrics không làm lộ secrets?
16. Worker cũ có thể leak state giữa tenants/jobs không?
17. Có thể rolling restart khi JAR/JDK version đổi mà không làm gián đoạn toàn host không?
18. Security controls có được **kiểm thử bằng hành vi bị từ chối**, không chỉ bằng tài liệu cấu hình không?

Nếu nhiều mục quan trọng chưa đáp ứng, hãy ghi nhận boundary hiện tại là **“separate JVM / fault isolation”**, chưa gọi là **“secure sandbox”**.

## 24. Bài tập mở rộng và kiểm thử

### Bài tập 1 — lỗi runtime trong worker

Đổi `EchoWorker` ở thực hành A để ném `RuntimeException` hoặc `System.exit(7)`. Quan sát host **vẫn chạy**, nhận exit khác 0 hoặc EOF/diagnostics, rồi có thể trả lỗi cho request thay vì sập JVM host. Không dùng exit code 0 để coi mọi kết quả là đúng; phải validate response.

### Bài tập 2 — giới hạn output

Thay worker bằng đoạn code liên tục in nhiều MB dữ liệu. Viết một **bounded stream consumer** trong host, dừng sau ví dụ 64 KiB output, hủy worker và đảm bảo không `readAllBytes()` toàn bộ stream. Đồng thời drain stderr nếu cần, có deadline để không bị block.

### Bài tập 3 — cấm network/file

Đưa worker vào một OS sandbox/container đã cấu hình chỉ cho đọc một input directory và ghi một output directory, chặn network. Yêu cầu worker thử đọc một file ngoài allowlist hoặc kết nối tới destination bị chặn, rồi kiểm tra **thực sự bị OS từ chối**. Đừng dựa vào Java ClassLoader để mô phỏng permission.

### Bài tập 4 — worker protocol sai

Cho `ProtocolWorker` cố tình trả `UNKNOWN 1`, một dòng dài quá quota hoặc đóng stdout giữa reply. Host phải **reject** và dọn process theo deadline, không coi đó là kết quả hợp lệ. Trong thiết kế production, frame decoder phải enforce size **trước khi allocate payload lớn**.

### Bài tập 5 — crash, timeout và retry

Cho worker kết thúc đột ngột rồi test host có phân biệt crash với timeout không, có backoff khi restart không, và có bảo vệ idempotency khi job đã gây side effects. Mục tiêu là vận hành có kiểm soát, không chỉ “gọi lại Java process” mỗi lần lỗi.

## 25. Câu hỏi tự kiểm tra

**1. URLClassLoader cô lập chủ yếu điều gì?** Runtime class namespace/defining loader, dependency versions; không tự cô lập heap/process hay OS permissions.

**2. Tại sao tiến trình riêng là boundary mạnh hơn loader?** Nó có address space/JVM heap/lifecycle độc lập và OS có thể cấp identity/quotas khác.

**3. Tại sao hai JVMs cùng OS user chưa đủ an toàn?** Worker vẫn có thể đọc file/network/secrets mà user đó được phép truy cập.

**4. `ProcessBuilder.start()` có tự bật sandbox không?** Không; nó chỉ khởi động process theo cấu hình command/environment/IO/cwd đã cung cấp.

**5. Có nên ghép `"sh -c " + userInput` để chạy tác vụ worker không?** Không; dễ command injection. Dùng fixed executable + argument list và operation allowlist.

**6. Vì sao không đọc stdout sau `waitFor()` trong mọi trường hợp?** Pipes có thể đầy khiến child block khi ghi và host block chờ exit.

**7. `waitFor(timeout, unit)` có tự kill không?** Không; khi trả `false` caller cần cancellation/destroy/cleanup.

**8. `-Xmx` có giới hạn toàn bộ RAM của JVM không?** Không; còn native/off-heap/metaspace/stacks.

**9. Có thể truyền object Java trực tiếp giữa hai processes không?** Không; cần serialize/protocol hoặc shared-memory mechanism có hợp đồng cụ thể.

**10. Tại sao response của worker vẫn cần validate?** Worker có thể bị compromise, trả dữ liệu sai hoặc gây protocol injection.

**11. `destroyForcibly()` có chắc kill process tree không?** Không; cần OS supervisor/group/cgroup handling khi worker sinh process con.

**12. Đổi `ProcessBuilder.directory` có cô lập filesystem không?** Không; chỉ đổi working directory.

**13. Java Security Manager có dùng được để sandbox trên JDK 24 không?** Không; từ JDK 24 nó permanently disabled.

**14. Khi nào nên dùng VM/container riêng mỗi job?** Khi threat model đòi tách kernel/tenant/credentials hoặc quotas mạnh hơn một process cùng quyền, và chi phí cho phép.

**15. Điều quan trọng nhất khi chọn boundary là gì?** Xác định **đối tượng đe dọa, tài nguyên cần bảo vệ và quyền worker thật sự có**, rồi kiểm thử giới hạn bằng hành vi thực.
