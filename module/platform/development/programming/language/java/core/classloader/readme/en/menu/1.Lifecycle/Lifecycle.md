# Class Loading Lifecycle

Java source code cannot execute merely because a `.class` file exists somewhere on disk. The JVM executes runtime types, represented by `Class<?>` objects, and it needs a controlled process that can locate class bytes, turn them into runtime classes, connect their symbolic references, and initialize their static state.

A **JAR** is simply a common archive format used to package Java class files and resources. You do not need its internal format for this module; the important point is that class bytes may live inside an archive rather than as standalone files.

This chapter establishes that process first. The rest of the module then explains who performs the loading, how loaders cooperate, how loader identity affects type identity, how frameworks cross loader boundaries, how resources are found, and why loaders can become memory-leak roots.

> **Prerequisite bridge:** this module assumes you already know that Java exposes a runtime type through `Class<?>`. If `Class<?>`, runtime type metadata, or reflection are still unfamiliar, review the `class-object` and `reflection` modules first. Here, `Class<?>` is used only as the runtime representation of a type so the focus can stay on how that type enters the JVM.

## <a id="loading-linking-initialization">What a ClassLoader Is and the Runtime Lifecycle</a>

A **ClassLoader** is the Java runtime mechanism that participates in turning a binary class name such as `demo.plugins.HelloPlugin` into a runtime `Class<?>`. For ordinary application classes, a `ClassLoader` locates the class bytes and eventually defines them. The JVM then links and, when required, initializes the resulting class.

That distinction exists because a program is larger than the source files compiled in one command. A running JVM may need classes from the JDK runtime image, the application class path, modules, test tooling, plugin directories, generated bytecode, application servers, or other sources that were not all known as one fixed block when the JVM process started.

Without a loading subsystem, the JVM would need every executable type to be hard-wired into one closed image before startup. Java would lose important runtime capabilities such as loading an application dependency only when it is needed, isolating plugins, discovering providers, or hosting multiple applications with different dependency versions in one process.

In this module, a runtime **namespace** means the mapping from binary class names to runtime types visible/defined through a loader boundary. Two different loaders can both know the name `demo.plugins.HelloPlugin` while mapping it to two different `Class<?>` objects.

The running example uses a few architecture terms:

```text
host
→ the main application

plugin
→ an extension loaded by the host

Plugin API / SPI
→ a shared interface/contract between host and plugin

provider
→ an implementation of that SPI

framework/library
→ infrastructure code that uses the API/SPI to discover and invoke providers
```

### Binary name, class-file path, and class path are different concepts

Suppose the source is:

```java
package demo.plugins;

public final class HelloPlugin {
}
```

For this top-level class:

```text
binary name
→ demo.plugins.HelloPlugin

ordinary class-file path relative to a class-path root
→ demo/plugins/HelloPlugin.class
```

`ClassLoader.loadClass(...)` receives the **binary name**, not a filesystem path such as `/opt/app/demo/plugins/HelloPlugin.class`.

The **application class path** is best understood as a set of locations made visible to the application loader, for example directories and JARs:

```text
build/classes/java/main/
libs/plugin-api.jar
libs/plugins.jar
```

A loader can map:

```text
demo.plugins.HelloPlugin
        ↓
demo/plugins/HelloPlugin.class
```

and look for that relative entry under each class-path root. When a root is a JAR, the entry is inside the archive rather than an independent filesystem class file.

Keep these concepts separate. For a top-level class, some names may look textually similar, but **their roles are different**:

```text
source/package naming
binary class name
class-file/resource path
class-path location
```

> **Advanced — safe to skip on the first pass:** named modules add visibility and encapsulation rules. The basic model remains: **a loader receives a runtime name and locates a representation through the sources visible to it**.

### When does the JVM load a class?

Do not picture the JVM reading every class in every JAR at process startup. Loading is commonly **demand-driven**: a type is loaded/linked when the runtime needs it for execution, dependency resolution, reflection/dynamic loading, or while processing another type.

For example:

```java
import demo.plugins.HelloPlugin;

public final class Demo {
    public static void main(String[] args) {
        System.out.println("start");
    }
}
```

`import` is a **compile-time source-name feature**. It is not a runtime instruction and does not mean `HelloPlugin` has already been loaded or initialized when `Demo` runs.

Operations such as these can cause the runtime to need a type:

```text
new HelloPlugin()
using a member whose symbolic reference must be resolved
Class.forName("demo.plugins.HelloPlugin")
loader.loadClass("demo.plugins.HelloPlugin")
resolving a symbolic reference from another class
```

Do not depend on one universal exact load moment: a JVM may load or link some types earlier when the specification permits it, as long as observable Java semantics are preserved. The durable model is that **not every class is loaded at startup, and loading is still distinct from initialization**.

The broad lifecycle is:

```text
source code
    ↓ javac
class bytes
    ↓ loading
runtime Class object exists
    ↓ linking
verified + prepared + symbolic references resolved as needed
    ↓ initialization
static initialization runs when active use requires it
    ↓
normal execution
```

These words describe different responsibilities:

| Stage | Main question | Typical result |
| --- | --- | --- |
| Loading | Where are the bytes for this binary class name, and which loader defines them? | A runtime `Class<?>` exists. |
| Linking | Are the bytes valid, is static storage prepared, and what do symbolic references point to? | The class is safe and structurally connected enough for use. |
| Initialization | When should class initialization code actually run? | Static field initializers and static blocks have executed. |

The **defining ClassLoader** is especially important. It is the loader that actually calls `defineClass` for a class, and it becomes part of that class's runtime identity. A loader may be asked to load a class but delegate the request to its parent; in that case the parent, not the requester, is the defining loader.

For the running example in this module, imagine a tiny plugin system:

```java
package demo.api;

public interface Plugin {
    String name();
}
```

The main application owns `Plugin`, while plugin implementations may come from another directory or JAR. The application therefore needs answers to several connected questions: which loader should own the API, which loader should define a plugin implementation, whether two same-named plugin classes are actually the same type, how a framework discovers plugin providers, and what must be released when a plugin is unloaded.

That gives the learning path for the module:

```text
Lifecycle
  → Built-in loaders
  → Parent delegation
  → Custom loaders
  → Class identity
  → Thread context ClassLoader
  → Resource loading
  → Initialization details
  → Unloading and leak prevention
```

The first rule to keep in mind is therefore simple: **"class bytes exist" and "the JVM has an initialized runtime class" are different states.**

## <a id="linking-phases">Verification, Preparation, and Resolution</a>

After loading, the JVM links the class. Linking prevents raw class bytes from becoming executable runtime behavior without structural checks and runtime setup.

Linking contains three conceptual phases:

1. **Verification** checks that the class-file structure and bytecode satisfy JVM constraints. Invalid bytecode must not be allowed to corrupt JVM type or memory safety.
2. **Preparation** allocates storage for static fields and gives them their default values. Java source initializers have not run yet.
3. **Resolution** turns symbolic references in the class file into direct runtime references when the JVM needs them. A JVM may resolve references lazily rather than resolving every dependency immediately.

Consider:

```java
final class PluginRegistry {
    static int maxPlugins = loadConfiguredLimit();

    private static int loadConfiguredLimit() {
        System.out.println("computing limit");
        return 20;
    }
}
```

During **preparation**, storage for `maxPlugins` exists and initially contains the JVM default value `0`. The call to `loadConfiguredLimit()` belongs to **initialization**, so it has not executed during preparation.

Resolution is also different from source-level imports. An `import` helps the Java compiler resolve names in source code; it does not eagerly load or initialize the imported class at runtime. Runtime resolution concerns symbolic references stored in class files, such as references to another class, field, or method.

### Which loader is used when class A needs class B?

This is the bridge from lifecycle to parent delegation. Under JVM class/interface resolution, when class `A` has a symbolic reference to class/interface `B`, **the defining ClassLoader of `A` is used to load `B`**. That loader may define `B` itself or delegate to a parent; the loader that ultimately defines `B` becomes `B`'s defining loader.

For the running plugin example:

```text
HelloPlugin
→ defined by PluginClassLoader
→ bytecode references demo.api.Plugin
→ JVM needs to resolve Plugin
→ loading starts through PluginClassLoader
→ PluginClassLoader applies parent delegation
→ parent Application ClassLoader already owns Plugin API
→ same shared Plugin.class is returned
```

The useful mental model is not to memorize VM internals, but to understand that the referring class's defining loader is the natural starting point for dependency loading. TCCL later exists because parent-owned framework code sometimes needs a different discovery context to see child/application providers.

This separation allows the JVM to check and prepare a type before executing its static initialization logic. It also explains why failures may appear at different moments: malformed bytecode can fail during verification, a missing referenced type can surface during resolution, and user code can fail later during initialization.

### Failure model: map the error to the lifecycle stage

Class-loading failures are easier to reason about when they are tied back to the runtime question being answered:

| Symptom | Mental model |
| --- | --- |
| `ClassNotFoundException` | Code explicitly asked a `ClassLoader`/`Class.forName` operation for a binary name and the requested class could not be found. Dynamic-loading APIs often expose this as a checked exception. |
| `NoClassDefFoundError` | The JVM needs a class definition during normal execution/linking but that definition cannot be made available or completed. It can also be seen on later active use after class initialization previously failed. |
| `VerifyError` | Bytes were loaded, but bytecode/class-file verification detected a JVM constraint violation. |
| `ClassFormatError` | Bytes were found, but they are not a valid JVM class-file representation. |
| `UnsupportedClassVersionError` | The class file targets a newer class-file version than the current JVM supports. |
| `LinkageError` | A family of errors indicating that definition/linking cannot produce a consistent runtime type graph; examples include `NoClassDefFoundError`, `ClassFormatError`, `NoSuchMethodError`, and `IncompatibleClassChangeError`. |

A useful debugging flow is:

```text
explicit dynamic lookup cannot find the requested name?
→ ClassNotFoundException

runtime dependency cannot be made available/linked?
→ NoClassDefFoundError or another LinkageError

bytes were found but the format/version is invalid?
→ ClassFormatError / UnsupportedClassVersionError

static initialization failed earlier?
→ first active use often ExceptionInInitializerError
→ later active use may be NoClassDefFoundError: Could not initialize class
```

The names matter less than the diagnostic questions: **were the bytes found, could the JVM define/link them, and did initialization succeed?**

## <a id="initialization-trigger">Active Use Triggers Initialization</a>

Initialization is delayed until the JVM sees an **active use** that requires the class or interface to be initialized. The purpose of the delay is practical: loading metadata does not always mean the program needs to execute that type's static setup immediately.

Common initialization triggers include:

- creating an instance with `new`;
- invoking a `static` method declared by the class;
- reading a `static` field declared by the class when that field is not a compile-time constant;
- assigning a `static` field declared by the class;
- reflective operations that explicitly request initialization, such as `Class.forName("...")` with initialization enabled.

Before a class is initialized, its superclass is initialized first. Some initialization rules for interfaces are more selective, which is why initialization should be understood as a JVM lifecycle rule rather than as "the first time the source file is mentioned."

For example:

```java
final class PluginBootstrap {
    static {
        System.out.println("PluginBootstrap initialized");
    }

    static void start() {
        System.out.println("plugin system started");
    }
}

public class Demo {
    public static void main(String[] args) {
        PluginBootstrap.start();
    }
}
```

The first invocation of `PluginBootstrap.start()` requires `PluginBootstrap` to be initialized before the method executes. The static block therefore runs first.

The later Initialization chapter goes deeper into `<clinit>`, synchronization, failure state, and compile-time constants. At this point, the key relationship is that **loading makes a class available to the runtime; active use is what normally forces initialization**.

## <a id="load-vs-initialize">Loading Is Not Initialization</a>

The difference can be observed directly with `Class.forName`:

```java
final class TracedPlugin {
    static {
        System.out.println("TracedPlugin initialized");
    }
}

public class LoadingDemo {
    public static void main(String[] args) throws Exception {
        ClassLoader loader = LoadingDemo.class.getClassLoader();

        Class<?> type = Class.forName(
                "demo.TracedPlugin",
                false,
                loader
        );

        System.out.println("loaded: " + type.getName());

        Class.forName(
                "demo.TracedPlugin",
                true,
                loader
        );
    }
}
```

The first call requests the class without initialization. Obtaining the `Class<?>` therefore does not, by itself, prove that the static block has run. The second call explicitly requests initialization, so the initialization message appears at that point if the class has not already been initialized.

This matters in frameworks and tools. A scanner may need class metadata without wanting to trigger database connections, native library loading, registry mutation, or other static side effects. A plugin manager may want to inspect or stage classes before activating them. Treating "loaded" and "initialized" as the same state would make those operations much harder to control.

It also matters while debugging. Seeing a class in a stack trace, heap view, or `Class<?>` variable does not tell you that its initialization completed successfully. Loading, linking, and initialization are separate lifecycle concepts, and later chapters build on that separation.
