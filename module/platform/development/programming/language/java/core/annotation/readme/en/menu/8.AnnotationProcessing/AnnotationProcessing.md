# Annotation Processing

Runtime reflection asks questions after classes have been loaded. That is too late when invalid metadata should fail the build, boilerplate should be generated before execution, or an index/resource must exist as part of the compiled artifact.

```text
invalid metadata
→ report a compile-time error

source implies boilerplate
→ generate source before runtime

declarations imply an index/resource
→ generate the artifact during the build
```

Annotation processing solves that timing problem by operating during compilation. A processor can inspect annotated program elements, validate rules, and generate source files or resources that become inputs to later compiler rounds.

Java's standard processing API is primarily in `javax.annotation.processing` and `javax.lang.model`. It models source/program structure through elements and types instead of requiring application classes to be loaded and executed.

## <a id="processing-rounds">Compile-time Processing Rounds</a>

Annotation processing happens in **rounds**. The compiler starts with the source types being compiled, runs applicable processors, and may receive new source/class files generated by those processors. Generated source can introduce new annotated elements, which leads to another round.

```text
initial source files
        ↓
round 1 processors run
        ↓
generated source/class files?
        ↓ yes
round 2 sees new roots
        ↓
more generated files?
        ↓
...
        ↓
final round: processingOver() == true
```

A processor receives a `RoundEnvironment` for each invocation:

```java
if (roundEnv.processingOver()) {
    // final-round cleanup/reporting if needed
}
```

`roundEnv.errorRaised()` also lets a processor observe whether an error was raised in the prior round.

### WHY — processors must tolerate repeated invocation

Do not write a processor as though `process(...)` runs exactly once. Generation in one round can cause more rounds, and the final round has different conditions from normal discovery rounds.

State kept inside a processor instance should therefore have deliberate lifecycle semantics and must not cause the same file to be generated repeatedly.

## <a id="processor-contract">`Processor` and `AbstractProcessor` Contract</a>

A processor implements `javax.annotation.processing.Processor`. Most processors extend `AbstractProcessor`, which provides standard lifecycle support.

The standard processor model spans two closely related packages:

- `javax.annotation.processing` — processor lifecycle and services;
- `javax.lang.model` — declarations and compile-time types exposed by the compiler.

Use this mental model before reading processor code:

```text
Element
→ a source/model declaration such as a class, method, field, or parameter

TypeElement
→ an Element representing a type declaration such as a class/interface/record/annotation interface

TypeMirror
→ a Java type represented at compile time

AnnotationMirror
→ an annotation represented in the compiler model

Elements
→ utility service for declaration-model queries

Types
→ utility service for type-model queries/comparisons
```

```java
public final class AuditProcessor extends AbstractProcessor {

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        for (Element element :
        roundEnv.getElementsAnnotatedWith(GenerateMapper.class)) {
            // inspect element model
        }

        return true;
    }
}
```

Returning `true` means the processor claims the annotation types it was asked to process for that round, so subsequent processors are not asked to process those claimed types. Returning `false` leaves them unclaimed for other processors.

`AbstractProcessor` exposes the compiler environment after initialization through `processingEnv`. Useful services include:

```text
Messager
→ emit diagnostics attached to compilation

Filer
→ create generated source/class/resource files

Elements
→ query language-model elements

Types
→ query/compare language-model types
```

Prefer `Messager` for processor diagnostics rather than printing arbitrary text to standard output:

```java
processingEnv.getMessager().printMessage(
        Diagnostic.Kind.ERROR,
        "@GenerateMapper requires a valid type declaration",
        element
);
```

That lets the compiler associate the message with the relevant program element.

### DISCOVERY — how does the compiler find a processor?

A processor can be named explicitly with compiler options, discovered as a service provider (for example through `META-INF/services/javax.annotation.processing.Processor`), or provided through the Java module system with an appropriate `provides ... with ...` declaration.

Discovery/configuration is part of the build contract. Merely placing a `Processor` implementation somewhere in application source does not guarantee it will participate in compilation.

The processor itself must already be compiled and made available to the compiler/build tool before it can process the application's source:

```text
processor source
→ compile processor library/JAR
        ↓
build tool / javac puts it on the processor path
        ↓
compiler discovers and initializes processor
        ↓
process(...) participates in rounds
```

## <a id="supported-types-source-version">Supported Annotation Types and Source Version</a>

A processor declares which annotation types it supports. `AbstractProcessor` can derive this from `@SupportedAnnotationTypes`:

```java
@SupportedAnnotationTypes("com.example.Audit")
public final class AuditProcessor extends AbstractProcessor {
    // ...
}
```

Patterns may also use `*` according to the processor API contract when a processor intentionally supports a broader set.

The processor also declares the latest source version whose language model it supports. For Java 21 code, a processor can state:

```java
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public final class AuditProcessor extends AbstractProcessor {
    // ...
}
```

or override `getSupportedSourceVersion()` when a dynamic policy is appropriate.

### WHY — source version is a compatibility claim

Do not blindly claim a newer source version merely to silence a warning. New Java releases can add element kinds, syntax, or model details that processor logic must handle correctly.

```text
processor declares RELEASE_21
→ claims it understands the Java 21 source/model level it will inspect
```

The annotation type set and source version together define when the compiler should consider the processor applicable and what language model the processor claims to understand.

### Processor options with `@SupportedOptions`

A processor can also declare build-level options that it understands:

```java
@SupportedOptions("mapper.debug")
@SupportedAnnotationTypes("com.example.GenerateMapper")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public final class MapperProcessor extends AbstractProcessor {
}
```

A compiler/build tool can pass a processor option in a form such as:

```text
-Amapper.debug=true
```

and the processor can read it from:

```java
String debug =
        processingEnv.getOptions().get("mapper.debug");
```

Processor options are build-level inputs. Annotation elements are metadata attached to particular declarations/types; they solve a different configuration problem.

## <a id="generated-source">Generating Source and Resources</a>

An end-to-end miniature example makes the pipeline concrete.

Application annotation:

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.SOURCE)
public @interface GenerateMapper {
}
```

Application source:

```java
@GenerateMapper
class Order {
}
```

Processor logic:

```java
public final class MapperProcessor extends AbstractProcessor {

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        for (Element element :
                roundEnv.getElementsAnnotatedWith(GenerateMapper.class)) {

            String generatedName =
                    element.getSimpleName() + "MapperGenerated";

            try {
                JavaFileObject file =
                        processingEnv.getFiler()
                                .createSourceFile(generatedName, element);

                try (Writer writer = file.openWriter()) {
                    writer.write(
                            "final class " + generatedName + " {}"
                    );
                }
            } catch (IOException e) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        e.getMessage(),
                        element
                );
            }
        }

        return true;
    }
}
```

Observable flow:

```text
@GenerateMapper on Order
→ roundEnv discovers Order
→ processor calls Filer
→ OrderMapperGenerated.java is created
→ output is closed
→ compiler observes the generated source in a later round
→ generated source compiles like ordinary Java source
```

`Filer` is the standard output boundary for generated artifacts.

```java
JavaFileObject file = processingEnv.getFiler()
        .createSourceFile("com.example.generated.AuditIndex", element);

try (Writer writer = file.openWriter()) {
    writer.write("""
            package com.example.generated;

            public final class AuditIndex {
                private AuditIndex() {}
            }
            """);
}
```

Generated source files are compiled in later rounds of the same compilation when applicable. `Filer.createResource(...)` can similarly produce resources in supported output locations.

The optional originating elements passed to `createSourceFile`, `createClassFile`, or `createResource` describe which program elements caused the output. Build tools may use that relationship for dependency/incremental reasoning.

### BOUNDARY — generate new artifacts; do not rewrite user source

The standard annotation-processing model is designed around inspecting elements and creating new files through `Filer`. It is not a portable source-rewriting API.

```text
inspect @Audit declarations
→ generate AuditIndex.java
→ compiler sees generated type in a later round
```

Trying to generate the same file again in another round causes a filer error. Processors must therefore keep generation idempotent at the logical level and understand which round owns each output.

## <a id="processing-vs-reflection">Annotation Processing vs Runtime Reflection</a>

Processing and reflection consume metadata at different lifecycle stages and through different program models.

| Question | Annotation processing | Runtime reflection |
| --- | --- | --- |
| When? | During compilation | While application/runtime code executes |
| Main model | `Element`, `TypeMirror`, compiler model | `Class`, `Method`, `Field`, etc. |
| Can see SOURCE-retained annotations during compilation? | Yes, when applicable to the processing model | No |
| Can generate source/resources for compilation? | Yes | Not as part of compiler processing rounds |
| Requires `RUNTIME` retention for annotation lookup? | No | Yes for ordinary reflective annotation access |

For example, a compile-time processor can validate `@Audit` usage and generate an index even if `@Audit` is SOURCE-retained. A runtime library that calls `Method.getAnnotation(Audit.class)` requires the annotation to survive with RUNTIME retention.

### `Class`-valued annotation elements at compile time

If an annotation element has a type such as `Class<?>`, processor code should not assume the referenced user type can be loaded as a runtime `Class`. General processors are usually safer working with `AnnotationMirror` and `TypeMirror`. Proxy-style access to class-valued elements can surface `MirroredTypeException` or `MirroredTypesException` because the compiler is representing source types, not running application classes.

```text
compile-time consumer
→ annotation processing module boundary

runtime metadata inspection
→ reflection module boundary
```

Do not model annotation processing as “reflection that happens earlier”. The APIs, available information, lifecycle, and outputs are different.

## <a id="processor-pitfalls">Processor Determinism and Generated-code Pitfalls</a>

Annotation processors participate in every consumer's build, so small design mistakes can make compilation fragile or non-reproducible.

### PITFALL — non-deterministic output

Avoid output that depends on unstable iteration order, timestamps, random values, machine-specific paths, or network responses unless the build contract explicitly requires them.

```text
same source + same processor inputs
→ should normally produce the same generated artifacts
```

Sort elements when output order matters and keep external side effects outside ordinary processing logic.

### PITFALL — assuming one round

Generated sources can create new rounds. Track what has already been generated and do not recreate the same file on each call to `process(...)`.

The final round (`processingOver() == true`) is appropriate for final diagnostics or cleanup. Do not generate a new type there if the design expects another normal processing round to consume that type.

### PITFALL — source-name collisions

Before choosing generated type names, define a stable ownership/naming scheme. Two processors or two annotated elements attempting to create the same source file will conflict.

### PITFALL — treating compiler internals as portable API

`javax.annotation.processing` and `javax.lang.model` are the standard contracts. Depending on compiler-specific AST internals can tie a processor to one compiler implementation or release and should be a deliberate choice rather than an accidental dependency.

### PITFALL — hiding actionable validation errors

When metadata is invalid, report a precise diagnostic on the relevant element. A generated file that fails later with an unrelated compiler error gives the user a much worse feedback loop.

### TRADE-OFF — generated code reduces runtime work but adds build complexity

Compile-time generation can move discovery and validation earlier, improve type safety, and avoid some runtime scanning. It also introduces processor configuration, generated-source debugging, build-cache/incremental-build concerns, and another compatibility surface.

Use annotation processing when compile-time validation or generation materially improves the design. For runtime-only metadata decisions, a processor may add complexity without removing a real problem.

This completes the annotation lifecycle story: define structured metadata, constrain where it is valid, choose how long it survives, understand repeatable/inherited lookup, and select a compile-time or runtime consumer that matches the problem.
