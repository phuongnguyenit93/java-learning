## <a id="process-memory-purpose">Why the Java Heap Is Not the Whole JVM Process Memory</a>

<details>
<summary>Click for details</summary>

A JVM process needs much more memory than the storage used for Java objects. Beyond the heap, the runtime needs thread stacks, class metadata, compiled code, internal VM structures, native libraries, direct buffers, and memory used by other subsystems.

So:

```text
process RSS / committed memory
≠ Java heap usage
```

A dashboard that only watches `-Xmx` or heap-used metrics can miss the reason a process hits a container/OS limit while the heap still has free space.

This chapter builds a **whole-process memory model**. Measuring categories with NMT/JFR/OS tooling belongs to Runtime Diagnostics.

</details>

## <a id="runtime-areas-vs-process-memory">Runtime Data Areas vs Process-Level Memory</a>

<details>
<summary>Click for details</summary>

JVMS runtime data areas are abstractions that define execution semantics. Process-level memory is how a concrete implementation obtains native/virtual memory from the operating system to implement those abstractions and other runtime subsystems.

There is no required one-to-one mapping:

```text
spec concept       implementation examples
-----------        -----------------------
heap               heap reservation/commit
method area        class metadata structures
JVM stacks         native thread-stack mappings
execution engine   code cache/compiler data
```

A JVM implementation may reorganize these internals across releases and still conform to the same specification.

Do not force every byte reported by the OS into exactly one JVMS runtime area.

</details>

## <a id="thread-and-native-stack-memory">Thread-Stack and Native-Stack Memory</a>

<details>
<summary>Click for details</summary>

Each platform thread requires process-level stack resources. A large platform-thread count can therefore consume significant memory even when each thread allocates almost nothing on the Java heap.

```text
N platform threads
× per-thread stack reservation
→ process virtual/native memory pressure
```

`-Xss` is a HotSpot/JVM-launcher control associated with thread-stack sizing, not a universal Java language rule.

Virtual threads use a different runtime architecture, but their scheduling and stack model belong to the Concurrency/Virtual Threads curriculum. The JVM lesson here is simply that thread count can affect total process memory.

</details>

## <a id="class-metadata-memory">Class Metadata and Memory Beyond the Heap</a>

<details>
<summary>Click for details</summary>

The runtime must retain metadata for loaded classes: type information, field/method structures, and other state required for class lifecycle and execution.

Modern HotSpot commonly stores much of this class metadata in **Metaspace**, which uses native memory rather than ordinary Java object heap.

Practical consequences include:

- loading many distinct classes/class loaders can increase native memory;
- unloading depends on class-loader reachability/lifecycle;
- a healthy Java heap does not rule out class-metadata pressure.

Diagnosing class-loader leaks belongs to Class Loading/Runtime Diagnostics. Here the goal is recognizing class metadata as a non-heap contributor.

</details>

## <a id="compiled-code-memory">Memory for Compiled Code</a>

<details>
<summary>Click for details</summary>

Machine code generated by the JIT compiler requires executable process memory. HotSpot manages this through code-cache-related structures.

Compiled-code memory can grow as the runtime profiles and compiles more methods. It is not ordinary Java object heap.

```text
warm-up
→ more compilation
→ more generated native code
→ process memory may increase
```

This helps explain why a service may have a larger RSS after several minutes even when its live heap is similar to startup.

Measuring code-cache/compiler pressure belongs to diagnostics tooling.

</details>

## <a id="direct-and-offheap-memory-awareness">Direct and Off-Heap Memory Awareness</a>

<details>
<summary>Click for details</summary>

`ByteBuffer.allocateDirect` creates a **direct byte buffer**. The Java API contract does not simply define “direct” as “off-heap”; it states that the JVM will make a best effort to perform native I/O directly on the buffer and avoid intermediate copying where possible. HotSpot commonly backs direct-buffer contents with native memory, so that footprint may not appear as ordinary Java-heap usage.

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(1 << 20);
```

“Off-heap” is a broad label: not all native memory is a direct buffer, and different off-heap mechanisms have different ownership/lifetime rules.

The practical lesson is:

```text
heap monitoring
→ does not describe all application memory
```

JNI/FFM native-memory programming belongs to Native Interoperability.

</details>

## <a id="process-memory-growth">Why Process Memory Can Grow While the Heap Is Not Full</a>

<details>
<summary>Click for details</summary>

Process memory can increase for reasons independent of the live Java heap:

- more platform threads;
- more loaded classes/class loaders;
- JIT compilation and code-cache growth;
- direct buffers;
- JNI/native libraries;
- runtime internal structures;
- allocator fragmentation or committed-but-currently-unused memory.

So this pattern is not contradictory:

```text
heap used: stable
RSS: rising
```

At that point the right question is no longer only “heap leak?” but “which memory category is growing?” NMT/OS evidence belongs to Runtime Diagnostics.

</details>

## <a id="nonheap-resource-exhaustion">Memory and Resource Exhaustion Beyond the Heap</a>

<details>
<summary>Click for details</summary>

An application can fail because of process/native resource pressure even when the Java heap has not reached `-Xmx`.

Examples include class-metadata pressure, inability to create more native threads, failed direct/native allocations, or exceeding a container memory limit.

The failure may still surface as an `OutOfMemoryError` with a particular message, or the operating system/container may terminate the process.

Therefore:

```text
OutOfMemoryError
→ a failure category, not one universal root cause
```

Root cause requires evidence from the error, process limits, and diagnostic tools.

</details>

## <a id="native-memory-vs-native-interoperability">Native-Memory Awareness vs Native Interoperability</a>

<details>
<summary>Click for details</summary>

The JVM module teaches **native-memory awareness** so you can reason about total process footprint and runtime implementation resources.

Native Interoperability teaches how Java code **actively crosses the native boundary** using mechanisms such as:

- JNI;
- the Foreign Function & Memory API;
- native-library loading;
- linker/symbol lookup;
- explicit native-memory lifetime.

```text
JVM Process Memory
→ “Where is the runtime consuming memory?”

Native Interoperability
→ “How does Java code call or access native resources?”
```

The topics meet around memory safety and lifetime, but they have different learning goals.

</details>
