# Overview: Source Collaboration with GitLab

GitLab hosts Git-backed projects and repositories where teams propose changes through merge requests, discuss and review work, and govern when changes can be accepted. Git owns version history and command mechanics; GitLab adds group/project ownership, membership permissions, review and approval workflows, and protected branches. Proposing a change is not the same as being authorized to merge it.

**Prerequisites:** Know the basic Git concepts of repositories, commits, and branches. No prior GitLab user-interface or CI/CD configuration knowledge is required.

**Learning path:** Begin with projects/repositories, personal namespaces, groups and subgroups, participants, and merge request fundamentals. Continue with project organization and visibility, permissions and inherited membership. Learn contribution through a shared-project branch or a fork, the merge request lifecycle, reviewers, and approvals. Then study protected branches and overlapping rules before connecting Issues and Releases. Finish by tracing a team change and diagnosing merge blockers.

**Learning outcome:** Identify ownership and access scopes, choose a valid merge request contribution path, interpret review evidence and approval conditions, understand branch protection gates, and locate the controls to investigate an unmergeable proposal. Some features and visibility choices vary by GitLab tier and by GitLab.com, Self-Managed, or Dedicated offerings.

**Boundaries:** Git commands and internals belong to Git; team branch-model decisions belong to Branching Strategy. GitLab CI/CD appears only as context for check status rather than pipeline implementation. Issues and Releases remain project collaboration surfaces, not a replacement for project-management methodology, versioning, deployment, or specialized DevSecOps.
